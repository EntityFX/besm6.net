# Dhrystone virtual: горячий цикл, JIT и учёт команд

Дата: 15 октября 2026. Код базы — `b1a172e`; измерения выполнены поверх `4466355`, добавившего материалы статьи без изменения процессора. Все эксперименты выполнены поверх опубликованного memory watchpoint batching, с `memoryWatchpointBatching=true`.

**Оставлено одно изменение:** `NoInlining` на внутреннем generic-цикле [InstructionExecutor.ExecuteUnobservedBlock](../../src/Besm6.Processor/Execution/InstructionExecutor.cs#L223). Архитектура, публичные API, реализации команд, учёт и проверки памяти сохранены. В повторной серии на 50000 итераций без `--stats` CPU процесса снизился на 6.0%; со статистикой разница медиан составила только 0.9%. Это результаты этого хоста, а не обещание ускорения на любом .NET/CPU.

## Итоги по приоритетам

| Участок | Проверено | Решение |
|---|---|---|
| Горячий цикл | Стековые профили, Tier1 disassembly, дублирование цикла в обёртке, повторные чтения состояния и A/Y | Оставить границу встраивания; вариант с локальными значениями fetch отклонить |
| Оставшиеся JIT-атрибуты исполнителей памяти/переходов | Два варианта, повторная серия | Отклонить снятие `AggressiveOptimization`: выигрыш не воспроизвёлся; [отдельный отчёт](dhrystone-jit-dispatch.md) |
| `ProcessorInstructionAccounting.Begin/Complete` | Вариант с объединённой проверкой pending/границ таблицы, A/B | Отклонить: ускорения нет; pending во время исполнения сохранён |
| Запуск и FOREX | Короткий профиль, разность размеров, проверка границы по выводу, путь загрузки по коду | Постоянные затраты значительны; точная доля компилятора не измерена, кэширование гостевого образа не внедрено |

Продолжение: [дополнительные варианты accounting и измерение фаз запуска](dhrystone-accounting-startup.md).

## Что показали профиль и машинный код

Release net8.0, SDK 10.0.202, runtime 8.0.26, Intel Core i5-4570TE, 2 ядра / 4 логических процессора, Windows. По одной трассе основного потока для каждого режима/варианта на 50000 итераций: `dotnet-sampled-thread-time,dotnet-common`, преобразование в Speedscope. Отдельно снят короткий профиль оставленного варианта без статистики.

Ниже **доли собственных выборок стеков**, включая встроенный код. Это не фактические проценты CPU и не число вызовов. Одна трасса на сочетание не задаёт доверительный интервал. Время профилируемых запусков не используется для оценки ускорения.

| Метод / категория | База stats, % | NoInlining stats, % | База без stats, % | NoInlining без stats, % |
|---|---:|---:|---:|---:|
| `ExecuteUnobservedBlock` — обёртка | 70.56 | 2.10 | 70.81 | 4.42 |
| `ExecuteUnobservedBlock<TAccounting>` — цикл | 3.58 | 75.66 | 2.94 | 72.10 |
| `MemoryInstructionExecutor.ExecuteOther<TExecution>` | 5.09 | 5.28 | 5.50 | 6.73 |
| `IndexInstructionExecutor.Execute` | 1.48 | 1.42 | 1.61 | 1.52 |
| `ControlInstructionExecutor.ExecuteOther` | 0.99 | 0.73 | 1.25 | 1.16 |
| Unmanaged / неразрешённые native-стеки | 7.37 | 7.05 | 6.41 | 6.17 |

Основная цепочка: `DubnaLoader.BootAndRun → ExecutionLoop.RunCore → FunctionalProcessorSimulation.ExecuteBlock → InstructionExecutor.ExecuteUnobservedBlock → ExecuteUnobservedBlock<TAccounting> → Dispatch`. Перенос выборок из обёртки во внутренний цикл отражает изменение встраивания, а не исчезновение исполнения команд.

В снятых Tier1 disassembly counted-пути:

| Сгенерированный метод | База, байт | NoInlining, байт |
|---|---:|---:|
| Внешний `ExecuteUnobservedBlock` | 11659 | 321 |
| Отдельный generic-цикл | 17725 | 16426 |
| Сумма этих двух тел | 29384 | 16747 |

До изменения JIT встроил большую версию цикла в обёртку с обработчиком `DebugWatchAbortException`, одновременно сохранив отдельную версию. Запрет встраивания уменьшил суммарный размер этих двух тел на 43%. Это размеры из конкретных диагностических запусков, а не всего JIT-кода процесса. Tiered compilation и Dynamic PGO остались активны — это подтверждено заголовками disassembly. Новая граница вызова находится на блоке, а не на каждой команде.

Доказано уменьшение размера и изменение размещения кода. Уменьшение instruction-cache misses не измерялось; приписывать ему весь наблюдаемый выигрыш нельзя.

### Повторные обращения к состоянию и A/Y

В исходном цикле после нормализации `K` адрес снова читается для `MemFetch` и индекса decode cache, а `IsRightHalf` — для fetch, выбора полуслова и индекса. Tier1 действительно содержит повторные загрузки полей и пути проверок типов для интерфейсов состояния. Проверен вариант с локальными `instructionAddress` и `rightHalf` только в fetch/decode; повторное чтение состояния после `accounting.Begin` не переносилось через потенциальный вызов пользовательского accounting.

Загрузка A/Y в `ExecutionFrame` выполняется до dispatch даже для команд, которым эти значения не нужны. В disassembly видны две загрузки 64-битных значений и сохранение в кадр. Обратная публикация уже условна: `FinalizeInstruction` проверяет `RegistersInState`. Поэтому безусловно убирать запись A/Y или считать её одинаковой для всех команд неправильно.

Локальные значения fetch не дали выигрыша; они восстановлены. Ленивую загрузку A/Y не внедряли: дублирование классификации опкодов либо изменение представления кадра потребует отдельной проверки и может увеличить расходы других команд. Роли состояния не заменялись прямыми обращениями к конкретному процессору.

## A/B без профилировщика

У каждого варианта отдельная копия DLL/PDB/runtimeconfig. На каждой итерации измерений запускается новый процесс. Порядок вариантов чередуется, размеры идут в разном порядке по раундам. Команды используют `--speed virtual --guest-clock --no-wall-clock --limit 200000000`, со статистикой или без неё. Прогрев исключён из медиан; исключённых выбросов нет.

На длинном запуске без статистики CPU −6.0%, wall −4.0%; в первой серии CPU −11.7%. С `--stats` в повторной серии CPU −0.9%, wall практически без изменения. Медиана относительной разницы CPU внутри пяти пар: −8.2% без stats и −4.6% со stats; в обоих случаях кандидат выиграл четыре пары из пяти. Эти показатели отличаются от отношения медиан, поэтому не подменяются друг другом.

Разброс на хосте заметен, статистическая значимость не установлена. Короткий запуск со stats сильно зависит от запуска процесса/JIT; его −11.5% CPU нельзя переносить на вычислительный цикл. Между режимами нет гарантированного постоянного соотношения; отдельное обсуждение — в [отчёте о stats](dhrystone-memory-watchpoint-batching.md).

## Дополнительные отклонённые варианты

Каждый вариант сравнивался с уже оставленным `NoInlining`. По одному предварительному и три измерения на 50000 итераций; порядок трёх вариантов вращается.

| Режим | Вариант | Wall, с | CPU, с | CTIME, с |
|---|---|---:|---:|---:|
| Без stats | NoInlining | 4.435 | 4.453 | 2.94 |
| Без stats | Локальные значения fetch | 4.420 | 4.500 | 2.88 |
| Без stats | Изменённый Complete | 4.561 | 4.547 | 2.88 |
| Stats | NoInlining | 4.839 | 4.969 | 3.22 |
| Stats | Локальные значения fetch | 5.015 | 5.078 | 3.26 |
| Stats | Изменённый Complete | 4.951 | 5.031 | 3.24 |

У `Complete` пробовали сначала unsigned-проверку попадания opcode в таблицу: отрицательный pending и неизвестные опкоды уходили в ветку fallback. Обычный путь объединял проверку наличия pending с проверкой границ таблицы. Контракты `Begin`, `CancelPending`, cycle limit и исключений при этом не менялись. Медиана CPU со stats стала на 1.3% хуже, локальный fetch — на 2.2% хуже. Эти небольшие различия не доказывают устойчивую регрессию, но оснований оставлять правки нет. Оба варианта отменены.

Отдельно упрощать учёт через удаление `Begin` нельзя: watchpoint оставляет незавершённую команду, а исключения и лимиты имеют заданный порядок завершения. В исходном коде pending снимается только в `Complete`; эта схема сохранена. Большой вес встроенного цикла не позволяет утверждать, что основная проблема — accounting.

## Инициализация и компиляция FOREX

В коротком профиле без stats generic-цикл получил 56.06% собственных выборок, обёртка — 8.75%, `MemoryInstructionExecutor.ExecuteOther` — 4.76%, `TextWriter.SyncTextWriter.Write` — 1.16%, unmanaged-категория — 13.55%. Это профиль всего короткого запуска, а не отдельной фазы компиляции. Гостевой FOREX исполняется внутри того же эмулятора; название managed-метода не отделяет компиляцию от Dhrystone.

По [пути загрузки](../../src/Besm6.Runtime/Loading/DubnaLoader.cs#L160) job записывается на барабан, монтируются образы, запускаются MONSYS и гостевой компилятор. [JobProgramLoader](../../src/Besm6.Runtime/Loading/JobProgramLoader.cs#L35) кодирует строки в COSY; сам FOREX не является отдельной функцией .NET. `RunScript` также дважды читает исходный файл — через `ParseFile` и `ReadAllLines`; его стоимость здесь не подтверждена как существенная, поэтому это не объявлено узким местом.

Если приблизить CPU процесса линейной моделью `C(N)=Cfixed+N*Citeration`, то для оставленного варианта без stats по разнице медиан:

- `Citeration ≈ (4.6875−2.109375)/45000 = 57.3 мкс`;
- `Cfixed ≈ 1.823 с CPU`, около 86% CPU короткого запуска.

Это оценка по двум размерам, включающая загрузку, компиляцию, JIT, подготовку и контрольный вывод. Она **не измеряет отдельно FOREX** и зависит от предположения о линейности; разная история JIT/PGO между процессами ограничивает точность. Доли CPU нельзя получать простым вычитанием гостевого CTIME из CPU процесса: в virtual гостевые часы отражают elapsed time, а не CPU.

Попытка установить начало тела по появлению заголовка `DHRYSTONE 2.1` в stdout отклонена: даже быстрый C# reader наблюдает заголовок почти в конце процесса, с оставшимися 0.016–0.047 с CPU. Эти значения несовместимы с длительностью тела по CTIME и не дают пригодной границы. Сырые результаты сохранены, в оценки выше не входят. Точные границы CTIME не инструментировались.

## Проверка

- 88 A/B-запусков этого этапа, включая предварительные: 16 предварительной серии NoInlining, 48 повторной и 24 дополнительных вариантов. Все завершились успешно, подтвердили 18 числовых, 4 строковых контрольных значения и `BAD CONTROL VALUES=0`.
- Все пять sampling-профилей и четыре диагностических запуска с JIT disassembly также прошли контрольные значения.
- Два запуска без гостевых часов: база и оставленный вариант совпали по `finalState`, памяти SHA-256, количеству инструкций, model cycles и ticks.
- Dhrystone `original`, 5000 итераций: контрольные значения совпали, гостевое время **4.36 с** сохранено. Это проверка семантики модельного времени, а не сравнительный бенчмарк ускорения original.
- В конце принятого блока: полная Release-сборка без предупреждений/ошибок; **3355 тестов успешно, 0 ошибок, 395 прежних пропусков**. Среди проверок — границы сборок, роли состояния, accounting/cycle limit, исключения, события, self-modification и watchpoints.
- После отклонения дополнительных вариантов восстановлен исходный `Complete` и fetch. Пересобранный процессор побайтово совпал с измеренным и проверенным вариантом NoInlining: SHA-256 `43D90AAB254D86A149E118C3898391221B82F745DC94D5B93697C279C025A296`. Та же DLL находится в каталогах Processor.Tests и Runtime.Tests; повторный полный прогон идентичного кода не выполнялся.
- Статья и пользовательские материалы этим этапом не редактировались. Новых настроек и публичных API нет.

Следующий приоритет — отделить холодные ветки dispatch от частых команд и проверить машинный код кадра, прежде чем менять загрузку A/Y. Потенциал пока не измерен; риск — изменение публикации состояния при исключениях и переходах. Для ускорения короткого задания стоит отдельно оценить повторное использование готового гостевого задания; корректный ключ кэша должен учитывать deck, образы библиотек, конфигурацию и начальное состояние. Это более высокий риск воспроизводимости и отдельная задача. GC и переписывание арифметики этот этап не обосновывает.
