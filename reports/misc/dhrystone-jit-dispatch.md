# Dhrystone virtual: проверка JIT-атрибутов исполнителей

Дата: 15 октября 2026. База: `b1a172e9e9ed88b684bf89e17e6c5158021ab184`, опубликована в `origin/main`.

**Решение: эксперимент отклонён, исходные атрибуты восстановлены.** Первоначальный выигрыш не воспроизвёлся в повторной серии. Новых изменений кода приложения по результатам этого этапа нет.

## Проверяемые варианты

| Вариант | Отличие от базы |
|---|---|
| baseline | Опубликованная оптимизация memory watchpoint batching |
| memory | Снят `AggressiveOptimization` с generic `MemoryInstructionExecutor.ExecuteOther<TExecution>` |
| both | Дополнительно снят `AggressiveOptimization` с `ControlInstructionExecutor.ExecuteOther` |

Участки: [MemoryInstructionExecutor](../../src/Besm6.Processor/Execution/MemoryInstructionExecutor.cs#L102), [ControlInstructionExecutor](../../src/Besm6.Processor/Execution/ControlInstructionExecutor.cs#L64). Тела методов, роли состояния, публичные API и архитектура не менялись. Гипотеза: разрешение tiered compilation для этих методов может дать дополнительный выигрыш после оптимизации главного цикла. Генерируемый машинный код не анализировался, поэтому причины отдельных колебаний JIT не приписываются.

## Методика

Release, net8.0, SDK 10.0.202, runtime 8.0.26, Windows, Intel Core i5-4570TE (2 ядра / 4 логических процессора). `memoryWatchpointBatching=true`. Для каждого размера и варианта — предварительный запуск и пять измерений, каждый в новом процессе; порядок вариантов и размеров чередуется. Профилировщик не подключён. Это сравнение только со `--stats`, выводы на запуск без статистики не переносятся.

Параметры: `--speed virtual --guest-clock --stats --no-wall-clock --limit 200000000`. Исходный deck на 5000 итераций и временная копия на 50000. Все значения ниже — медианы в секундах. CPU — фактическое процессорное время полного процесса; wall — полное время процесса; CTIME — показание гостевого измерения тела Dhrystone. Доли выборок стеков здесь не измерялись.

### Первая серия

| Итерации | Вариант | Wall, с | CPU, с | CTIME, с |
|---:|---|---:|---:|---:|
| 5000 | baseline | 2.720 | 2.703 | 0.52 |
| 5000 | memory | 2.638 | 2.625 | 0.32 |
| 5000 | both | 2.318 | 2.391 | 0.32 |
| 50000 | baseline | 6.106 | 5.875 | 3.72 |
| 50000 | memory | 5.946 | 5.734 | 3.64 |
| 50000 | both | 5.681 | 5.563 | 3.48 |

Первоначальный результат `both`: CPU длинного запуска −5.3%, wall −7.0%. Из-за разброса выполнена независимая повторная серия с теми же бинарниками.

### Повторная серия baseline / both

| Итерации | Вариант | Wall, с | CPU, с | CTIME, с |
|---:|---|---:|---:|---:|
| 5000 | baseline | 2.175 | 2.281 | 0.34 |
| 5000 | both | 2.595 | 2.703 | 0.34 |
| 50000 | baseline | 5.719 | 5.703 | 3.42 |
| 50000 | both | 5.681 | 5.656 | 3.40 |

На длинном запуске осталось −0.8% CPU и −0.7% wall. На коротком получено +18.5% CPU и +19.3% wall. В первой серии CPU базы длинного запуска менялся от 5.609 до 8.016 с; сравнивать небольшие изменения медиан без повторения недостаточно. Статистическая значимость не установлена; ни стабильное ускорение, ни стабильная регрессия этих атрибутов не доказаны. Оснований включать изменение нет.

## Проверки

- 60 запусков с гостевыми часами: 36 в первой серии и 24 во второй, включая предварительные. Все завершились успешно, подтвердили 18 числовых, 4 строковых контрольных значения и `BAD CONTROL VALUES=0`.
- Ещё три запуска на 5000 итераций без гостевых часов подтвердили контрольные значения и точное совпадение `finalState`, SHA-256 памяти, `completedInstructions` и `modelCycles` между baseline, memory и both.
- После восстановления обоих файлов из HEAD CLI собран в Release: 0 ошибок, 0 предупреждений.
- Полный набор тестов для отклонённого эксперимента не запускался. Опубликованная база ранее прошла полную проверку: 3355 успешно, 0 ошибок, 395 пропусков; это предыдущая проверка, а не новый прогон этого этапа.
- Статья и пользовательские изображения этим этапом не изменялись.

## Артефакты и воспроизведение

Временные материалы находятся в игнорируемом каталоге `tests-run/jit-dispatch-20261015/`: три комплекта бинарников `baseline/`, `memory/`, `both/`, SHA-256 в `*-binary-hashes.json`, журналы каждого запуска, `timing.json`, `repeat.json`, сводки `*-summary.json`, `verification.json` и журналы сборок. Эти материалы локальные, в Git не включены.

Локальное повторение при сохранённых бинарниках и временных скриптах:

```powershell
& ./tests-run/jit-dispatch-benchmark.ps1 -Variants @('baseline','memory','both') -ResultName timing -Rounds 5
& ./tests-run/jit-dispatch-benchmark.ps1 -Variants @('baseline','both') -ResultName repeat -Rounds 5
& ./tests-run/jit-dispatch-verify.ps1
```

Для повторения на другой машине нужно собрать базу, затем отдельно варианты с удалением указанных атрибутов и сохранить комплекты DLL перед следующей сборкой. Команда отдельного запуска:

```powershell
dotnet <variant>/besm6.dll run <deck.dub> --config examples/memory-watchpoint-batching.json --speed virtual --guest-clock --stats --no-wall-clock --limit 200000000
```

Профилировка после batching приведена в [предыдущем отчёте](dhrystone-memory-watchpoint-batching.md). Следующая проверяемая гипотеза — расходы учёта команд в counted-цикле. До изменения нужно разделить стоимость учёта и инлайнированного исполнения по дизассемблированию/профилю: большая доля главного цикла сама по себе не доказывает избыточные расходы. Любой кандидат требует отдельных A/B со статистикой и без неё, точного сравнения счётчиков и сохранения событий/watchpoints на границах команд.
