# Dhrystone virtual: следующая итерация с порогом 2%

Дата: 15 октября 2026. База — `414ce8d`, включая ранее принятые NoInlining и успешный accounting. Свежая Release-сборка CLI, SDK 10.0.202, runtime 8.0.26, Intel Core i5-4570TE. Memory watchpoint batching включён.

**Решение: остановить эту ветку точечных оптимизаций.** Кандидат не подтвердил выигрыш больше 2% ни со статистикой, ни без неё. Эксперимент отменён; код приложения восстановлен к базе. Вывод относится к этой итерации и проверенной оптимизации.

## Свежий профиль и кандидат

Сняты новый профиль базы и Tier1 disassembly на 100000 итераций. Около 80% собственных выборок основного потока приходится на generic `InstructionExecutor.ExecuteUnobservedBlock`, включая встроенный код.

Внутри встроенного `CoreMemory.Read` подтверждены две последовательные проверки одной границы: явная проверка с диагностическим исключением и проверка индексирования массива. Проверен один кандидат:

- в `Read` возврат `words[address]` перенесён в ветвь `address < words.Length`;
- в `Write` запись и возврат перенесены в такую же ветвь;
- приватный бросающий helper возвращал `Word48`, чтобы холодная ветвь `Read` завершалась `return ThrowAccessViolation(address)`;
- тип исключения, текст адреса/банка и публичные API сохранялись; unsafe-доступ не использовался.

Повторный disassembly подтвердил: в рассматриваемом fetch-чтении осталось одно сравнение границы вместо двух. Само устранение инструкции не означает достаточного ускорения всего приложения.

По одной трассе `dotnet-sampled-thread-time,dotnet-common` для базы и кандидата, со stats. Доли ниже — **собственные выборки стеков**, включая inlining, а не проценты фактического CPU. Профилируемые запуски исключены из таблицы производительности.

| Метод / категория | База, own % | Кандидат, own % |
|---|---:|---:|
| Generic ExecuteUnobservedBlock | 79.99 | 77.97 |
| MemoryInstructionExecutor.ExecuteOther | 5.58 | 5.63 |
| IndexInstructionExecutor.Execute | 1.64 | 1.99 |
| Внешний ExecuteUnobservedBlock | 1.49 | 1.40 |
| ControlInstructionExecutor.ExecuteOther | 1.32 | 1.66 |
| Unmanaged / неразрешённые native-стеки | 3.89 | 4.90 |

Снижение относительной доли цикла на 2.02 процентного пункта не является ускорением на 2% и не используется для прохождения порога.

## A/B без профилировщика

Порог перед замерами: сокращение CPU времени полного процесса **больше 2%**, основной режим — со stats; wall time и режим без stats проверяются отдельно. Размер — 100000 итераций, около 142 млн команд, лимит 200 млн. По одному предварительному запуску и пять измерений каждого варианта/режима. Каждый запуск — новый процесс, порядок вариантов чередуется; выбросы не удалены.

Команда: `run <deck> --speed virtual --guest-clock --no-wall-clock --limit 200000000`, с `--stats` или без него, конфигурация `memoryWatchpointBatching=true`.

| Режим | Вариант | Wall процесса, с | CPU процесса, с | Гостевой CTIME, с | Гостевой DMIPS |
|---|---|---:|---:|---:|---:|
| Stats | База | 8.302 | 8.172 | 6.20 | 9.180 |
| Stats | Кандидат | 8.576 | 8.156 | 6.60 | 8.624 |
| Без stats | База | 7.228 | 7.281 | 5.40 | 10.540 |
| Без stats | Кандидат | 7.121 | 7.172 | 5.48 | 10.386 |

Медианы CPU и попарные результаты:

| Режим | Снижение медианы CPU | Медиана попарного выигрыша CPU | Выигранных пар | Порог >2% |
|---|---:|---:|---:|---|
| Stats | 0.19% | −0.78% | 2 из 5 | Не пройден |
| Без stats | 1.50% | 1.72% | 3 из 5 | Не пройден |

Со stats медиана wall time стала хуже на 3.30%; без stats — лучше на 1.49%. Рост гостевого DMIPS также не получен. В virtual CTIME отражает elapsed time тела, тогда как CPU измеряет процессорное время всего процесса; это разные границы и метрики.

Разброс заметен, статистическая значимость столь малых различий не установлена. Результаты позволяют отклонить кандидата по заданному критерию; они не устанавливают точное предельное быстродействие эмулятора. После непрохождения порога другие изменения кода в этой итерации не пробовались.

## Проверка и восстановление

- 24 A/B-запуска, включая предварительные, прошли успешно: 18 числовых, 4 строковых контрольных значения, `BAD CONTROL VALUES=0`.
- Две sampling-трассы и два JIT-запуска также подтвердили контрольные значения.
- База и кандидат без гостевых часов на 5000 итераций совпали по полному finalState, памяти SHA-256, completed instructions, model cycles и ticks.
- В конце блока на кандидате выполнены существующие CoreMemoryLayoutTests: **7 успешно, 0 ошибок**. Проверены адреса всех банков, размеры 8/24/32768, нулевая память, выход за границы и `uint.MaxValue`, точный тип и текст исключений. Сборка без ошибок и предупреждений.
- После отклонения восстановлен CoreMemory из HEAD и пересобран CLI. DLL процессора побайтово совпадает со свежей базой: SHA-256 `7B9DE4098FFDDE2606271AF92F9AEBA9CDCEE9485A3558B99C10910FFD4DF40A`.
- Полный набор тестов заново не запускался: итоговый код приложения идентичен базе, ранее проверенной полным набором из 3360 успешных тестов и 395 пропусков. Это предыдущая полная проверка, а не новый полный прогон.
- Статья, изображения, публичные API и архитектура не редактировались. В Git сохраняется только этот отчёт.

Локальные игнорируемые материалы: `tests-run/next-profile-20261015/`. Внутри — commit.txt, dotnet-info.txt, отдельные комплекты `baseline/` и `candidate/`, SHA-256 DLL, `trial.json`, `no-stats.json`, сводки и попарные разницы, журналы всех запусков, обе `.nettrace`/Speedscope-трассы и `*-jit.asm`, verification.json, журналы сборок и memory-tests.log. SHA-256 кандидата: `4466557320E2E1F29046CABE7AE1D6E514EB24B77D205B0910F5450E7533A8BC`.

Локальные команды при сохранённых бинарниках и временных скриптах:

```powershell
& ./tests-run/next-profile-benchmark.ps1 -Variants @('baseline','candidate') -ResultName trial -Rounds 5 -Sizes @(100000) -Modes @('stats')
& ./tests-run/next-profile-benchmark.ps1 -Variants @('baseline','candidate') -ResultName no-stats -Rounds 5 -Sizes @(100000) -Modes @('nostats')
& ./tests-run/next-profile-verify.ps1
```

Для новой машины нужно отдельно собрать базу `414ce8d` и описанный вариант CoreMemory, сохранив комплекты DLL между сборками. Размер deck меняется только во временной копии: `DATA NUMBER/5000/` → `DATA NUMBER/100000/`. Сбор трассы: `dotnet-trace collect --profile dotnet-sampled-thread-time,dotnet-common --output <trace.nettrace> --show-child-io -- dotnet <variant>/besm6.dll run <deck> --config <config> --speed virtual --guest-clock --stats --no-wall-clock --limit 200000000`.
