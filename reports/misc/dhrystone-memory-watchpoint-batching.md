# Быстрые блоки с memory watchpoints: настройка и проверка

Дата: 15 октября 2026. Изменения поверх `7df33e4`, без изменения графа сборок, контрактов исполнения и владения состоянием.

## Включение

Настройка JSON **`memoryWatchpointBatching`**, тип bool, по умолчанию **false**. Пример [конфигурации](../../examples/memory-watchpoint-batching.json):

```json
{ "memoryWatchpointBatching": true }
```

```powershell
dotnet src/Besm6.Cli/bin/Release/net8.0/besm6.dll run examples/dhrystone-forex.dub --config examples/memory-watchpoint-batching.json --speed virtual --guest-clock --stats --no-wall-clock --limit 200000000
```

Настройка применяется фабрикой и к новой, и к переданной машине и сохраняется при Reset/LoadScript. Она разрешает уже существующий специализированный цикл с активным memory watchpoint на plain CoreMemory. Сам watchpoint остаётся активным. Fetch watchpoints, наблюдатели, нестандартная память, подготовленная команда и аппаратная модель не получают послаблений.

## Что изменено

- [Processor.CanExecuteUnobservedBlock](../../src/Besm6.Processor/Cpu/Processor.cs#L283): opt-in допуск при memory watchpoint; остальные ограничения сохранены. Публичные интерфейсы процессора и read-only State не менялись.
- [InstructionExecutor.ExecuteUnobservedBlock](../../src/Besm6.Processor/Execution/InstructionExecutor.cs#L194): `DebugWatchAbortException` перехватывается вне горячего generic-цикла. Управление возвращается runtime, чтобы события на текущем tick доставлялись до команды продолжения.
- При watch abort сохранено существующее поведение Step: функциональный счётчик/тики продвигаются, opcode accounting остаётся незавершённым; регистры кадра и память после запрещённого эффекта не публикуются. Частичные эффекты стековых команд, выполненные до watchpoint, сохраняются.
- У generic-цикла снят `AggressiveOptimization`. Этот атрибут обходит tiered compilation и исключает dynamic PGO; теперь JIT может оптимизировать горячие реализации ролей состояния/учёта. [Документация Microsoft](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.compilerservices.methodimploptions?view=net-8.0). Другие методы не переписывались; арифметика и memory checks общие.

Первый промежуточный вариант с одним разрешением batching не дал выигрыша и не принят за результат оптимизации. Повторное измерение ниже выполнено после корректировки JIT-атрибута. Архитектурные роли не заменялись прямым доступом к публично изменяемому состоянию.

## A/B Dhrystone virtual без профилировщика

Одна Release-сборка net8.0, .NET runtime 8.0.26, Intel Core i5-4570TE (2 ядра / 4 логических процессора). Для каждого размера и настройки: один предварительный запуск и пять измерений; порядок OFF/ON чередовался. CLI запускается новым процессом; JIT не прогрет между процессами. Параметры: virtual, guest-clock, stats, no-wall-clock, limit 200000000. Приведены медианы.

| Итерации | Настройка | Полный wall time, с | CPU процесса, с | CTIME тела Dhrystone, с |
|---:|---|---:|---:|---:|
| 5000 | False | 3.285 | 3.359 | 0.620 |
| 5000 | True | 2.695 | 2.734 | 0.420 |
| 50000 | False | 10.156 | 9.750 | 7.040 |
| 50000 | True | 5.578 | 5.484 | 3.280 |

- **5000 итераций:** полный запуск быстрее в **1.22 раза** (−18.0% времени); CPU — в **1.23 раза**; тело Dhrystone по CTIME — в **1.48 раза**.
- **50000 итераций:** полный запуск быстрее в **1.82 раза** (−45.1% времени); CPU — в **1.78 раза**; тело Dhrystone по CTIME — в **2.15 раза**.

Числа относятся к этому хосту и заданию; значительная часть короткого запуска — компиляция/инициализация, поэтому ускорение тела не равно ускорению CLI. Все исходные значения, включая предварительные запуски, находятся в `timing.json`.

## Повторный sampling-профиль

Снято по одной дополнительной трассе OFF/ON на 50000 итераций с `dotnet-sampled-thread-time,dotnet-common`. Время профилируемых запусков не использовалось для расчёта ускорения. Проценты — собственные выборки основного потока, не аппаратные проценты CPU; inlining влияет на атрибуцию.

| Метод / категория | OFF, % own | ON, % own |
|---|---:|---:|
| `InstructionExecutor.ExecuteFetchedInstruction` | 37.56 | 0.00 |
| `InstructionExecutor.Execute` | 26.25 | 0.00 |
| `ExecutionLoop.RunCore` | 10.58 | 0.31 |
| `InstructionExecutor.ExecuteUnobservedBlock` | 1.08 | 72.71 |

Изменение долей отражает перенос работы в существующий специализированный цикл. Оно не означает устранение fetch/dispatch/finalize: вычислительная семантика осталась общей. Доказательство ускорения — unprofiled A/B выше, а профиль подтверждает выбор пути.

## Проверка корректности

- Итоговая полная проверка: **3355 пройдено, 0 ошибок, 395 прежних пропусков**; сборка Release без ошибок и предупреждений.
- Новые проверки: JSON/default/reset, обе половины команды, load/store watchpoints, cache on/off, accounting on/off, попадание и промах, частичные эффекты STX/XTS, pending C/ApplyC, продолжение и события на точном tick, завершённые opcode-счётчики.
- Расширены существующие проверки самомодификации и установки watchpoint событием планировщика. Сохранены проверки контрактов сборок, памяти, диагностики и подготовленного исполнения.
- Dhrystone с выключенными гостевыми часами: OFF/ON совпадают по всем финальным регистрам, памяти SHA-256, completedInstructions, modelCycles и clockTicks. Это проверяется сравнением JSON, а не только печатаемых контролей.
- Режим original с настройкой ON: контрольные значения корректны, CTIME **4.36 с**, как до оптимизации; статистическая модель времени и её hooks не переключены на быстрый путь.
- Во всех 24 запусках основной A/B-серии, трёх проверочных запусках и двух sampling-прогонах проходят 18 числовых и 4 строковых контроля. В virtual с часами значения таймеров и содержащие их слова памяти закономерно зависят от скорости.

## Отдельное сравнение `--stats` ON/OFF после оптимизации

Измерено отдельно 15 октября 2026: `memoryWatchpointBatching=true` в обеих группах, одна и та же Release-сборка, `virtual --guest-clock --no-wall-clock --limit 200000000`. Единственное различие CLI — наличие `--stats`. По одному предварительному запуску и пять измерений на каждый вариант и размер; порядок размеров и ON/OFF чередовался. Профилировщик не подключался. Ниже медианы, предварительные запуски исключены.

| Итерации | --stats | Полный wall time, с | CPU процесса, с | CTIME тела, с | Гостевой DMIPS |
|---:|---|---:|---:|---:|---:|
| 5000 | False | 2.906 | 2.531 | 0.340 | 8.369882 |
| 5000 | True | 2.257 | 2.391 | 0.320 | 8.892999 |
| 50000 | False | 5.481 | 5.297 | 3.840 | 7.410833 |
| 50000 | True | 6.402 | 5.984 | 4.560 | 6.240701 |

- 5000 итераций: изменение с `--stats` относительно варианта без него: **-22.3% wall time**, **-5.6% CPU time**; медиана DMIPS меняется с **8.369882** до **8.892999**. Отрицательный процент означает уменьшение времени.
- 50000 итераций: изменение с `--stats` относительно варианта без него: **16.8% wall time**, **13.0% CPU time**; медиана DMIPS меняется с **7.410833** до **6.240701**. Отрицательный процент означает уменьшение времени.

Отдельные короткие пары могут давать более высокий рейтинг со статистикой. Пример измеренной пары №2 на 5000 итераций: без stats — CTIME 0.34 с, 8.369882 DMIPS, CPU процесса 2.359375 с; со stats — CTIME 0.32 с, 8.892999 DMIPS, CPU процесса 2.390625 с. Разница CTIME — один шаг гостевых часов 20 мс; CPU всего процесса при этом не уменьшился. Это не доказательство ускорения от статистики. Сама формула DMIPS не содержит поправки на `--stats`.

В медиане короткой серии преимущество со stats действительно наблюдается, в том числе по CPU процесса. На длинном задании оно меняется на замедление. Поэтому нельзя объяснять все различия только накладными расходами счётчиков или только округлением часов: меняются специализация JIT, startup и фоновые задержки. Эта серия устанавливает направление и величину эффекта на данном хосте, но не выделяет точную причину различий машинного кода.

По коду `--stats` в virtual создаёт сессию opcode accounting: в цикле выполняются Begin/Complete и накопление счётчиков. Без stats используется специализация UncountedBlockAccounting. После выполнения со stats дополнительно вычисляется SHA-256 памяти и сериализуется отчёт; эта завершающая работа входит в wall/CPU процесса, но не в CTIME тела. JIT специализирует два варианта независимо; конкретная разница машинного кода в этой проверке не исследовалась.

Результат относится к медианам серии на данном хосте; кратковременная нагрузка и дискретность гостевых часов дают разброс отдельных значений. Все 24 запуска подтвердили 18 числовых и 4 строковых контроля; без stats строка Execution stats отсутствует, со stats присутствует. Исходники не менялись, бинарные хеши сохранены. Сырые значения и stdout — `tests-run/stats-ab-batching-20261015/`; сценарий — `tests-run/stats-ab-batching.ps1`. Новых сборок или полных тестовых прогонов для сравнения CLI-флага не потребовалось.
