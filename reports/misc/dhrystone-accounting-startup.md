# Dhrystone virtual: дополнительные проверки accounting и запуска

Продолжение [анализа горячего цикла](dhrystone-loop-optimization.md). Рабочая база — `d2bd98d`, уже содержит `NoInlining`. Настройка memory watchpoint batching включена. Первые два варианта accounting отклонены. **Оставлен третий вариант: отдельное завершение успешно декодированной команды для штатной сессии.** Добавлены четыре метода проверки контракта учёта команд, пять тестовых случаев.

## Два варианта accounting

Первый вариант сохранял стоимость в `Begin` вместо opcode. `Complete` проверял наличие pending, снимал его и прибавлял готовую стоимость; нулевая стоимость оставалась допустимой незавершённой командой. Таблица стоимости принадлежит сессии и не меняется после её создания, поэтому стоимость можно вычислить заранее без нового публичного API. Это упрощало `Complete`, но переносило lookup в `Begin`.

Второй вариант оставлял `ProcessorInstructionAccounting` неизменным. Тип штатной сессии выбирался один раз на блок и передавался в приватную struct-специализацию общего generic-цикла. Сохранялся интерфейсный путь для остальных реализаций и декораторов. Цель — убрать повторные проверки типа сессии из встроенных `Begin/Complete/AtCycleLimit`, не копируя алгоритмы pending и cycle limit. Специализация в итоговый код не включена.

SDK 10.0.202, runtime 8.0.26, Release net8.0, тот же Intel Core i5-4570TE. Каждый замер — новый процесс; предварительные запуски исключены, порядок вариантов меняется. Параметры: `--speed virtual --guest-clock --no-wall-clock --limit 200000000`, с `--stats` или без него. Профилировщика в A/B нет, выбросы не удалялись. Все значения в таблицах — медианы.

### Специализация штатной сессии

По одному предварительному и три измерения каждого варианта, 50000 итераций, stats включён.

| Вариант | Wall процесса, с | CPU процесса, с | CTIME тела, с |
|---|---:|---:|---:|
| База NoInlining | 4.721 | 4.828 | 3.08 |
| Специализация сессии | 4.867 | 4.953 | 2.98 |

Медиана CPU хуже на 2.6%. Кандидат проиграл две пары из трёх, поэтому в большую серию и в итоговый код не включён. Меньшее показание гостевого CTIME не компенсирует отсутствие выигрыша полного CPU процесса: это разные метрики.

Для обоих вариантов дополнительно снято Tier1 disassembly. Размер generic counted-цикла в этих диагностических запусках: 17551 байт с сохранённой стоимостью, 16272 байта со специализацией. Сам размер не доказывает ускорение. Стоимость ветвей не измерялась аппаратными счётчиками, поэтому влияние instruction cache или branch prediction не объявляется причиной результатов.

## Принятый вариант: завершение декодированной команды

В [InstructionExecutor](../../src/Besm6.Processor/Execution/InstructionExecutor.cs#L199) штатная sealed-сессия выбирается один раз на блок. Приватный [ProcessorBlockAccounting](../../src/Besm6.Processor/Execution/ProcessorBlockAccounting.cs) вызывает обычный `Begin` и внутренний `CompleteDecodedInstruction`; остальные реализации и декораторы используют прежний интерфейсный путь. Цикл fetch/dispatch/finalize остаётся общим, новые публичные API и зависимости сборок не появляются.

У [ProcessorInstructionAccounting](../../src/Besm6.Processor/Execution/ProcessorInstructionAccounting.cs#L45) успешное завершение декодированной команды читает стоимость из таблицы и вызывает общий `Retire`. Общий `Complete` сохраняет проверки отсутствия pending и неизвестного opcode. Сброс pending и накопление счётчиков не дублируются.

Предусловия отдельного пути:

- `InstructionCodec.DecodeHalf` выдаёт opcode в диапазоне таблицы из 256 элементов;
- перед исполнением той же команды вызывается `Begin`;
- unobserved block ограничен обычной памятью и запрещает наблюдателей; до callback-способного экстракода он возвращается;
- исключение или memory watchpoint выходит до вызова завершения; pending остаётся установленным;
- лимит циклов проверяется после успешного retirement, как раньше, события доставляются на прежних границах блоков.

Проверки отсутствия pending и fallback-стоимости удалены только из этого внутреннего успешного пути. Проверка границ массива остаётся. Публичный `Complete`, `CancelPending`, завершение сессии и внешние реализации не получают новых предусловий.

### Две серии по 100000 итераций

Увеличенный размер даёт около 142 млн команд и укладывается в прежний `--limit 200000000`. В каждой серии: один предварительный и пять измерений на вариант/режим. Оба варианта — отдельные замороженные комплекты DLL; время профилировщика не входит в таблицу.

| Серия | Режим | Вариант | Wall процесса, с | CPU процесса, с | CTIME тела, с |
|---|---|---|---:|---:|---:|
| Первая | Stats | База NoInlining | 8.194 | 8.344 | 6.28 |
| Первая | Stats | Отдельное завершение | 8.184 | 8.234 | 6.44 |
| Повторная | Stats | База NoInlining | 8.254 | 8.328 | 6.36 |
| Повторная | Stats | Отдельное завершение | 7.660 | 7.672 | 5.96 |
| Повторная | Без stats | База NoInlining | 7.168 | 7.250 | 5.42 |
| Повторная | Без stats | Отдельное завершение | 7.250 | 7.188 | 5.76 |

CPU counted-запуска: −1.3% в первой серии и −7.9% в повторной. Кандидат выиграл четыре пары из пяти в первой серии и все пять в повторной. Медиана относительной разницы внутри пар — −4.9% и −8.3% соответственно. Повторный wall time со stats снизился на 7.2%; в первой серии практически не изменился. Разброс не позволяет обещать фиксированное ускорение.

Без stats accounting не используется: медиана CPU −0.9%, wall +1.2%, медиана попарной разницы CPU равна нулю. Для этого режима ускорение не заявляется. Важное ограничение: CTIME тела — elapsed time гостевых часов virtual, а CPU — процессорное время всего процесса. Первое не подменяет второе.

Tier1 disassembly принятого варианта содержит обёртку на 326 байт и специализированный цикл на 15698 байт; в последнем нет вызовов `IProcessorInstructionAccounting`. Уменьшение числа проверок подтверждается кодом, его отдельная стоимость аппаратными счётчиками не измерялась.

## Где находятся затраты запуска

Проверка по появлению заголовка в stdout оказалась непригодной для определения начала тела Dhrystone; подробнее в предыдущем отчёте. Вместо неё отдельный временный .NET host измеряет публичные этапы создания и загрузки:

1. `Config.Load`;
2. `MachineFactory.ValidateRuntimeAssets`;
3. `MachineFactory.CreateMachine`;
4. `MachineFactory.CreateLoader` с уже проверенными assets;
5. `DubnaLoader.LoadScript`, включая подготовку задания и начальную загрузку MONSYS;
6. `DubnaLoader.RunLoaded`.

Host ссылается на сохранённые DLL принятого варианта NoInlining, не меняет их и не устанавливает per-instruction hooks. Результаты гостевого вывода направляются в `StringBuilder`; контролируются 18 числовых и 4 строковых значения. Точные границы CTIME не инструментируются. Пять новых процессов после предварительного запуска, 5000 итераций, virtual/guest-clock, без stats.

| Этап | Wall, мс | CPU, мс |
|---|---:|---:|
| Конфигурация | 70.1 | 78.1 |
| Проверка assets | 64.4 | 62.5 |
| Создание машины | 15.2 | 15.6 |
| Создание загрузчика | 4.9 | 0.0 |
| LoadScript и начальная загрузка MONSYS | 52.0 | 62.5 |
| RunLoaded | 1449.7 | 1531.3 |

CPU процесса здесь имеет шаг около 15.6 мс: значение 0.0 не означает бесплатную операцию. Это медианы отдельных этапов, их сумма не является медианой полного запуска. Host начинает измерение в `Main`: запуск CLR, загрузка части зависимостей и JIT самого `Main` вне этих границ. Кроме того, вывод в память отличается от CLI. Эти данные используются для локализации затрат, а не как новый бенчмарк ускорения CLI.

На стороне host подготовка занимает около 0.2 с; гораздо больший интервал остаётся в `RunLoaded`. В нём работают гостевой MONSYS, FOREX, загрузка библиотек, сам Dhrystone и контрольный вывод. **Точная отдельная стоимость компилятора всё ещё не измерена.** Из этих данных нельзя заключать, что весь `RunLoaded` — компиляция, или вычитать из CPU показание гостевого wall clock.

Проверка конфигурации и assets — возможные небольшие цели для дальнейшего анализа, но они не объясняют основной вес цикла. Двойное чтение deck в `RunScript` не объявляется горячим участком: оно не показано как заметная доля профиля. Для существенного сокращения повторных коротких запусков потенциально полезно повторное использование готового гостевого задания; это отдельная задача с проверкой ключа кэша, версий библиотек и состояния машины.

## Контракты и итоговая проверка

Новые [InstructionAccountingContractTests](../../tests/Besm6.Processor.Tests/InstructionAccountingContractTests.cs) проверяют:

- нулевую стоимость как настоящий pending и однократное завершение;
- отмену и замену pending-команды без ложного retirement;
- момент достижения cycle limit и владение копией таблицы стоимости;
- завершение сессии с pending без добавления команды;
- неизвестные opcode и накопление стоимости `int.MaxValue` в long-счётчике;
- декоратор сессии, его вызовы Begin/Complete, точный выход на cycle limit и продолжение до STOP.

Существующие runtime-тесты дополнительно покрывают исключения, watchpoints с частичными эффектами, незавершённый accounting, точные ticks, границы событий и самомодификацию.

До третьего варианта, на восстановленной базе, Release-сборка всей solution прошла без ошибок и предупреждений, четыре новых случая прошли. В том полном прогоне было 3358 успешных тестов, 395 пропусков и одна ошибка существующего `LightweightLoop_DoesNotAllocatePerInstruction`: измерено 3648 байт вместо нуля. Повторён весь проект Processor.Tests на тех же бинарниках: 1626 успешно, 0 ошибок. Причина единичного сбоя не установлена; порог и код аллокационного теста не менялись. После добавлена ещё одна DataRow для явного сравнения штатной и декорированной сессии.

Итоговая проверка третьего варианта: новый полный прогон solution — **3360 успешно, 0 ошибок, 395 прежних пропусков**; Release-сборка без ошибок и предупреждений. Все пять новых случаев прошли, включая штатную и декорированную сессии. В этом прогоне аллокационный тест также прошёл. Без гостевых часов база и принятый вариант совпали по полному `finalState`, памяти SHA-256, completed instructions, model cycles и ticks. Dhrystone original на 5000 итераций подтвердил контроли и прежние 4.36 с гостевого времени.

Измеренная DLL процессора и DLL итоговой сборки совпадают: SHA-256 `0022264DECE0029B3491AAD4BEE69D499180E0D257FEDE7AE79D66CE01C11DDD`.

104 A/B-запуска этого продолжения (включая предварительные: 68 первых двух вариантов, 36 третьего), шесть запусков диагностического host и три JIT-запуска завершились успешно. Числовые и строковые контроли пройдены; сырой вывод сохранён. Неудачная промежуточная сборка тестов была исправлена до запуска набора: псевдоним класса Processor конфликтовал с одноимённым namespace.

Артефакты в игнорируемом `tests-run/`: `jit-dispatch-20261015/pending-cost-{screen,confirm}.json`, `processor-account-screen.json`, `decoded-account-{screen,confirm}.json`, `decoded-verification.json`, соответствующие журналы/бинарники/хэши; `loop-profile-20261015/{pending-cost,processor-account,decoded-account}-jit.asm`, `*-100000-stats.nettrace`, Speedscope и сводки, `startup-phases-0..5.json`, `startup-phases-summary.json`, журналы `accounting-final-*`, `accounting-processor-recheck.log`, `decoded-final-*` и `decoded-original-verification.log`. Принятые границы архитектуры и публичные API сохранены. Ранее принятый `NoInlining` остаётся в коде. Успешный учёт команды упрощён только в закрытом обычном пути; общий контракт и его проверки сохранены.
