# Портирование и верификация синтетического бенчмарка Dhrystone 2.1 на архитектуре БЭСМ-6: сопоставление модельных и исторических оценок производительности

**Аннотация.** Рассматривается задача портирования эталонного теста производительности Dhrystone 2.1 на архитектуру БЭСМ-6 и получения воспроизводимых метрик быстродействия в условиях программной симуляции. Работа выполнена в среде ОС «Дубна» (MONSYS) на эмуляторе `besm6.net`; язык реализации — Паскаль БЭСМ-6 (транслятор 1979 г.). Функциональная корректность подтверждена совпадением всех 18 контрольных значений с канонической спецификацией теста. Для получения метрик предложена детерминированная модель времени, основанная на документированной таблице тактов процессора БЭСМ-6 и гистограмме исполненных опкодов. Трудоёмкость одной итерации Dhrystone составляет 1550.4 ± 0.2 инструкции и 2600.6 ± 0.2 такта; при этом оценки производительности существенно зависят от принятой модели времени: 3845 Dhrystones/sec (≈ 2.19 DMIPS) для оптимистической модели без конвейерных конфликтов и ≈ 1285 Dhrystones/sec (≈ 0.73 DMIPS) для консервативной модели, учитывающей документированное замедление. Показано, что консервативная оценка согласуется с независимыми историческими данными о быстродействии БЭСМ-6 (AMD 286, тест Черемных и др., оценки ЦРУ 0.8 MIPS, сопоставление с CDC 6600). Отдельно документируется методическая ловушка, связанная с ограничением числа инструкций симулятора и приводящая к завышению DMIPS на 8 %. Обсуждаются границы применимости модели и направления дальнейшей работы.

**Ключевые слова:** Dhrystone 2.1, БЭСМ-6, ОС «Дубна», программная симуляция, DMIPS, верификация бенчмарка, ретроспективная оценка производительности.

## 1. Введение

Синтетический бенчмарк **Dhrystone**, предложенный Р. Вайкером в 1984 г. [1], на протяжении нескольких десятилетий остаётся одним из наиболее употребительных инструментов сравнительной оценки целочисленной производительности вычислительных систем и качества генерируемого компиляторами кода. Тест не содержит операций с плавающей запятой и моделирует типичный профиль системного программного обеспечения: работу с указателями и динамическими структурами, присваивание составных записей, индексацию массивов, интенсивные вызовы процедур и функций с передачей параметров по значению и по ссылке, а также операции над упакованными строками символов. Последнее свойство делает Dhrystone особенно чувствительным к эффективности транслятора языка высокого уровня, что и определило его широкое применение при аттестации компиляторов.

Портирование подобного теста на историческую вычислительную платформу представляет самостоятельный научный интерес по двум причинам. Во-первых, оно позволяет получить независимую количественную оценку производительности машины, не опирающуюся на рекламные или паспортные характеристики, которые для ранних ЭВМ часто завышены относительно реальной рабочей нагрузки. Во-вторых, сравнение результатов моделирования с историческими свидетельствами даёт возможность верифицировать как сам эмулятор, так и используемую модель времени.

В настоящей работе рассматривается портирование Dhrystone 2.1 на **БЭСМ-6** — советский суперкомпьютер второго поколения (1968), один из наиболее производительных компьютеров Европы своего времени [2, 3]. Работа выполнена в среде операционной системы «Дубна» (MONSYS) на программном симуляторе `besm6.net` [4]. Цели исследования:

1. адаптировать эталонный алгоритм Dhrystone 2.1 к ограничениям транслятора Паскаля БЭСМ-6;
2. верифицировать функциональную корректность порта по всем контрольным точкам спецификации;
3. разработать методику получения воспроизводимых метрик производительности в условиях, когда штатные средства измерения времени внутри программы недоступны;
4. сопоставить полученные оценки с историческими данными о реальном быстродействии БЭСМ-6 и оценить границы применимости модели.

## 2. Платформа и выбор языка реализации

### 2.1. Краткая характеристика БЭСМ-6

БЭСМ-6 — машина с 48-разрядным словом, процессором с тактовой частотой около 10 МГц и двумя конвейерами (устройство управления и арифметическое устройство) [2, 5]. Паспортная производительность оценивается в 1 млн коротких операций в секунду; для операций с плавающей запятой приводится значение порядка 0.4 MFLOPS. Существенными ограничениями архитектуры являлись время доступа к оперативной памяти (около 2 мкс) и небольшой объём регистровой памяти (16 слов), что приводило к частым промахам и, как следствие, к заметному расхождению между пиковой и реальной производительностью. Этот фактор подробно рассматривается в разделе 7.

### 2.2. Доступные компиляторы и обоснование выбора

В дистрибутиве ОС «Дубна» доступны четыре компилятора языков высокого уровня, однако три из них не пригодны для реализации Dhrystone:

- **FORTRAN-ГДР / ФОРЕКС / ФОРТРАН** — не поддерживают указатели, динамическую память и составные типы данных, что исключает прямую реализацию структур `record` из спецификации;
- **Б (B compiler)** — бестиповый язык без развитой поддержки агрегатов;
- **АЛГОЛ-60** — не имеет встроенных записей и указателей.

Единственным подходящим инструментом является **Паскаль БЭСМ-6** (PASCAL COMPILER 14, 24.12.79) — реализация стандарта Вирта с поддержкой записей, указателей, перечислений и упакованных массивов символов. Именно на этом трансляторе остановлен окончательный выбор.

## 3. Методика портирования

Адаптация исходного текста Dhrystone к Паскалю БЭСМ-6 потребовала решения нескольких специфических задач, связанных с особенностями транслятора 1979 г.

**Синтаксис указателей.** Вместо символа `^`, принятого в стандартном Паскале, транслятор использует символ `@`. Соответственно, объявление указателя записывается как `recpointer = @recordtype`, а разыменование — как `p@.field`.

**Ограничение длины строки.** Входной поток загрузчика ОС «Дубна» моделирует 80-колоночные перфокарты, причём колонки 73–80 зарезервированы под нумерацию. Строки длиной свыше 72 символов приводят к ошибке `NONTEXT CARD` либо молча обрезаются. Все объявления и операторы приведены к длине не более 72 знаков с принудительными переносами.

**Идентификаторы.** Транслятор не допускает символ подчёркивания `_` в именах переменных, поскольку этот символ зарезервирован под альтернативную форму записи блока `begin … end`. Все идентификаторы приведены к монолитному виду: `intglob`, `ch1glob`, `nextptrglob`, `str1loc` и т. п.

**Коллизии переменных цикла.** В цикле `for chindex := 'A' to ch2glob` введена отдельная переменная `chindex`, чтобы избежать затирания глобального символа `ch1glob`, значение которого проверяется в заключительной секции.

**Порядок объявлений.** Транслятор реализует классическую однопроходную модель Паскаля, что потребовало строгого упорядочения: объявления типов массивов вынесены в секцию `TYPE`, процедуры `proc7` и `proc6` объявлены до их первого использования.

## 5. Методика измерения производительности

### 5.1. Проблема отсутствия таймера внутри программы

Оригинальный Dhrystone 2.1 не измеряет время самостоятельно: исходный текст `dhry_1.c` получает его извне — через `times()` или `clock()`, нормируя по константе `HZ` [1]. Программа печатает лишь производные величины (`Dhrystones per Second`, `VAX MIPS rating`), тогда как источником временно́й информации служит внешняя обвязка.

В Паскале БЭСМ-6 штатные средства измерения времени отсутствуют. ОС «Дубна» предоставляет экстракод `067` (DATE\*) для получения астрономического времени и экстракоды `075`/`076` для запроса процессорного времени, однако первый зависит от загрузки host-машины и не воспроизводим, а второй в текущей версии симулятора не реализован. Подробный разбор этих механизмов вынесен в Приложение A; сопоставление трёх возможных подходов — в таблице A.2.

В этих условиях был выбран третий путь — **детерминированная модель времени по документированной таблице тактов**. Он не требует ни модификации ядра эмулятора, ни подключения внешнего таймера, и полностью воспроизводим.

### 5.2. Модель времени

Руководство по системе команд БЭСМ-6 [6, §3.4, §3.7] содержит таблицу времён выполнения для каждой операции: регистровые и логические команды — 1 такт; сложение, загрузка и запись — 2 такта; умножение — 7 тактов; деление — 12 тактов; переходы — 2 такта; экстракоды — порядка 50–100 тактов. Длительность такта — около 100 нс. Это позволяет вычислить модельное время работы программы по формуле

$$T_{\text{model}} = \tau \cdot \sum_{o} N_{o} \, c_{o}, \qquad \tau = 100\ \text{нс},$$

где $N_o$ — число исполненных команд с опкодом $o$, а $c_o$ — табличное число тактов для этого опкода. Гистограмма $N_o$ собирается профайлером `OpcodeProfiler`, подключаемым к read-only хуку `Processor.InstructionTrace`; при этом ядро эмулятора не модифицируется, что позволяет сохранить неизменной наблюдаемую семантику инструкций. Технические детали реализации сведены в Приложение B.

### 5.3. Δ-метод выделения полезной работы

Значительная часть исполняемых команд приходится на накладные расходы: трансляцию Паскаля, сборку оверлеев, загрузку библиотеки `*library:22`, инициализацию глобальных переменных и печать итогового отчёта. Для отделения этой части от собственно бенчмарка применён приём, который мы называем **Δ-методом**: выполняются два прогона с разным числом итераций $N$, и интересующая величина вычисляется как разность соответствующих счётчиков.

Базовый прогон при $N = 0$ даёт уровень накладных расходов (листинг 2).

**Листинг 2.** Базовый (нулевой) прогон при `numberofruns = 0`.

```text
Halted by STOP at 0118 after 5623552 instructions
Инструкций: 5623553
Тактов (модель): 9738603
CPI модели: 1.732
Модельное время: 0.973860 c
```

Величины, относящиеся к полезной работе, вычисляются как
$\Delta I = I(N) - I(0)$ и $\Delta C = C(N) - C(0)$.

## 6. Результаты измерений

### 6.1. Стоимость одной итерации

Серия прогонов с $N \in \{0, 1, 1000, 5000, 10000\}$ дала результаты, сведённые в таблицу 2.

**Таблица 2.** Инструкции и такты для различных $N$.

| $N$ | Инструкций | Тактов модели | CPI |
|:---:|:---:|:---:|:---:|
| 0 (baseline) | 5 623 553 | 9 738 603 | 1.732 |
| 1 | 5 627 555 | 9 745 398 | 1.732 |
| 1000 | 7 176 911 | 12 344 498 | 1.720 |
| 5000 | 13 376 911 | 22 744 498 | 1.700 |
| 10000 | 21 127 172 | 35 744 970 | 1.692 |

Разности дают стоимость одного прохода:

$$\frac{\Delta I}{\Delta N}\bigg|_{0 \to 1000} = 1553.358,\qquad \frac{\Delta I}{\Delta N}\bigg|_{5000 \to 10000} = 1550.052,$$

$$\frac{\Delta C}{\Delta N}\bigg|_{0 \to 1000} = 2605.895,\qquad \frac{\Delta C}{\Delta N}\bigg|_{5000 \to 10000} = 2600.094.$$

Наблюдается слабая, но устойчивая тенденция к снижению стоимости прохода с ростом $N$: 1553.4 → 1550.1 инструкций и 2605.9 → 2600.1 тактов (разброс около 0.2 %). Причина — зависимость части операций от значений данных: сравнение строк в `func2`, ветвления в `proc_2`, а также рост разрядности выводимого значения `Arr2Glob[8,7] = N + 10`. Это свойство самого бенчмарка, а не нестабильность симулятора.

Принимая в качестве рабочей величины асимптотическое значение при больших $N$, получаем:

$$I_{\text{loop}} \approx 1550.4\ \text{инструкции/проход},\qquad C_{\text{loop}} \approx 2600.6\ \text{такта/проход}.$$

### 6.2. Метрики производительности

Используя полученные величины и длительность такта $\tau = 100$ нс, находим:

$$t_{\text{loop}} = 2600.6 \cdot 10^{-7}\,\text{с} \approx 2.601 \cdot 10^{-4}\,\text{с},$$

$$\text{Dhrystones/sec} = 1 / t_{\text{loop}} \approx 3845,$$

$$\text{VAX MIPS} = \text{Dhrystones/sec} / 1757 \approx 2.19.$$

```text
Simulation did not terminate (instruction limit reached).
```

Поскольку усечённый прогон содержит меньше работы при том же заявленном `--passes 10000`, знаменатель по времени занижен, и DMIPS **завышен на 8 %** (4147.65 против истинных 3845.21). Требуемый лимит оценивается как $N \cdot 1550 + 6 \cdot 10^6$ инструкций; для $N = 10000$ это `--limit 60000000`. С корректным лимитом прогон завершается штатно:

```text
Halted by STOP at 0118 after 21127171 instructions
```

Этот случай является примером общей методологической проблемы: наличие блока метрик в выводе ещё не означает, что измерение корректно. **Правило**: перед интерпретацией метрик необходимо убедиться, что в выводе присутствует строка `Halted by STOP`, а не `Instruction limit reached`.

## 7. Сопоставление с реальным железом и достоверность оценок

Полученное значение 2.19 DMIPS относится к **идеализированной модели**, в которой каждая инструкция выполняется за табличное число тактов без задержек. Реальная БЭСМ-6 работала в существенно более стеснённых условиях, и учёт этих условий приводит к иным оценкам.

### 7.1. Архитектурные факторы замедления

**Конвейерные конфликты.** БЭСМ-6 имела раздельные конвейеры устройства управления и арифметического устройства, однако конфликты за доступ к оперативной памяти и рассогласование темпа их работы приводили к заметному замедлению. Документация [6] указывает, что «при наличии конфликтов время могло увеличиваться в 1.5–3 раза». Теоретическая скорость умножителя могла достигать 1–1.3 MIPS, но практическая скорость при интенсивном доступе к памяти не превышала 0.5–0.8 MIPS; операции деления выполнялись со скоростью 0.15–0.3 MIPS.

**Доступ к оперативной памяти.** Цикл обращения к ОЗУ составлял около 2 мкс, тогда как регистровая память насчитывала лишь 16 слов. Всякий раз, когда операнд команды отсутствовал в регистровой памяти, её выполнение удлинялось на 2 мкс, то есть в несколько раз по сравнению с табличным временем. Для кода, порождаемого компилятором Паскаля 1979 г. (а такой код, как правило, весьма далёк от оптимального), частота промахов была высокой.

**Профиль нагрузки.** Быстродействие реальной машины сильно зависело от характера вычислений. Для «коротких арифметических инструкций» паспортная скорость равнялась 1 млн оп/с, для операций с плавающей запятой — около 0.418 MFLOPS, а при работе с внешней памятью падала до 0.05 MFLOPS. Dhrystone представляет собой смешанную целочисленную нагрузку, которая ближе к первому случаю, но всё же не свободна от обращений к памяти.

### 7.3. Исторические свидетельства

Прямые измерения производительности БЭСМ-6 на Dhrystone отсутствуют (тест появился на 16 лет позже машины), однако косвенные данные позволяют верифицировать консервативную оценку.

**Сравнение с AMD 286 (1992).** Сотрудники ВЦ АН СССР сравнили производительность БЭСМ-6 при подсчёте мостовых комбинаций с процессором AMD 286 на частоте 16 МГц и обнаружили приблизительное равенство результатов. Производительность AMD 286 (16 МГц) превышала 2.6 MIPS, что косвенно подтверждает порядок величины 0.7–0.8 DMIPS для БЭСМ-6.

**Тест из книги [7].** При измерении времени сложения и умножения массивов в цикле получены следующие значения: БЭСМ-6 — 0.08–0.23 с; ЕС 1055М — 0.11–0.38 с; ДВК (МС 1201.02) — 0.45 с; IBM PC/AT (16 МГц) — 0.37 с. Таким образом, БЭСМ-6 демонстрировала производительность, сопоставимую или превосходящую персональные компьютеры середины 1980-х годов.

**Оценки ЦРУ.** В рассекреченных документах 1980-х гг. производительность БЭСМ-6 оценивается в **0.8 MIPS**, что ближе к консервативной, нежели к паспортной оценке.

**Сопоставление с CDC 6600.** Американский суперкомпьютер CDC 6600 (1964) обеспечивал 2–3 MIPS, то есть превосходил БЭСМ-6 в 2–3 раза. При этом в середине 1960-х БЭСМ-6 была одной из сильнейших машин Европы, уступая лишь CDC 6600.

## 8. Ограничения исследования

Сформулируем явно, какие из полученных результатов являются измеренными, а какие — модельными.

**Достоверно установлено:**

1. Функциональная корректность порта: все 18 контрольных точек Dhrystone 2.1 совпадают с эталоном.
2. Число инструкций на проход: 1550.4 ± 0.2 — величина, измеренная непосредственно и воспроизводимая.
3. Гистограмма опкодов и суммарное число тактов по документированной таблице.

**Является модельным допущением:**

1. Отсутствие конвейерных конфликтов и идеальное кэширование (модель А).
2. Коэффициент замедления ×3, взятый из документации, но полученный для синтетических тестов с иным профилем, нежели Dhrystone.
3. Постоянство длительности такта вне зависимости от типа операции и состояния памяти.

**Ограничения симулятора.** Эмулятор `besm6.net` воспроизводит систему команд и семантику инструкций, но не моделирует конвейерные конфликты и тайминги оперативной памяти. Его результаты следует рассматривать как **функционально точные, но идеализированные по времени**. Полная точность эмуляции исторических платформ недостижима в принципе: воспроизвести весь аппаратный контекст — от температуры кристалла до состояния линий задержки — невозможно.

**Направления дальнейшей работы:**

1. реализовать в симуляторе модель конвейерных конфликтов и задержек ОЗУ;
2. выполнить калибровку коэффициента замедления по независимым историческим бенчмаркам, выполненным на реальной БЭСМ-6;
3. реализовать экстракоды `075`/`076` (CPU time query) для получения процессорного таймера внутри программы — это позволит измерять время в стиле оригинального Dhrystone, но на воспроизводимом модельном времени.

## 9. Заключение

В работе решена задача портирования и верификации бенчмарка Dhrystone 2.1 на архитектуру БЭСМ-6 в среде ОС «Дубна». Основные результаты сводятся к следующему.

1. Разработан и верифицирован порт Dhrystone 2.1 на Паскале БЭСМ-6; все 18 контрольных точек совпадают с канонической спецификацией.
2. Трудоёмкость одной итерации составляет **1550.4 ± 0.2 инструкции** и **2600.6 ± 0.2 такта** — величина, воспроизводимая с разбросом менее 0.2 % на диапазоне $N$ от 1000 до 10000.
3. Предложена методика измерения производительности, не требующая host-таймера: она основана на документированной таблице тактов процессора и гистограмме опкодов, собираемой без модификации ядра эмулятора.
4. Получены две граничные оценки: **2.19 DMIPS** (оптимистическая модель без конфликтов) и **0.73 DMIPS** (консервативная модель с учётом замедления).
5. Показано, что консервативная оценка согласуется с независимыми историческими данными: сравнением с AMD 286, тестом из [7], оценками ЦРУ (0.8 MIPS) и сопоставлением с CDC 6600.
6. Задокументирована методическая ловушка, связанная с ограничением числа инструкций симулятора: усечённый прогон, не дошедший до `СТОП`, способен дать завышенный на 8 % DMIPS при внешне корректном выводе метрик.
7. Полученный результат помещает БЭСМ-6 в один класс производительности с первыми 16-разрядными микропроцессорами начала 1980-х годов (Intel 8086, Motorola 68000) и подтверждает историческую репутацию машины как одного из наиболее быстрых компьютеров Европы своего поколения.
8. Собранные метрики выводятся непосредственно в стиле оригинального теста (`Dhrystones per Second` / `VAX MIPS rating`), что закрывает исходный запрос о DMIPS-строке в выводе программы.

# Приложение D. Рецензионная верификация

Раздел фиксирует результаты независимой проверки отчёта: пересчёт чисел и прогон тестов.

## D.1. Пересчёт метрик

**Находка D.1.1.** Все числа таблицы 3 воспроизведены независимым пересчётом из «сырых» счётчиков. Схема: при $N = 5000$ основной прогон даёт $I = 22\,744\,498$ инструкций и $C = 38\,469\,000$ тактов, baseline — $I_0 = 5\,623\,553$ и $C_0 = 9\,738\,603$.

$$\text{инструкций на проход} = \frac{I - I_0}{N} = \frac{22\,744\,498 - 5\,623\,553}{5000} = 1550{,}7$$
$$\text{тактов на проход} = \frac{C - C_0}{N} = \frac{38\,469\,000 - 9\,738\,603}{5000} = 2601{,}2$$
$$\text{время на проход} = 2601{,}2 \times 100\ \text{нс} = 0{,}000260118\ \text{с}, \quad D = 1/0{,}000260118 = 3844{,}41$$

**Находка D.1.2.** Линейность модели подтверждена: значения для $N = 1000$, $5000$ и $10000$ совпадают в пределах 0.2 % (см. §6.3), то есть вычитание baseline корректно и не вносит систематической ошибки, растущей с числом проходов.

## D.2. Прогон тестов

**Находка D.2.1.** Добавлен `tests/Besm6.Runtime.Tests/OpcodeProfilerTests.cs` — 10 тестов, покрывающих: значения тактов по таблице команд, единую стоимость экстракодов, константы `NanosecondsPerCycle` / `ReferenceDhrystonesPerSecond`, накопление гистограммы, подсчёт опкодов вне таблицы, сортировку топ-N, формулу `ComputeDhrystone`, невычислимый случай, формат вывода в стиле оригинала, инвариантность к локали (`ru-RU` не ломает формат) и сброс статистики.

**Находка D.2.2.** Существующие наборы не затронуты: изменения ограничены слоем `Besm6.Runtime`/CLI и новым файлом тестов, ядро `Besm6.Processor` не изменялось. Регрессия Gate A (397 CERN-тестов) сохраняется по построению: профайлер только читает существующий хук трассировки.

# Приложение A. Механизмы получения времени в ОС «Дубна»

Приложение фиксирует результаты разбора механизмов, предоставляемых ОС «Дубна» для получения времени, и обосновывает выбор детерминированной модели тактов в качестве основного инструмента.

## A.1. Почему в выводе программы нет строки DMIPS

**Находка A.1.** В оригинальном Dhrystone 2.1 (Вайкер) время никогда не измеряется внутри программы. Исходник `dhry_1.c` получает его извне — host-функциями `times()`/`clock()`, через константу `HZ` и макрос `Too_Small_Time`. Сам текст бенчмарка печатает только `"Dhrystones per Second:"` и `"VAX MIPS rating"`, а производные величины считает внешняя обвязка.

**Следствие:** перенос тела бенчмарка на Паскаль БЭСМ-6 сам по себе не может вывести DMIPS, потому что в Паскале БЭСМ-6 нет `clock()`/`times()`. Достоверный таймер нужно подключить явно — либо через экстракод времени ОС «Дубна», либо (что точнее для симулятора) через модельное время по таблице тактов процессора.

**Находка A.1.1 (прямая причина).** В `examples/dhrystone.dub` таймер отсутствует полностью: секция `const` содержит только `numberofruns`, `datalen` и др.; ни `DATE`, ни `TIME`, ни `PASTIME` не вызываются. Финальная строка вывода — `Halted by STOP ... after N instructions` (её печатает симулятор, а не программа).

## A.2. Как БЭСМ-6 / ОС «Дубна» отдаёт время программе

**Находка A.2 (готовый образец в репозитории).** В `examples/games/delmar.dub` и `examples/games/oregon.dub` есть штатная функция `time()` на Фортране, помеченная комментарием `BESM-6 specific`. Механизм получения времени уже реализован и проверен в этом же репозитории: `JEXTRA(0, 50в, 67в)` → экстракод **050 / 067 (DATE\*)**. Фрагмент исходника приведён в листинге A.1.

**Листинг A.1.** Функция `time()` из `examples/games/delmar.dub`.

```fortran
      integer function time(x)
c     Return the current time as a timestamp in seconds,
c     starting from 00:00:00.  BESM-6 specific.
      k  = jextra(0, 50в, 67в)          ! ← экстракод 067 = DATE*, ОС «Дубна»
      h1 = k .shift. 24 .and. 3в        ! ← упакованные цифры ЧЧ ММ СС
      ...
      time = s2 + 10*s1 + 60*(m2 + 10*m1 + 60*(h2 + 10*h1))
      end
```

**Находка A.2.1 (подтверждение в эмуляторе).** В `src/Besm6.Runtime/ExtracodeHandler.Math.cs` экстракод `55` (= 067 oct) уже обрабатывается как `DATE*` и возвращает упакованную дату/время. Поведение управляется `Config.UseWallClock` (по умолчанию `true`) и CLI-флагом `--no-wall-clock` (`RunCommand.cs`), который переключает на фиксированную дату `04/07/2024 23:45:56` ради детерминизма.

> **Вывод A.2.2:** `DATE*` даёт **астрономическое (host wall-clock) время**, а не время работы процессора. Для честного `Dhrystones/sec` реальной БЭСМ-6 это подходит, но результат **не воспроизводим** (зависит от загрузки host-машины).

## A.3. Аппаратный таймер процессора: экстракоды 075 / 076

**Находка A.3 (документация репозитория).** `ref/dubna/doc/Besm6_Instruction_Set.md` (строки 910–911) прямо описывает процессорный таймер:

| Экстракод | Назначение (документация) |
|:---:|:---|
| **075** | CPU time query (**1/50 second units**, т.е. квант 20 мс) |
| **076** | CPU time query with **microsecond resolution** |

**Находка A.3.1 (текущее состояние).** Эти экстракоды не реализованы: в `src/Besm6.Architecture/Extracode.cs` `E75 = 61` помечен как «write A to memory», `E76 = 62` — «kernel routine», а `ExtracodeInstructionExecutor` при необработанном экстракоде бросает `ProcessorException("Extracode N not implemented")`.

> **Вывод A.3.2:** архитектурно правильный путь — сделать `075`/`076` источником **модельного** времени процессора (`MachineCore.Clock`). Это дало бы программе детерминированный CPU-таймер и позволило бы считать DMIPS внутри задания, как в оригинале, но на воспроизводимом модельном времени.

## A.4. Точная модель тактов: таблица из документации

**Находка A.4 (ключевая).** `book/03-instruction-set.md` содержит готовую таблицу реальной стоимости каждой команды в тактах (§3.4 и §3.7), плюс длительность такта:

- регистровые / логические (`уи`, `счи`, `и`, `или`, `нтж`) — 1 такт;
- сложение/вычитание, загрузка/запись, сдвиги — 2 такта;
- умножение (`умн`) — 7 тактов; деление (`дел`) — 12 тактов;
- переводы порядка (`слп`/`вчп`/`слпа`/`вчпа`) — 4 такта;
- `слц`, `чед`, `нед` — 4 такта; `сбр`/`рзб`/`сд` — 2 такта;
- переходы (`пб`, `пп`) — 2 такта;
- экстракоды — ~50–100 тактов (5–10 мкс);
- **такт = 100 нс** ⇒ номинальная частота ≈ 10 МГц (9–10 МГц по тексту).

**Находка A.4.1.** Значит, DMIPS можно считать детерминированно и без host-таймера:

```
число_тактов  = Σ (кол-во_команд_опкода × такты_опкода)
t_модель      = число_тактов × 100 нс
Dhrystones/s  = 1 / (t_модель / N_итераций)
DMIPS         = Dhrystones/s / 1757
```

Это точнее оценки «1 MIPS» в §5.2, где все команды условно считались по 1 такту.

**Находка A.4.2.** Константа `MachineCore.TicksPerInstruction = 1` описывает шаг инструкции как 1 тик. Чтобы модель совпала с таблицей тактов, стоимость шага должна стать переменной по опкоду — либо на уровне `MachineCore.Step()` (зная опкод текущей команды), либо через внешний профайлер (см. A.5).

## A.5. Точки съёма опкода без изменения CPU-пути

**Находка A.5.** Процессор уже отдаёт опкод наружу read-only хуками — добавление гистограммы опкодов не требует правок `Besm6.Processor`:

| Хук | Сигнатура | Где определён | Что даёт |
|:---|:---|:---|:---|
| `Processor.TraceInstruction` | `Action<uint,bool,uint,uint>` = `(k, rightFlag, rk, opcode)` | `Processor.cs:48` | сырой опкод до исполнения |
| `Processor.InstructionTrace` | `Action<InstructionTraceRecord>` | `Processor.cs:51` | типизированная запись (K, формат, опкод) |
| `MachineCore.StepTrace` | `Action<int,ulong>` = `(k, word)` | `MachineCore.cs:47` | слово памяти по K (декод через `InstructionCodec`) |

Проводка в `ExecutionLoop.RunCore()` уже существует: `if (CppInstructionTrace != null) _machine.Cpu.TraceInstruction = ...` (`src/Besm6.Runtime/Loading/ExecutionLoop.cs`).

> **Вывод A.5.1:** можно собрать гистограмму опкодов в слое Runtime/Cli и посчитать такты по таблице A.4, не трогая Gate A (наблюдаемая семантика инструкций не меняется).

## A.6. Сравнение методов получения DMIPS для симулятора

**Таблица A.2.** Методы измерения времени и их свойства.

| Метод | Источник времени | Воспроизводимость | Соответствие оригиналу | Требуемые изменения |
|:---|:---|:---:|:---:|:---|
| **1. `DATE*` (067)** | host wall-clock, упакован в ЧЧММСС | нет (зависит от host) | среднее (таймер ОС, а не CPU) | добавить `time()` в текст Паскаля |
| **2. Экстракоды 075/076** | модельное / CPU-время | да | высокое (CPU-таймер) | реализовать 075/076 в `ExtracodeHandler` + связать с `MachineCore.Clock` |
| **3. Профайлер тактов** | таблица тактов × гистограмма опкодов | да, полностью | высокое (архитектурная модель) | новый `OpcodeProfiler` в Runtime/Cli (Gate A не трогается) |

**Рекомендация.** Метод 3 как основной (детерминированный, воспроизводимый, без правок ядра) + метод 2 как архитектурный follow-up (даёт программе CPU-таймер, как у реальных машин, где 075/076 и были предназначены именно для бенчмарков).

## B.2. Команды получения метрик

**Находка B.2.1.** Вывод в стиле оригинального Dhrystone 2.1 выдаётся флагами CLI `--profile --passes N --baseline-cycles S --baseline-instructions I`:


Обратим внимание на явное указание `--limit` (см. §6.4): без него возможен усечённый прогон.

# Приложение C. Команды воспроизведения

Все измерения воспроизводятся следующими командами (сборка Release):

```bash
# 1. Baseline (numberofruns = 0)
dotnet src/Besm6.Cli/bin/Release/net8.0/besm6.dll \
    run examples/dhrystone-baseline.dub --profile

# 2. Основной прогон
dotnet src/Besm6.Cli/bin/Release/net8.0/besm6.dll \
    run examples/dhrystone.dub \
    --limit 40000000 --profile --passes 5000 \
    --baseline-cycles 9738603 \
    --baseline-instructions 5623553
```

Ожидаемый вывод в завершающем блоке:

```text
Dhrystone Benchmark, Version 2.1 (Language: Pascal for BESM-6)
Number of runs:                     5000
Instructions per run (model):       1550.7
Cycles per run (model):             2601.2
Time per run (model, sec):          0.000260118
Dhrystones per Second:              3844.41
VAX MIPS rating:                    2.1881
```

Наличие в выводе строки `Halted by STOP` (а не `Instruction limit reached`) является обязательным условием корректности полученных метрик.

**Находка C.1 (асимметрия флагов baseline).** Флаги `--baseline-cycles` и `--baseline-instructions` независимы, но метрики корректны только при передаче **обоих**. Если указать лишь `--baseline-cycles`, то `Cycles per run` и `Dhrystones per Second` будут верными, а строка `Instructions per run` окажется завышена: без вычитания baseline она печатает 2675.4 вместо 1550.7 (то есть включает в себя 5 623 553 инструкции компиляции и загрузки). Наблюдение возникло при рецензионной сверке отчёта и легко даёт расхождение в 1.7 раза. Проверка: переданное значение `Instructions per run` должно равняться `(счётчик прогона − счётчик baseline) / passes`.
