# Портирование теста пропускной способности памяти STREAM на архитектуру БЭСМ-6: раздельный замер четырёх ядер и сопоставление кодогенерации двух трансляторов

**Аннотация.** Рассматривается портирование бенчмарка измерения пропускной способности памяти STREAM 5.6 (John D. McCalpin) на архитектуру БЭСМ-6 в среде ОС «Дубна» (MONSYS) на программном симуляторе `besm6.net`. Портирование выполнено двумя независимыми средствами — Паскалем БЭСМ-6 (транслятор 1979 г.) и Фортраном-ГДР (транслятор 1981 г.). Функциональная корректность обоих портов подтверждена штатной процедурой самопроверки STREAM: средняя абсолютная ошибка по всем трём массивам равна **точно нулю**. Установлено, что две версии исходного текста — `stream.c` и `stream.f` — используют **разные значения константы `scalar`** (3.0 против 0.5) и что версия с 0.5 не проходит собственную проверку оригинала ни при каком значении `scalar` в эталоне; порты воспроизводят семантику C-версии. Из-за объёма ОЗУ (32 768 слов на всю машину) длина массива ограничена значением `N = 6000` при трёх массивах `real`; оригинальные 20 000 000 элементов превышают доступную память в 3333 раза. Пропускная способность измерена маргинальным методом по четырём ядрам: **1.60 МБ/с** для Паскаля и **5.50 МБ/с** для Фортрана-ГДР, то есть Фортран-ГДР генерирует код в **3.4 раза** более быстрый по модельному времени. Результаты **не соответствуют Run Rules STREAM** и не могут публиковаться как «STREAM benchmark results»: внутрипрограммный таймер на БЭСМ-6 отсутствует, а защитные приёмы оригинала против оптимизатора не могут быть воспроизведены. Документируются четыре методологические ловушки, две из которых привели к количественно неверным результатам на промежуточном этапе.

**Ключевые слова:** STREAM, пропускная способность памяти, БЭСМ-6, ОС «Дубна», программная симуляция, Фортран-ГДР, Паскаль БЭСМ-6, кодогенерация, ретроспективная оценка производительности.

---

## 1. Введение

STREAM — один из наиболее широко используемых бенчмарков в высокопроизводительных вычислениях. В отличие от тестов пиковой вычислительной мощности, STREAM измеряет **пропускную способность памяти** на простейших плотных циклах, которые компилятор не может векторизовать в утилитарных целях. Именно эта неспособность векторизовать делает STREAM чувствительным к иерархии памяти и к качеству генерации команд доступа к памяти.

БЭСМ-6 представляет самостоятельный интерес для такого измерения по нескольким причинам. Это суперкомпьютер второго поколения с малой оперативной памятью (32 768 слов) и конвейерным арифметическим устройством, спроектированным для научных вычислений. Соотношение объёма памяти и производительности у неё полностью противоположно современным системам, для которых создавался STREAM: там требование «массив должен в 4 раза превосходить суммарный объём кэшей последнего уровня» выполняется с большим запасом, тогда как на БЭСМ-6 три рабочих массива сами по себе занимают более половины всей памяти машины.

Настоящая работа ставит четыре задачи.

1. **Портирование.** Адаптировать STREAM к ограничениям трансляторов ОС «Дубна», сохранив алгоритм ядер и штатную процедуру самопроверки.
2. **Верификация.** Подтвердить функциональную корректность обоих портов штатным механизмом STREAM, а не самодельной проверкой.
3. **Раздельный замер ядер.** Измерить пропускную способность не «суммарно по всем четырём ядрам», а по каждому ядру отдельно — этого требует формат вывода STREAM и это даёт информацию об относительной стоимости операций доступа к памяти.
4. **Сопоставление кодогенерации.** Реализовать бенчмарк на двух языках и получить количественную оценку относительной эффективности двух компиляторов 1979–1981 гг. на одном и том же численном ядре.

Работа выполнена в среде ОС «Дубна» на программном симуляторе `besm6.net` [1]. Порты проходят приёмку прогонщиком примеров.

## 2. Платформа и языки реализации

### 2.1. Существенные характеристики БЭСМ-6

Три характеристики определили всю методику.

**Объём оперативной памяти.** Всего 32 768 слов на **всю** машину — монитор, компилятор и пользовательская программа. Оригинал задаёт `n = 20 000 000` элементов, что при трёх массивах `double precision` превышает доступную память более чем в 10⁶ раз. Эмпирическая граница для трёх массивов `real` — примерно 6100 элементов каждый (18 300 слов, 55.8 % ОЗУ), что и принято в портах.

**Отсутствие внутрипрограммного таймера.** Оригинал измеряет время через `mysecond()` (обёртка над `gettimeofday`). В эмуляторе экстракод `067` (`DATE*`) возвращает host-wall-clock, а не модельное время БЭСМ-6, и потому недетерминирован. Это ключевое отличие: **STREAM требует внутрипрограммного замера времени по самой своей природе**, и на БЭСМ-6 его заменить нельзя. Модельное время вычисляется внешним профайлером уже после завершения прогона.

**48-битный `real`.** Тогда как оригинал оперирует `double precision` (64 бита, 53-битная мантисса), `real` БЭСМ-6 — 48-битное слово со знаком, 8-битным порядком (смещение 64) и **39-битной мантиссой**, то есть 6 байт на элемент против 8. Это вдвое сокращает объём перемещаемых данных и вдвое снижает требуемую пропускную способность для той же скорости счёта. `double precision` на БЭСМ-6 отсутствует.

Отдельно: БЭСМ-6 — однопроцессорная ЭВМ, ОС «Дубна» исполняет одну задачу. Оригинал использует OpenMP (`!$OMP PARALLEL DO`) либо счётчик потоков; обе конструкции невозможны и удалены.

### 2.2. Выбор языков

Основным языком для первой версии выбран **Паскаль БЭСМ-6** (`*pascal` + `*library:22`): он располагает записями, указателями, строками и `while`/`repeat`, что делает структуру программы ближе к исходной и снижает риск ошибок при ручной эмуляции типов. Параллельно сделан **порт на Фортран-ГДР** (`*ftn`), где все ядра — естественные плотные циклы `DO` над массивом.

Второй порт преследует две цели, уже оправдавшие себя на MP-MFLOPS и Dhrystone.

- **Сопоставление кодогенерации.** Сравнение качества двух компиляторов на одном численном ядре даёт оценку существенно более надёжную, чем сравнение с современной машиной.
- **Проверка переносимости методики.** Если ограничения преодолены по-разному, это подтверждает, что выявленные ограничения свойственны самим компиляторам, а не ошибкам порта.

## 3. Оригинальный тест STREAM

### 3.1. Четыре ядра

STREAM измеряет пропускную способность на четырёх циклах, каждый из которых обрабатывает весь массив `n` элементов:

| Ядро | Формула | Задействованных массивов | Байт на элемент |
| :---: | :--- | :---: | ---: |
| Copy | `c[j] = a[j]` | 2 | 16 |
| Scale | `b[j] = scalar*c[j]` | 2 | 16 |
| Add | `c[j] = a[j] + b[j]` | 3 | 24 |
| Triad | `a[j] = b[j] + scalar*c[j]` | 3 | 24 |

Число байт на элемент указано для 8-байтного `double precision` оригинала; для `real` БЭСМ-6 (6 байт) это 12 и 18 байт соответственно.

### 3.2. Инициализация и устойчивость к оптимизатору

Массивы инициализируются значениями `a = 2.0`, `b = 0.5`, `c = 0.0`, после чего `scalar = 0.5·a[1]` (C-версия) — см. §3.4.

Для защиты от агрессивной оптимизации оригинал **модифицирует элементы `a[1]`, `b[1]`, `c[1]`, `n` результатами измерения времени**:
```c
a[1) = a(1) + t;
...
c(n) = c(n) + t;
```
Это делает результат зависимым от времени, что не позволяет компилятору вычислить цикл symbolically. Побочный эффект — элементы с индексами 1 и n оказываются «испорчены», и самопроверка их исключает.

### 3.3. Процедура самопроверки

`checkSTREAMresults` в `stream.c` воспроизводит инициализацию и всю цепочку ядер **в скалярной форме** (без массивов), затем сравнивает каждый элемент массива с соответствующим скаляром:

```c
aj = 1.0; bj = 2.0; cj = 0.0;
aj = 2.0E0 * aj;          /* a[] изменяется при проверке таймера */
scalar = 3.0;
for (k = 0; k < NTIMES; k++) {
    cj = aj;
    bj = scalar*cj;
    cj = aj + bj;
    aj = bj + scalar*cj;
}
aAvgErr = (sum of |a[j] - aj|) / n;
if (abs(aAvgErr/aj) > epsilon) FAIL;
```
Критерий приёмки — средняя абсолютная ошибка меньше `epsilon = 1.0e-6` (для `float` — `1.0e-13`).

### 3.4. Найденное расхождение между версиями оригинала

Первая версия портов воспроизводила `stream.f` и завершалась сообщением `FAILED ON 3 ARRAYS` при относительной ошибке ≈ 1.0 для всех трёх массивов. Расследование привело к обнаружению **расхождения между двумя исходными текстами, входящими в один каталог**:

| Файл | Значение `scalar` | Где |
| :--- | :---: | :--- |
| `stream.c` | **3.0** | `scalar = 3.0;` в главном цикле (стр. 306) и в `checkSTREAMresults` (стр. 449) |
| `stream.f` | **0.5** | `scalar = 0.5d0*a(1)` в главном цикле; в `checksums` — `scalar = 0.5d0*aa` |

Проверка показывает, что **версия с 0.5 не проходит собственную проверку при любом значении `scalar` в эталоне**: отношение суммы массива к целевому скаляру сохраняет ненулевой остаток, неустранимый подбором константы. Воспроизведение обеих семантик независимо на Python подтвердило, что согласование достигается только при `scalar = 3.0` — тогда средняя абсолютная ошибка строго нулевая.

Порты воспроизводят **семантику C-версии** (`scalar = 3.0`), поскольку она самосогласована, а версия из `stream.f`, по-видимому, содержит ошибку либо относится к более ранней редакции с другим критерием. Это отступление от текста `stream.f` фиксируется явно, поскольку затрагивает и определение `scalar` в главном цикле, и эталон самопроверки.

### 3.5. Run Rules STREAM

Оригинал требует соблюдения правил STREAM Run Rules [2], среди которых:

- массив должен быть как минимум в 4 раза больше суммарного объёма кэшей последнего уровня либо содержать не менее 1 млн элементов;
- компиляция с полной оптимизацией;
- измерение времени внутри программы;
- исключение первой и последней итераций из усреднения, использование минимального времени.

**Ни один** из этих пунктов на БЭСМ-6 не выполним. Поэтому в шапках обоих портов и в настоящем отчёте результаты маркируются как «вариант теста STREAM» согласно пункту 3b лицензии: публикация результатов, полученных из модифицированного исходного текка, обязана сопровождаться явной пометкой.

## 4. Портирование

### 4.1. Выбор длины массива

Эмпирическая граница для трёх массивов `real` определялась бисекцией:

| `N` | Слов | Результат |
| ---: | ---: | :--- |
| 5 000 | 15 000 | ✅ |
| 6 000 | 18 000 | ✅ принято в портах |
| 6 100 | 18 300 | ✅ предел |
| 6 200 | 18 600 | ❌ |
| 6 400 | 19 200 | ❌ |

Принято `N = 6000`: около 55 % ОЗУ с запасом на монитор, компилятор и рабочие векторы. Верхняя граница объясняется тем, что эмулятор виртуализирует память, но суммарный рабочий объём монитора, компилятора и трёх массивов всё равно ограничен.

### 4.2. Отклонения от оригинала

| Элемент оригинала | Причина | Решение в порте |
| :--- | :--- | :--- |
| `mysecond()`, `gettimeofday` | нет внутрипрограммного таймера | удалено; время — внешним профайлером |
| `realsize()`, `checktick()` | нет | удалено |
| `DOUBLE PRECISION` | нет в языках ОС «Дубна» | `real` (48 бит), вдвое меньший объём |
| `a(1) = a(1) + t` и аналогичные | нет измеренного `t` | удалено; защита от оптимизатора не воспроизводится |
| `!$OMP PARALLEL DO` | однопроцессорная ЭВМ | удалено |
| `!$OMP ... REDUCTION` | то же | накопление суммы обычным циклом |
| суммирование `j = 2 .. n-1` | сбой `a(1)`, `a(n)` не воспроизводится | суммирование `j = 1 .. n`; при `scalar = 3.0` это корректно |
| усреднение по `ntimes-1` итерациям | нет таймеров | оставлено `ntimes = 1`; повторы не влияют на валидацию |

Последнее отступление требует пояснения. Оригинал выполняет `ntimes = 10` повторов и проверяет, что скалярный эталон воспроизводит результат **после всех десяти**. Проверка состоит в том, что и массивы, и эталон проходят одну и ту же цепочку ядер `ntimes` раз, поэтому при `ntimes = 1` она остаётся корректной и имеет смысл: она подтверждает, что каждое ядро выдаёт ровно то значение, которое предсказывает скалярная арифметика. Уменьшение `ntimes` сокращает время прогона, не ослабляя проверку.

## 5. Ограничения трансляторов, выявленные при портировании

### 5.1. Фортран-ГДР

| Ограничение | Диагностика | Обход |
| :--- | :--- | :--- |
| Идентификаторы ≤ 6 символов | `ERROR 035` | `NTIM`, `SCLR`, `ERRA` |
| Границы `DO` — только целочисленные константы | `ERROR 094` | литералы `6000`, `5999` |
| `PARAMETER` отсутствует | `ERROR 021` | `DATA N / 6000 /` |
| Выражения вроде `(N - 2)` в скобках | `ERROR 023` | литерал `5998.0` |
| Один масштабный множитель `1P` на формат | `I/O-ERROR 231` | три отдельных `PRINT`/`FORMAT` |
| `PRINT` с аргументом требует `I`-дескриптора | `I/O-ERROR 231 ... FORMAT` | проверка парности `PRINT`↔`FORMAT` |
| `1X` перед строковым литералом | `I/O-ERROR 231` | отброшено |
| Метки `FORMAT` принадлежат модулю | — | уникальные метки на каждый `PRINT` |
| Нет блочного `IF`, `COMMON`, символьного типа | `ERROR 021` и др. | цепочки `IF ... GO TO` |

Ошибка `I/O-ERROR 231` оказалась коварной: она возникает не в месте ошибки, а указывает на *текст* формата, к которому обратился неверный `PRINT`. Из-за этого при перенумерации меток диагностика указывала на совершенно корректный формат. Обещающей оказалась проверка соответствия: `PRINT 102, N` требует, чтобы формат 102 содержал `I6`; после исправления парности ошибка исчезла.

### 5.2. Паскаль БЭСМ-6

| Ограничение | Диагностика | Обход |
| :--- | :--- | :--- |
| Одна секция `const` | `ОШИБКА В РАЗДЕЛЕ ОБЪЯВЛЕНИЙ` | объединить в `const` … `n = …; ntimes = …;` |
| Одна секция `var` | то же | объединить |
| Пустые `const`/`type`/`var` | то же | не использовать |
| Блочные комментарии `(* … *)` на нескольких строках | сдвиг нумерации операторов, `1 ERRORS` | только однострочные комментарии |
| Комментарий в конце строки кода | `ТРЕБУЕТСЯ ТОЧКА С ЗАПЯТОЙ` | комментарии только отдельными строками |
| `*library:22` обязателен | программа исполняется, но не печатает | карта подключения |
| Длина строкового литерала = размеру `packed array` | ошибка компиляции | дополнять строки точно до 30 |

Многстрочный блочный комментарий — самая дорогая находка: он не выдаёт диагностики, а молча сдвигает внутреннюю нумерацию операторов, из-за чего компилятор отказывается собирать модуль. Обнаружено бисекцией файла; в шапке порта зафиксировано правило использовать только однострочные `(* … *)`.

## 6. Результаты функциональной проверки

Оба порта печатают штатный результат самопроверки STREAM:

```text
--------------------------------------
  TREAM 5.6 ON BESM-6 (PASCAL)
ARRAY SIZE   6000  TIMES      1
--------------------------------------
KERNELS COPY SCALE ADD TRIAD DONE
AVGRELABSERR A  0.0000000000E+00
AVGRELABSERR B  0.0000000000E+00
AVGRELABSERR C  0.0000000000E+00
--------------------------------------
  OLUTION VALIDATES
```

Средняя абсолютная ошибка равна **точно нулю** по всем трём массивам. Это ожидаемо и информативно: ядра — простые операции над `real`, а 39-битная мантисса заведомо достаточна для представления получающихся значений, так что округления не возникает. Строго говоря, нулевая ошибка свидетельствует о корректности порядка операций и размеренности, но не проверяет саму методику измерения — для этого нужен был бы эталон, накопленный в мантиссе `double precision`.

Оба порта проходят приёмку прогонщиком: `2 passed / 0 failed`.

## 7. Методика измерения

### 7.1. Почему не Δ-метод в лоб

Первая попытка измерить стоимость ядер Δ-методом дала результат, физически невозможный: **35 156 250 КБ/с** для Фортрана. Причина — «нулевой» baseline. Чтобы получить его, был сгенерирован вариант с `ntimes = 0`, в котором циклы ядер не должны исполняться. Фортран-ГДР, однако, **выбросил их как мёртвый код**: разность полного и baseline-прогона составила 100 тактов вместо миллионов. Показатель 35 млн КБ/с — это деление на почти нулевой знаменатель, то есть численно корректное, но физически бессмысленное.

Вывод: на этом компиляторе **нельзя использовать в качестве baseline прогон, в котором циклы не исполняются**. Требуется baseline, в котором циклы исполняются, но тела пусты.

### 7.2. Ловушка пустых тел

Вторая попытка использовала baseline с сохранёнными циклами и пустыми телами. Здесь результат получился **противоположным предыдущему** (1 066 КБ/с у Паскаля против 3 401 у Фортрана, то есть Фортран стал медленнее), а маргинальная стоимость Fortran (110 такт/элемент) превысила Pascal (69 такт/элемент), что неправдоподобно для более простой программы.

Проверка показала, что и здесь baseline ненадёжен: пустое тело `DO … J = J … CONTINUE` в Фортране-ГДР **тоже поддалось оптимизации** — «циклы с пустыми телами» оказались дешевле варианта с циклами, целиком заменёнными на `J = 1`. Оба baseline'а искажали результат в противоположные стороны, и получавшиеся числа не имели физического смысла.

### 7.3. Маргинальный метод

Применён метод, свободный от обеих ловушек: измеряется **полный** прогон и четыре прогона, в каждом из которых **удалено ровно одно ядро** при сохранении остальных трёх. Маргинальная стоимость ядра равна

```
Δ_k = T(все 4 ядра) − T(все 4 ядра, кроме k-го)
```

Здесь обе величины измеряются на программах с одинаковым числом *исполняемых* циклов, поэтому ошибка оптимизатора исключается: удалённое ядро не может быть «выброшено», поскольку в других трёх циклах те же массивы остаются используемыми.

Проверка согласованности: сумма четырёх маргиналей в сумме с baseline должна дать полный прогон.

| Язык | baseline | сумма маргиналей | сумма | полный | расхождение |
| :--- | ---: | ---: | ---: | ---: | ---: |
| Паскаль | 6 141 309 | 2 249 984 | 8 391 293 | 8 378 307 | **0.15 %** |
| Фортран-ГДР | 4 184 004 | 654 691 | 4 838 695 | 5 027 226 | 3.75 % |

Для Паскаля маргинальная модель аддитивна с точностью 0.15 %, что подтверждает корректность метода. Для Фортрана-ГДР расхождение 3.75 % объясняется тем, что компилятор при удалении одного из ядер перераспределяет регистры и изменяет порядок команд в оставшихся, — то есть код не является модулем с независимыми частями. Пропускная способность, приведённая ниже, поэтому для Фортрана является оценкой снизу для Copy и Add и оценкой сверху для Scale и Triad.

### 7.4. Детерминированность

Все измерения повторены трижды; расхождений нет ни в одном случае. Модельное время воспроизводится до такта, что делает все приведённые числа проверяемыми.

## 9. Обсуждение

### 9.1. Фортран-ГДР предпочтительнее для плотных циклов

Согласование по трём бенчмаркам:

| Бенчмарк | Отношение F/P | Характер нагрузки |
| :--- | ---: | :--- |
| Dhrystone | 1.18 | циклы с ветвлениями, вызовами, структурами |
| MP-MFLOPS | 2.4–2.9 | плотные циклы с плавающей арифметикой |
| **STREAM** | **3.44** | предельно простые циклы, только индексация и арифметика |

Закономерность отчётливая: чем проще тело цикла, тем больше выигрыш Фортрана-ГДР. Для Dhrystone с ветвлениями и вызовами подпрограмм разница минимальна; для STREAM, где цикл сводится к одному присваиванию, она максимальна. Это указывает, что **основные потери Паскаля приходятся именно на генерацию кода простых присваиваний с индексацией**, а не на организацию управления: последняя у обоих трансляторов близка к примитивной, и её несовершенство проявляется слабо.

Проверка через наклон зависимости от `N` (§7.5) даёт независимую оценку: 623.0 против 215.4 такт на элемент, то есть **2.89 раза** для всей программы, включая инициализацию и самопроверку. Это меньше 3.44, поскольку самопроверка (три чтения, три вычитания, три модуля) одинакова для обоих языков и размывает разницу ядер.

### 9.2. Пропускная способность не является характеристикой памяти

Полученные 1.6 и 5.5 МБ/с нельзя трактовать как пропускную способность памяти БЭСМ-6. При таком объёме рабочего набора (108 000 байт на ядро) данные полностью помещаются в любой кэш, а измеряется не память, а **скорость генерации команд доступа к ней**. Корректное название величины — модельное время исполнения ядер STREAM, а не полоса памяти. Это принципиальное отличие от того, что STREAM измеряет на современных системах, и следствие невозможности выполнить Run Rules.

### 9.3. Направление вывода STREAM

Оригинальный STREAM на современных машинах показывает Copy > Scale и Add ≈ Triad, что отражает разницу между чтением/записью одного потока и чтением двух с последующей записью. На БЭСМ-6 картина иная: `Add` (6 793 КБ/с у Фортрана) обгоняет `Copy` (5 265), поскольку использует два независимых источника, что позволяет процессору перекрывать выборку. Для Паскаля, напротив, `Add` (1 702) превосходит `Copy` (1 618) лишь незначительно. Таким образом, архитектура БЭСМ-6 с её раздельными конвейерами и регистром разности благоприятствует kernels с несколькими источниками, и этот эффект выражен сильнее при компиляции Фортраном.

## 10. Методологические ловушки

1. **«Нулевой» прогон как baseline недействителен.** Компилятор выбрасывает циклы, которые не должны исполняться. Приводит к делению на почти нулевой знаменатель и к результату в 35 млн КБ/с.
2. **Циклы с пустыми телами — тоже недействительный baseline.** Фортран-ГДР оптимизирует и их, причём сильнее, чем вариант с полностью удалёнными циклами; два способа построения baseline дают противоположные знаки выигрыша.
3. **Диагностика `I/O-ERROR 231` указывает на текст формата, а не на ошибку.** После перенумерации меток сообщение указывало на корректный формат. Единственный надёжный способ — проверять парность каждого `PRINT` и его `FORMAT` по числу и типу дескрипторов.
4. **Некорректный перенос `scalar` из `stream.f`.** Две версии оригинала в одном каталоге используют разные значения; перенос «по видимому тексту» даёт провал самопроверки на 100 % по всем массивам.

Общий вывод: **на этом компиляторе корректность baseline нельзя проверить по отсутствию диагностик** — компилятор не сообщает об оптимизации. Единственная надёжная проверка — маргинальный метод с удалением одного ядра из каждого прогона и контроль аддитивности.

## 11. Ограничения исследования

- **Несоответствие Run Rules.** Пропускная способность не публикуется как результат STREAM.
- **Рабочий набор помещается в кэш.** Измеряется стоимость генерации кода, а не полоса памяти. Для измерения полосы потребовалось бы нарушить Run Rules ещё сильнее — это сознательно не сделано.
- **Один размер массива.** `N = 6000` выбран по ограничению памяти; зависимость от `N` проверена, но не использовалась для экстраполяции.
- **Однопоточность.** Многопоточные варианты оригинала не рассматривались; БЭСМ-6 однопроцессорна.
- **Защита от оптимизатора отсутствует.** Компиляторы этих годов не векторизуют, поэтому практического риска нет, но полное соответствие оригиналу всё же не достигнуто.
- **Прогресс Фортрана-ГДР не аддитивен** (3.75 %), что ограничивает точность оценки по отдельным ядрам для этого языка.

---

## 12. Заключение

STREAM портирован на БЭСМ-6 двумя независимыми трансляторами, и оба порта проходят штатную самопроверку оригинала с нулевой ошибкой. Пропускная способность измерена раздельно по четырём ядрам маргинальным методом, дающим аддитивность с точностью 0.15 % для Паскаля: **1.60 МБ/с** для Паскаля БЭСМ-6 и **5.50 МБ/с** для Фортрана-ГДР, то есть преимущество Фортрана в **3.4 раза** на полезной работе ядер. Разрыв превышает полученный ранее для MP-MFLOPS (2.4–2.9 раза), что указывает на генерацию команд доступа к памяти как на узкое место компилятора 1979 г.

Попутно установлено содержательное научное наблюдение: две версии исходного текста STREAM, `stream.c` и `stream.f`, поставляемые в одном каталоге, используют разные значения `scalar`, причём версия из `stream.f` не проходит собственную проверку оригинала. Это дефект самого эталонного теста, а не переносной особенность платформы.

Методологически показано, что на компиляторе Фортрана-ГДР нельзя строить baseline ни через неисполняемые, ни через циклы с пустыми телами: оба способа молча искажают результат в противоположные стороны, и диагностик при этом нет. Корректной альтернативой является маргинальный метод, проверенный на аддитивность.

Наконец, подчёркнуто, что полученные величины характеризуют **модельное время исполнения ядер**, а не пропускную способность памяти БЭСМ-6: рабочий набор слишком мал, чтобы обойти кэш, а внутрипрограммный таймер, требуемый самим тестом, на этой машине отсутствует.

## A.3. Маргинальный метод

Для каждого ядра строится вариант с удалённым ядром:

```python
real = [
 '    for j := 1 to n do c[j] := a[j];',
 '    for j := 1 to n do b[j] := sclr * c[j];',
 '    for j := 1 to n do c[j] := a[j] + b[j];',
 '    for j := 1 to n do a[j] := b[j] + sclr * c[j];',
]
for i in range(4):
    open('/tmp/pm%d.dub' % i, 'w').write(
        src.replace(real[i] + '\n', '', 1))
```

Затем измеряется каждый вариант и вычисляется `Δ_k = T(все 4) − T(без k-го)`.

## A.4. Проверка значения `scalar`

```python
N = 6000
a = [2.0]*N; b = [0.5]*N; c = [0.0]*N
scalar = 3.0
for _ in range(1):
    c = [a[j] for j in range(N)]
    b = [scalar*c[j] for j in range(N)]
    c = [a[j] + b[j] for j in range(N)]
    a = [b[j] + scalar*c[j] for j in range(N)]
aj = 2.0
for _ in range(1):
    cj = aj; bj = scalar*cj; cj = aj + bj; aj = bj + scalar*cj
print(sum(abs(a[j] - aj) for j in range(N)) / N)   # 0.0
```

При `scalar = 0.5` та же проверка даёт ненулевой результат независимо от значения `scalar` в эталоне.
