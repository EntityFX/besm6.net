### Независимые векторы

[JSON](../tests/Besm6.Processor.Tests/TestData/book-vectors.json) содержит
100 векторов исполнения и шесть буквальных печатных констант.
У каждого вектора есть идентификатор, ссылки на источники, начальные
регистры, сырые команды, память, ожидаемые A/Y/R/C/ApplyC/M/K/half,
STOP/ошибка/успешные тики и ожидаемые записи памяти.
Все 16 M и вся память, включая слова команд, проверяются.

`expected` — полное ожидаемое состояние **профиля Dubna**.
`bookDefined` перечисляет поля, для которых использовано правило книги;
`differences` содержит отдельное книжное ожидание и идентификатор вопроса.
Доказанная полнота книжного правила ограничивается описанными сценариями.
Вне их списка значение регистра не считается аппаратным эталоном.
Например, книга не определяет Y после деления; его точное значение всё
равно проверяется как контракт Dubna. C/ApplyC после погашения признака,
STOP и регистры при исключении также закреплены как программный контракт.

Векторы строит [generate_book_vectors.py](../tools/generate_book_vectors.py).
Он использует `Fraction` и целые числа, не вызывает конвертеры, АУ,
нормализатор C# или C++. Из главы § 2 непосредственно получается

`value = signed41(mantissa) × 2^(order − 64 − 40)`.

Положительная нормализованная мантисса лежит в `[1/2, 1)`, отрицательная
в `[-1, -1/2)`. Для INT порядок равен 40. Шесть печатных кодов:

| Константа | Восьмеричное слово |
|---|---|
| LOG 4 | `0000 0000 0000 0004` |
| INT 38 | `6400 0000 0000 0046` |
| INT −5 | `6437 7777 7777 7773` |
| REAL 1 | `4050 0000 0000 0000` |
| REAL 20 | `4252 0000 0000 0000` |
| REAL −1 | `4020 0000 0000 0000` |

Для выбранных сложений и произведений строится точный 80-разрядный
результат. Его целочисленные старшая и младшая части задают A/Y.
Нормализация выполняется до округления; округление устанавливает младший
бит A через OR, если выполнено условие § 5. Это не ближайшее чётное.
Область оракула ограничена: только выбранные двоичные рациональные числа,
остаток которых целиком помещается в 80 разрядов. Потерю более дальних
битов, весь диапазон переполнения и внутренний цикл деления он не моделирует.

Контрольный пример: `1/2 + 2^-41` при включённом округлении даёт
`A=808000000001`, `Y=008000000000`; при блокировке округления
`A=808000000000`, Y сохраняет ту же младшую часть. Пример с уже единичным
младшим битом отличает OR от прибавления единицы. Другой пример проверяет
перенос единицы из Y при нормализации и отмену дополнительного округления.

| Область | Закреплённые сценарии |
|---|---|
| Формат | Печатные REAL/INT/LOG, точные числовые значения |
| АУ | A+X/A−X/X−A/AMX/A*X в четырёх сочетаниях блокировок |
| A/Y | Положительный и отрицательный результат, остаток, нормализация, OR-округление |
| Деление | Точные ±9/±6, 1/2, ноль; округление включено/выключено |
| Логика | XTA/ATX/AAX/AEX/AOX/ARX, перенос циклической суммы |
| R | NTR, сохранение блокировок при смене группы, AVX, RTE |
| C/M | UTC/WTC, использование ровно следующей командой, 15-битное переполнение, ATI/ITA/MTJ/J+M |
| Переходы | UZA/U1A в каждой группе R и для обоих исходов |
| Экстракод | Обе половины, следующая левая команда, M14; пустая услуга изолирует CPU dispatch |
| Авост | Нулевой и ненормализованный делитель, переполнение после нормализации, underflow |
| Dubna | Старшие биты Y на нулевом пути, STOP, состояние до/после перехвата |

Это ядро спецификации, а не исчерпывающая проверка всех команд. Следующие
независимые векторы потребуют описания YTA в арифметических группах,
крайних сдвигов, APX/AUX/ANX, магазина и полного порядка аппаратных авостов.
Существующие программные тесты этих областей продолжают выполняться.

### Реестр расхождений и решений

| ID | Книга / дополнительный источник | Текущий Dubna | Решение |
|---|---|---|---|
| BOOK-R-EXTRACODE | § 6, с. 23: R сохраняется | После обработанного экстракода устанавливается логическая группа; вектор R: `063 → 047` | Подтверждено отличие от текста. Оставить совместимость; уточнить версию диспетчера и интерфейс до аппаратного изменения |
| BOOK-R-RTE | Приложение 1, с. 248: группа не изменяется | RTE устанавливает логическую группу; тот же `063 → 047` | Сверено со сканом. Для аппаратного правила нужна инструкция [22], для Dubna значение закреплено |
| BOOK-Y-BRANCH | Приложение 1, с. 249: Y=0 для UZA/U1A | Y получает A при переходе и при его отсутствии | Сверено со сканом. Не исправлять общие обработчики по краткой таблице без подробной инструкции |
| DIVISION-VERSION | Закреплённая новая таблица upstream | 51/200 частных отличается | Различие алгоритмов, не ошибка печатного эталона. Потребуется отдельное аппаратное решение |
| Y-DIVISION | Приложение 1: Y не определён | Обычно Y=0; нулевой путь сохраняет старшие восемь бит | Не объявлять аппаратным расхождением. Все биты продолжают проверяться для Dubna |
| Y-ZERO | § 5 определяет 80-разрядный результат | На zero/underflow сохраняются старшие восемь бит старого Y | Верхние восемь бит не определены этим описанием; требуется отдельный источник |
| AVOST-STATE | § 5 определяет причину авоста, но не весь порядок фиксации регистров | K/half продвигаются до операции; при overflow A/Y уже изменены, R ещё прежний | Закреплён программный переход, аппаратный порядок остаётся вопросом |
| AVOST-CAUSE | § 5: деление на нуль либо ненормализованное число | Оба случая имеют сообщение `Division by zero` | Причины различать в будущей аппаратной диагностике; строку совместимости не менять |
| STOP-33 | Приложение 1, с. 249: код 33 не используется | Код 33 — STOP профиля Dubna | Программное расширение, не доказательство аппаратной команды |

Ни одно из этих расхождений не устраняется заменой эталона «на то, что
выдал процессор». Книжное ожидание хранится отдельно. Тест явно требует
как текущее значение Dubna, так и его отличие от зафиксированного книжного.
При будущем исправлении нужно осознанно сменить профиль/классификацию.

### Аудит версии деления

Upstream-коммит
[1d73a86ae71ac8d6a9d1a56a487007e5a240f8ba](https://github.com/besm6/dubna/commit/1d73a86ae71ac8d6a9d1a56a487007e5a240f8ba)
переносит `au_divide` из SIMH, добавляет таблицу и меняет выводы ряда тестов.
Автор связывает алгоритм с ТО ИЫ1 700 000 ТО-3, ч. IV, п. 4.16,
листами 86–102. Комментарий в коде отдельно отмечает правило переноса,
подобранное по константе Диспака. Само техническое описание здесь ещё
не прочитано и независимо не проверено.

[Аудит JSON](../reports/hardware-time/division-version-audit.json) и
[CSV](../reports/hardware-time/division-version-audit.csv) сохраняют все 200 исходных
операндов, ожидаемое кандидатом частное, текущее частное, Y и исключение.
149 совпадают, 51 отличается; исключений в этой таблице нет.
Разности машинных кодов candidate−current: +1 (21 случай), −1 (19),
−2 (5), +8 (2), +4 (2), −4 (2). Это разности кодов, не относительная
численная погрешность и не сравнение с измерением реальной машины.

Например, `3350142233513616 / 4212000000000000`:
текущий результат `3155066705654343`, кандидат `3155066705654344`.
Входы каждой строки одинаковы; аудит не пересчитывает цепочку следующих
делений с изменившимся результатом предыдущей строки.

В таблице книги частные с точным представлением должны получаться точно,
а дополнительного округления результата деления нет. Книга не задаёт
полный алгоритм получения неточного частного. Следовательно, 51 различие
не даёт основания заменить алгоритм в текущем Dubna. Обязательства перед
аппаратным изменением: получить техническое описание, проверить указанное
подобранное правило, закрепить отдельные биты и версию профиля, затем
провести полный CERN/golden и новый замер скорости.

## Управляющие признаки M17

Реализован `ControlUnitStatus`, неизменяемый семантический снимок семи
признаков из ТО-8, §7.7–7.8, печатный лист135. M17 здесь имеет
**десятичный номер17, восьмеричный021**. Нынешний M[15]=oct017 — обычный
стековый регистр, он не переименован и не заменён специальным.

| Разряд | Признак | Маска |
|---:|---|---:|
| 1 | БлП, блокировка приписки операндов | 0x001 |
| 2 | БлЗ, блокировка защиты операндов | 0x002 |
| 3 | ПОП, останов при внутреннем прерывании | 0x004 |
| 4 | ПОК, останов при прерывании по контролю | 0x008 |
| 5 | Зп(M29), совпадение адреса записи | 0x010 |
| 11 | БлПр, блокировка внешнего прерывания | 0x400 |
| 12 | АвтБ, автомат Б | 0x800 |

Известная маска —0xC1F (oct06037). Книга описывает отдельные усилители,
не подтверждая хранение остальных позиций полного слова. Поэтому
конструктор снимка отклоняет неизвестные флаги как ошибку API хоста;
это не моделирование аппаратного прерывания. Нулевой `default` — пустой
снимок, без предположений о холодном сбросе.

Книга разрешает управляющей программе только запись M17. Получение
снимка через host API не добавляет гостевую команду чтения. В явном профиле
`ProcessorProfile.Supervisor` специальные регистры и их гостевые операции
реализует `SupervisorControl`; профиль Dubna сохраняет прежнее поведение.
Упаковка искусственного RUU в SIMH не перенесена в архитектуру.

`WithSupervisorAddressControls(address)` задаёт только БлП/БлЗ/БлПр
по соответствующим разрядам адреса, сохраняя остальные четыре признака.
Маска0x403 (oct02003) закреплена в §7.8 для ПА/СА с регистром00 в
режиме супервизора. Она используется гостевыми ПА/СА00 в профиле Supervisor.
Адрес должен быть15-битным, прочие его разряды
не влияют на эти три признака.

```csharp
var controls = new ControlUnitStatus(ControlUnitFlags.AssignmentBlocked |
    ControlUnitFlags.ProtectionBlocked | ControlUnitFlags.ExternalInterruptsBlocked);
machine.MappedMemory!.ApplyControlStatus(controls);
```

`ApplyControlStatus` явно меняет только БлП/БлЗ операндов. Supervisor,
инверсия контрольных разрядов, память, приписка, буферы, часы и очередь
сохраняются. Сам метод не выполняет прерывание, не останавливает CPU
и не включает автомат Б. В профиле Supervisor отдельные обработчики
используют ПоП/ПоК, Зп(M29) и БлПр. Полное действие АвтБ пока не моделируется.
В Dubna ResetCpu сохраняет эти режимы памяти; в Supervisor он устанавливает
явно определённое программное bootstrap-состояние, сохраняя память и RP/RZ.
Оба варианта не являются общей аппаратной установкой нуля.

ОВУ89–92; внутренние прерывания119–120; внешние129;

как требует книга; искусственная упаковка PSW/RUU из SIMH не копируется.

Штатные `monsys.9`, `bemsh.739`, `librar.12`, `librar.37`, `b.7`
используются текущим hosted-контуром. Название образа не доказывает
готовность аппаратного загрузчика. В закреплённом архиве найден настоящий
bootstrap ДИСПАК и комплект носителей с проверенными SHA. Его активная
генерация достигает готовности в независимом SIMH с 512K. Книжная конфигурация 32K с этим комплектом не подтверждена. В явно
выбранной экспериментальной Simh512K наш CPU выполнил фортранное задание
и следующую операторскую команду; состояние и события original/max совпали.
Функциональный ОС-гейт пройден, приёмка скорости отражается в общем отчёте.

## Функциональный супервизор и выбранные устройства

`ProcessorProfile.Supervisor` включается явно через API. По умолчанию
остаётся Dubna. Обработчики обычных команд и арифметическое устройство
общие; аппаратные отличия деления и округления из этапа 2 этим изменением
не исправляются. Профиль не моделирует предвыборку и перекрытие операций.

```csharp
var machine = new MachineCore(ProcessorProfile.Supervisor);
machine.Cpu.StartAt(0x400);
var result = machine.RunInstructions(1000000, ExecutionSpeed.Max, true);
```

`RunInstructions` использует существующий исполнительный цикл, таблицу
`Besm6Timing` и абсолютные сроки `ExecutionPacer`. Hosted-обработчик
экстракодов не устанавливается. `max` без статистики не считает табличные
такты для ожидания. Скорость не меняет гостевые режимы или очередь событий.
Новый флаг CLI аппаратной точности пока не вводится.

### Команды и управляющее состояние

Источник: [ТО-8, система команд](https://www.besm6.org/doc/БЭСМ6-ТО-IX-описание-системы-команд.pdf),
SHA-256 `7412b2c1c90195e029fe5b0067e859ce6c6f846a780062de8ab6ab4f96b6c113`.
Номера специальных регистров ниже десятичные; номера команд и векторов
в таблице восьмеричные.

| Механизм | Реализованное правило | Источник |
|---|---|---|
| Экстракоды 050–077 | Вектор 00500 + код, левая половина; Э20/Э21 соответствуют Э060/Э061 | §3.55, листы 80–82 |
| Сохранение экстракода | M14 — исполнительный адрес, M26 — следующее слово; A/Y/R сохраняются, модификатор потреблён | §3.55 |
| Внутреннее/внешнее прерывание | Векторы 00500/00501, M27 и признаки в M23 | §6.16, §6.35 |
| Вход в управляющую программу | Установить БлП, БлЗ, БлПр, сохранив остальные признаки M17 | §§6.16, 7.7–7.10 |
| ВЫПР | Три младших бита номера: только 2/3 выбирают M26/M27, остальные дают нулевой математический адрес | §3.60, листы 95–96 |
| Возврат | Восстановить режим, половину, модификатор и только БлП/БлЗ/БлПр; остальные признаки M17 сохранить | §3.60 |
| M17 | Только гостевая запись; незадействованные позиции игнорируются, host-снимок допускается | §§7.7–7.8 |
| ПА/СА00 супервизора | Изменить лишь маску 0x403 | §7.8, лист 135 |
| РЕГ/ОВУ | Раздельные чтение/запись регистров и обращения к устройствам | §§3.56, 3.59 |
| 032/046/047 | В матрежиме недопустимы; в супервизоре 032 — ОВУ, 046/047 используют адрес как константу и номер M | §§3.62–3.64, листы 98–99 |
| STOP | Отдельная кнопка останова; при отключении ПоК выбирает NOP или Э063 | §3.61, лист 97 |

При записи M28 пропускаются четыре последующие успешно завершённые
команды. Это функциональная граница из §6.7, а не модель задержек УУ.
Проверка защиты предшествует проверке адресного совпадения; приоритет
одновременных аппаратных сигналов отдельно книгой не установлен.

Нулевой адрес команды в этом профиле проходит обычную приписку и контроль:
закрытая RP0 даёт защиту команды, открытая страница допускает выборку.
Искусственный запрет Dubna на переход к нулю сохраняется только в Dubna.
Нулевой операнд по-прежнему не обращается к памяти.

`SupervisorSnapshot` наблюдает специальные регистры без добавления
гостевых операций чтения. АвтБ представлен в M17 и сохраняется при
переходах; его полный аппаратный механизм не объявляется реализованным.

### БРЗ и память

Супервизор использует отдельную функциональную границу завершения записи:
заполнение последнего свободного БРЗ публикует старейшую запись, оставляя
не более семи ожидающих публикации значений. Основание — ТО-2, книга 2,
§§4.19–4.20, печатные листы 62–64. Запись адреса перестраивает старшинство
и разрешает передачу следующего БРЗ в МОЗУ. Запросы в полёте — этап 5.

Прежний самостоятельный `MappedMemoryBackend` сохраняет восемь ожидающих
записей. Девять пультовых записей остаются гарантией публикации этой модели.
В settled-границе супервизора восемь пультовых записей публикуют семь БРЗ.

РЕГ0–7 обращаются к стабильным физическим слотам БРЗ, а не к индексам
снимка в порядке MRU. Запись содержимого сохраняет активный адресный тег.
Слоты после публикации сохраняют данные для чтения регистра. Выбор первого
свободного слота при программном старте не является доказанным состоянием
аппаратуры после включения питания.

Гостевая ЗпР меняет RP без автоматического вытеснения БРЗ: программа
обязана выполнить публикацию перед сменой приписки (ТО-8 §4.24, лист 107).
Host `ImportAssignmentGroup` сохраняет прежнюю сериализацию под старой RP.
Текущая конфигурация — 32K; неподдерживаемое расширение RP отклоняется
явно. Это ограничение конфигурации, а не выдуманный гостевой авост.

### Прерывания и жизненный цикл

В функциональном последовательном исполнении внешнее прерывание может
начаться между любыми завершёнными командами, включая половины слова.
Источник не подтверждается автоматически. Отложенные события исполняются
в установленном ранее порядке MachineCore: до следующей команды либо
после её диагностики и обновления счётчиков/часов.

Внутренний сигнал не начисляет тик завершённой инструкции. Состояние A/Y
и побочные изменения индексных регистров сохраняются согласно общим
обработчикам. Позиции M27/M23 для ошибок памяти закреплены таблицей
ТО-8 §6.21, лист 121. Позиция арифметического отказа здесь последовательная;
она не доказывает точный СчАС реального совмещённого АУ/УУ (§6.20).
ПоП/ПоК и БРО могут привести к `SupervisorHaltException` вместо входа
в вектор. Исключения callback остаются `SchedulerCallbackException`.
Они не попадают в обработчик авоста Dubna.

`ResetCpu` сохраняет память, RP/RZ, буферы, часы, очередь, подключение
устройств и настройку кнопки останова. Он возвращает CPU к явно выбранному
программному bootstrap-состоянию. Это не полная аппаратная УН машины.

### Устройства выбранной конфигурации

Протоколы контроллера проверяются по закреплённому исходному
[SIMH BESM6](https://github.com/simh/simh/tree/9e318d16a203a3efae3420ea3f5700a8d7e3bec3/BESM6):
`besm6_disk.c`, `besm6_drum.c`, `besm6_tty.c`, `besm6_printer.c`,
`besm6_punch.c` и диспетчер портов `besm6_cpu.c`.
Это источник функционального протокола выбранных устройств; универсальная
историческая точность всех вариантов контроллеров не предполагается.

Реализованы два направления МБ и КМД, raw50 DMA, служебные слова,
полустраницы/секторы, форматированный рабочий диск 2052, последовательные
телеграфные линии, отдельные консоли, ФС1500 и АЦПУ. DMA обходит RP/RZ
и CPU-буферы, сохраняя контрольные разряды. Подключение устройств явно.

SIMH-образы используют little-endian 64-битные слоты с семантическими
тегами 1/2. Они преобразуются в книжные контрольные разряды по данным;
тег образа не выдаётся за физическую чётность. Неизвестные классы
отклоняются. Образы ОС не включаются в репозиторий.

УВВ0153 в выбранном SIMH-контракте не имеет наблюдаемого действия.
Она сохраняет телеграфные кадры и очередь; полный исторический сигнал
гашения аппаратуры сопряжения не моделируется. Запрос 04115 возвращает ноль только в явной экспериментальной конфигурации
Simh512K, как в закреплённом SIMH; Classical32K отклоняет его.
Неподдержанные магнитные ленты, перфокарты и варианты обмена отклоняются.
Функциональные `CompletionDelayTicks`, периоды таймера/serial и АЦПУ
не являются аппаратными задержками. Их уточнение относится к этапу 5.

### ОС-гейт

`tools/stage4_boot_probe.py` проверяет SHA исходников и носителей,
загружает настоящий bootstrap и собирает диагностику обмена. Hosted
экстракоды не устанавливаются. Успех требует реального приглашения ОС,
выполненного гостевого задания и совпадения original/max; отсутствие
любой части оставляет гейт непройденным.

В выбранном pinned-комплекте ДИСПАК проверка памяти/МБ проходит после
введения границы БРЗ. Затем 32K-контур отклоняет расширенную запись RP
в цикле определения памяти. Независимый SIMH с 32/64/128/256K останавливается
по контролю команды; с 512K достигает операторской готовности. Это
наблюдение данного комплекта, а не доказательство аппаратной геометрии.
В явно выбранной Simh512K наш CPU выполнил фортранное задание: девять
контрольных значений, напечатанный конец задачи и ответ ОС на следующую
команду подтверждены. Original/max совпали по итоговому SHA256 состояния,
инструкциям, тактам и истории обмена. Книжная Classical32K не объявляется
совместимой с этим комплектом. Приёмка производительности описывается отдельно.

### Источники генерации и граница памяти

Выбранный комплект закреплён по ревизиям SIMH и архива носителей;
URL, размеры и SHA256 перечислены в
[`reports/supervisor/supervisor-source-audit.json`](../reports/supervisor/supervisor-source-audit.json).
Наличие текста старой генерации внутри образа не подтверждает, что загрузчик
исполняет именно эту генерацию.

[Каталог генераций СЕРП](https://github.com/besm6/dispak/blob/f21ea8780dad397b436151f2328ead4f8e617494/tests/serp-gens-ogl/output.txt)
показывает варианты М1В1, М2В1 и М3В1–М3В4 с параметром `ОЗУ 512К`.
Это закреплённый результат программы в пользовательском эмуляторе ДИСПАК:
он подтверждает содержимое каталога, но не аппаратную разводку памяти,
разрядное представление расширенных RP или успешный запуск этих вариантов
на исторической машине. Применимость каталога к конкретному образу требует
сопоставления его данных; одинаковое имя пакета само по себе недостаточно.

Статья участников разработки в
[SORUCOM-2023](https://www.computer-museum.ru/document/trudy_sorucom_2023.pdf),
печатная страница 46, сообщает о последующем расширении физической памяти
БЭСМ-6 до 128 страниц. Она не задаёт схему расширенных RP и банков и потому
не заменяет техническую спецификацию. Книга
[«Оперативная память ЭЦВМ БЭСМ-6», 1969](https://github.com/besm6/besm6.github.io/blob/c30c14eb7bb7d56de477c8aaa3c1d6be9d10a320/doc/%D0%9E%D0%BF%D0%B5%D1%80%D0%B0%D1%82%D0%B8%D0%B2%D0%BD%D0%B0%D1%8F-%D0%BF%D0%B0%D0%BC%D1%8F%D1%82%D1%8C-%D0%AD%D0%A6%D0%92%D0%9C-%D0%91%D0%AD%D0%A1%D0%9C6.pdf)
описывает отдельный МОЗУ на 4K 52-разрядных слов; её аннотация также
не является спецификацией расширения адресного пространства до 512K.

Для нынешнего книжного профиля сохраняются 32K и отклонение неподдержанных
разрядов RP. Расширение геометрии требует отдельного выбора конфигурации,
источника с точными правилами и независимых контрольных векторов.
Изменение загрузочных данных или гостевых признаков ради прохождения
проверки ОС не считается подтверждением совместимости.

### Явная экспериментальная конфигурация SIMH

Расширение для проверки выбранного комплекта ОС включается отдельным
параметром API. Все прежние конструкторы сохраняют `Classical32K`.

```csharp
var machine = new MachineCore(
    ProcessorProfile.Supervisor, MemoryConfiguration.Simh512K);
var physicalWords = machine.MappedMemory!.PhysicalMemory.CapacityWords;
```

`Simh512K` предоставляет 524288 физических слов и 512 физических страниц.
Математические адреса и теги запросов остаются 15-разрядными, RP отображает
32 математические страницы в выбранные физические страницы. Загрузочная
физическая `HostMemory` проверяет границы по выбранной ёмкости; нулевой
гостевой операнд, защита, публикация БРЗ и инвалидирование БРС сохраняются.

Правило расширенного RP закреплено по
[SIMH `mmu_setrp`](https://github.com/simh/simh/blob/9e318d16a203a3efae3420ea3f5700a8d7e3bec3/BESM6/besm6_mmu.c#L691):
четыре младших пятиразрядных поля берутся из разрядов 1–20 аккумулятора,
следующие разряды страниц чередуются в позициях 29–48. Маска ёмкости 511
оставляет девять разрядов номера страницы; десятый закодированный разряд
игнорируется в этой явно выбранной конфигурации. `Classical32K` продолжает
отклонять неподдержанные шестые разряды.

Это экспериментальная совместимость с закреплённым программным контрактом
SIMH. Она не объявляет историческими геометрию банков, задержки памяти
или расширенные управляющие схемы. Статические `PhysicalMemory.GetBank`
и `GetBankOffset` сохраняют прежнюю область 32K; для расширенной ёмкости
аппаратная банковая адресация не задаётся.

Проверка этого комплекта использует `tools/stage4_boot_probe.py` с параметром
`--memory-configuration Simh512K`; выбор фиксируется в отчёте. Само наличие
расширенной памяти не означает прохождения ОС-гейта.

### Проверенный запуск и жизненный цикл

`RunInstructions` использует общий исполнитель и pacing, не устанавливая
hosted-экстракоды. В Supervisor лимит также ограничивает попытки шага:
повторная ошибка обработчика не создаёт бесконечного запуска при нулевом
числе успешно завершённых команд. Неуспешный шаг не добавляет тик и счётчик.
При завершении снимаются только подписки данного запуска; hooks, изменённые
callback, сохраняются.

В ОС-проверке выполняется настоящий bootstrap без подмены гостевых
регистров или DATE/YEAR. Сохраняется дата образа, время задаётся операторской
командой ВРЕ. Ограничение 180 миллионов попыток завершает диагностический
запуск после выполненного задания; STOP ОС не требуется.

Общий SHA состояния включает CPU, RP/RZ, всю физическую память raw50,
БРС/БРЗ, изменённые носители, часы, ближайшее событие и историю I/O.
При 179999977 завершённых командах и 351503298 модельных тактах оба режима
дали SHA `13741684af90f6f230be2394cb7a1940e67aa70464823bb8f1ade07dbee84a0c`.
Диагностический запуск с hook на каждой команде занял 65.69 с в max и
65.30 с в original при модельных 35,15 с: хост здесь не выдержал темп.
Это проверка функциональности и порядка событий, не аппаратного времени.

Периоды АЦПУ задаются отдельно `PrinterPulseTicks` и `PrinterZeroTicks`;
по умолчанию используют прежний `CompletionDelayTicks`. Медленный таймер
включается явно и выдаёт свой сигнал каждый четвёртый основной импульс.
Повторное включение ФС не переносит уже назначенный срок. Пустой выбор
диска снимает подключение без изменения сигналов; KMD006 имеет указанное
в SIMH отсутствие наблюдаемого действия, не имитирует неизвестный компаратор.
`IsSerialIdle` предоставляет состояние кадра и очереди для оператора.
