# Ядро монитора MONSYS: восстановленный код и устройство

**Дата:** 27.09.2026
**Источник:** снимок работающей ОС, снят с эмулятора (`--dump-mem-at 300000`)
**Инструмент:** `tools/besm6kernel.py`

В отличие от `docs/ose-tape-decompilation.md`, где картировались ленты, здесь
получен **исполняемый код ядра** и разобрано, как оно устроено.

---

## 1. Как получено

```bash
dotnet src/Besm6.Cli/bin/Release/net8.0/besm6.dll run examples/copy.dub \
     --limit 400000 --dump-mem /tmp/kernel.img \
     --dump-mem-at 300000 --trace-regs /tmp/trace.txt

python3 tools/besm6kernel.py structure /tmp/kernel.img /tmp/trace.txt
python3 tools/besm6kernel.py listing  /tmp/kernel.img /tmp/trace.txt \
     --start 0o76000 --count 1023 > docs/monsys-kernel.listing.txt
```

Трасса даёт **точный** следующий `K` после каждой команды. Это принципиально:
статически восстановить поток управления нельзя (раздел 2), по трассе — можно.

## 2. Две архитектурные особенности, из-за которых нужна трасса

**(а) Две команды в одном слове.** 48-битное слово = два 24-битных полуслова.
Если левая команда передаёт управление, правая **не исполняется вовсе**, но
остаётся возможной целью перехода. Листинг «две мнемоники на строку» вводит
в заблуждение: вторая может быть мёртвой.

**(б) Регистр C — одноразовый модификатор адреса.** После `utc`/`wtc` значение C
прибавляется к адресному полю **ровно следующей** команды, после чего признак
`ApplyC` сбрасывается (`InstructionExecutor.FinalizeInstruction`:
`if (frame.NextC != 0) { C = NextC; ApplyC = true; } else { ApplyC = false; }`).

Отсюда: **ядро позиционно-независимо** — все внутренние ссылки записаны как
смещения относительно базы. Статически «увидеть» цель перехода нельзя, нужно
знать C в каждой точке. В трассе C выводится явно (`C = 01614`, сброс — `Clear C`).

**Нумерация регистров.** Мнемоники печатают номер регистра **восьмеричным**
(`(16)` = M[14] = регистр обмена, `(17)` = M[15] = стек). То же в трассе:
`M17` = M[15], `M12` = M[10].

## 4. Точки входа

Управление попадает в ядро **извне** ровно дважды за прогон, оба раза одним
путём: `K=0o00542` → `0o76002`.

```
шаг 167361 -> 0o76002  wtc 17
шаг 246353 -> 0o76002  wtc 17
```

Первая же команда ядра — `wtc 17` (загрузить базу), что подтверждает пункт 2б:
ядро начинается с установки собственного адреса.

`0o76000` — второй, холодный вход: достигается только из `0o76673` (`uj`),
2 раза за прогон. Похоже на обработчик ловушки/вектора.

## 5. Соглашение о вызовах

Обратный адрес хранится **в индексном регистре, а не в стеке** — это следует из
семантики `vjm`: `m[reg] = frame.NextK; Branch(addr)`.

| Регистр | Назначение | Наблюдения |
|---|---|---|
| M(16) = M[14] | основной регистр обратного адреса | большинство вызовов; `uj (16)` 2555 раз |
| M(6) | второй уровень вложенности | `vjm ...(6)` 3347; `uj (6)` 1982 раз |
| M(7) | третий уровень | `uj (7)` 1038 раз (только из `0o77001`) |
| M(11), M(0) | эпизодически | 180 и 67 раз |
| M(17) = M[15] | стек | 28 699 изменений за прогон |

Возврат: `uj` с пустым адресным полем и индексным регистром — `uj (16)`.

Три уровня регистров возврата — типичная схема для вложенных вызовов без
аппаратного стека. `0o77000–0o77001` (`stx, atx (16)` / `stx, uj (7)`) —
сохранить и восстановить M(7); это самая частая точка входа во «внешний» слой
ядра (2076 попаданий).

## 7. Горячее ядро

### 7.1 Цикл ожидания `0o77661–0o77662`

```
077661   ita,      utc (4)         ; A := M(0);  C := M(4)
077662   atx (2),  vlm 77661(4)    ; Mem[M(2)+C] := A;  M(4)++;  loop
```

17120 исполнений каждого слова, 8560 переходов назад. Состояние при входе:
`M(4) = 0o77615`, `C = 0o77615`.

Цикл крутится, пока `M(4) != 0`, каждый раз **инкрементируя** его, то есть
считает `32768 − M(4)` итераций (около 115 при M(4)=0o77615). Побочно каждый
проход пишет A по адресу `C + M[2]`.

Это **задержка/ожидание**, а не вычисление: длительность задаётся M(4).

> Расхождение с учебником: `book/03-instruction-set.md` утверждает для `ЦИКЛ`
> `M--`, но реализация в `ControlInstructionExecutor` делает `m[reg] + 1`.
> Проверено на трассе: M(4) растёт. Для БЭСМ-6 верно второе.

### 7.2 `0o77613` — самая частая подпрограмма

```
077613   ati 5,  asn 112   ; A := M(5); сдвиг по адресу 112
077614   ati 1,  uj 77273(1)
```

6694 исполнения; за вызов уходит в `0o77273` → `0o77345`/`0o77355` → `0o77002`.

### 7.3 Внешний слой `0o77000–0o77001`

```
077000   stx,  atx (16)    ; 2076 попаданий — вход
077001   stx,  uj (7)      ; возврат через M(7)
```

## 8. Таблицы данных

432 слова ядра не исполнялись ни разу. Крупные блоки:

| Диапазон | Слов | Содержание |
|---|---:|---|
| `0o77600–0o77606` | 7 | указатели: `0o76234`, `0o104000`, `0o104204`, `0o104132`, `0o5071`, `3`, `0o16` |
| `0o77610–0o77612` | 3 | константы/флаги |
| `0o77357–0o77557` | 129 | самый большой блок, в этом прогоне не использовался |
| `0o77700–0o77756` | ~40 | хвост таблиц |

Наиболее цитируемые адреса из кода ядра: `0o77421` (28 раз), `0o77420` (16),
`0o77616` (13), `0o77610` (11), `0o77607` (10), `0o77567` (9).

Пример: `0o76316–0o76320` — процедура, которая **заполняет таблицу по ссылке**:

```
076316   ita 16,    atx 77600    ; M(16) → ячейка 0o77600
076317   xta 77510, atx 77601
076320   xta 77567, atx 77602
```

то есть `0o77600` — не код, а рабочая таблица, заполняемая при старте.

## 9. Системные вызовы из ядра

| Экстракод | Вызовов | Смысл |
|---|---:|---|
| `*75` | 440 | запись аккумулятора в память |
| `*70` | 15 | обмен с диском/барабаном |

Прочие экстракоды не используются: ядро почти не зависит от обработчиков
симулятора, что согласуется с ролью супервизора.

## 10. Полный листинг

`docs/monsys-kernel.listing.txt` — 1023 строки, весь диапазон с аннотациями:

```
адрес  счётчик  слово             дизассемблирование        роли
076002      16  230001772477770   wtc 17,vtm -10(16)         LC=8
076012      32  7377601100370003   vlm 76011(16),ntr 3        Lloop=28
077661   17120  42000022200000     ita,utc (4)                RC=8560
```

Пустой счётчик = слово в этом прогоне не исполнялось (данные или холодный код).
`L`/`R` — левое/правое полуслово; `jmp`/`call`/`jz`/`jnz`/`loop` — роль команды;
`C` — установка базы; `E75` — экстракод; число после роли — сколько раз.
Воспроизводится командой из раздела 1.

## 11. Границы достоверности

- **Проверено измерением:** расположение ядра, точки входа, соглашение о
  вызовах, карта подпрограмм и их частота, содержимое таблиц, поведение цикла
  ожидания, экстракоды. Всё получено из трассы и образа, а не угадано.
- **Интерпретация (не факт):** назначение подпрограмм по мнемоникам
  («похоже на построение таблицы»), отождествление `0o76000` как обработчика
  ловушки (основано лишь на том, что туда прыгают 2 раза), вывод о трёх
  уровнях вложенности.
- **Не сделано:** автоматическое восстановление управляющих конструкций и имён
  переменных; разбор подпрограмм в псевдокод; сопоставление символьных имён
  (в образе их нет — только адреса).
- **Выборка:** структура снята с одного задания (`examples/copy.dub`,
  339 161 команда). Холодные ветви, не покрытые этим прогоном, в карте
  подпрограмм отсутствуют — их больше 432 неисполнённых слов.
