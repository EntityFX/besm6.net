### Типичный цикл работы

```bash
# 1. снять снимок работающей ОС и трасс
dotnet src/Besm6.Cli/bin/Release/net8.0/besm6.dll run examples/copy.dub \
     --limit 400000 --dump-mem /tmp/kernel.img \
     --dump-mem-at 300000 --trace-regs /tmp/trace.txt

# 2. карта ядра
python3 tools/besm6kernel.py structure /tmp/kernel.img /tmp/trace.txt

# 3. псевдокод всего ядра или одной подпрограммы
python3 tools/besm6decomp.py /tmp/kernel.img /tmp/trace.txt
python3 tools/besm6decomp.py /tmp/kernel.img /tmp/trace.txt --routine 0o77661

# 4. собрать корпус по всем заданиям
python3 tools/besm6harvest.py --out /tmp/harvest <список .dub>
python3 tools/besm6corpus.py /tmp/harvest --json /tmp/corpus.json
```

### Три особенности, без которых анализ врёт

1. **Регистр C одноразовый.** После `utc`/`wtc` база действует ровно на одну
   следующую команду. Ядро позиционно-независимо, статически цели переходов
   не восстанавливаются — нужна трасса.
2. **Две команды в одном слове.** Если левая передаёт управление, правая не
   исполняется. «Две мнемоники на строку» — иллюзия.
3. **Правила адресации у команд разные.** `uj`/`uza`/`u1a` идут по
   `адрес + M[i]`, а `vjm`/`vzm`/`v1m`/`vlm` — по голому адресу.

Плюс: номера индексных регистров всюду **восьмеричные** (`(16)` = M[14]),
в трассе `M17` = M[15] = стек.

## Дизассемблирование лент ОС «Дубна» на БЭСМ-6

**Дата:** 27.09.2026
**Предмет:** разбор образов ОС и системных лент из `tapes/`, восстановление и
дизассемблирование исполняемого кода монитора MONSYS.

---

### 1. Инвентарь лент

| Файл | Слов | Зон (1024) | Содержание |
|---|---:|---:|---|
| `monsys.9` | 294 912 | 288 | ОС «Дубна», лента 011 oct |
| `librar.12` | 327 680 | 320 | CERNlib lib1, 012 oct |
| `librar.37` | 434 176 | 424 | CERNlib lib2, 037 oct |
| `bemsh.739` | 28 672 | 28 | DISPAC/BEMSH, 0331 oct |
| `b.7` | 23 552 | 23 | Компилятор B (FORTRAN), 007 oct |

Формат — SIMH: 6 байт на 48-битное слово, big-endian (`TapeImage.cs`).

### 2. Инструменты

#### 2.1. `tools/besm6tape.py` — дизассемблер

Разбирает образ в слова, дизассемблирует в мнемоники MADLEN или БЭМШ,
декодирует текст (ASCII и GOST-10859), показывает карту зон и ищет строки.

Команды: `info`, `dis`, `text`, `strings`, `zones`.

Таблицы мнемоник и разбор полуслов взяты из `OpcodeTable.cs` и
`InstructionCodec.cs`, то есть дизассемблер совпадает с эталонным.

**Верификация:** 300 случайных слов со всех пяти лент прогнаны через
эталонный дизассемблер `besm6 disasm` — **0 расхождений**.

#### 2.2. `--dump-mem` в `besm6 run`

В `RunCommand` добавлены ключи:

- `--dump-mem FILE` — дамп ОЗУ после прогона (SIMH, 6 байт на слово);
- `--dump-mem-at N` — снимок после N инструкций.

Второй ключ необходим: к концу задания монитор затирает собственный образ,
и дамп «после» содержит пустоту вместо кода ядра.

`--dump-mem-at` совместим с `--profile`: оба ключа подписываются на один и тот же
хук `Processor.InstructionTrace`, и наблюдатели вызываются оба. Это проверено
тестом `MemoryDumpTraceHookTests` в `tests/Besm6.Cli.Tests/`: снимок с `--profile`
побайтово совпадает со снимком без него.

### 3. Как ленты используются эмулятором

Отдельного ленточного экстракода в модели нет: ленты смонтированы как
**диски**, зона = 1024 слова. Чтение идёт через E70:

```
memAddr = (page << 10) + (sectIo ? paragraph << 8 : 0)
tape offset = 1024 * diskZone + 256 * sector
diskZone = tract + (drum - mappedDrum) * 32
nwords = sectIo ? 256 : 1024
```

То есть содержимое ленты — это фактически образ памяти, разложенный по зонам.

Загрузка ОС выполняется бутстрапом `MonsysBootstrapper`: 12 команд
по адресам 1032–1043 Decimal, которые читают монитор с ленты через барабан
и передают ему управление. Код бутстрапа не лежит на ленте, а задан
непосредственно в симуляторе (порт `dubna/machine.cpp`).

### 4. Метод восстановления

1. Прогнать задание с `BESM6_TRACE=1` → `ec_trace.log` с полным списком E70.
2. Снять снимок памяти: `--dump-mem-at 300000` (момент, когда ядро уже в памяти).
3. Дизассемблировать снимок.

**Проверка снимка:** 14 адресов, реально исполнявшихся по `--trace`,
сверены с содержимым дампа — **14 из 14 совпали**. Снимок достоверен.

### 5. Что найдено в коде

|---|---:|---|
| `0o00000–0o05777` | ~1200 | низкая память: обработчик команд, драйверы |
| `0o10000–0o12777` | 61 | программа-монитор |
| `0o22000–0o27777` | ~3000 | сервисы ОС |
| `0o33000–0o45777` | ~4000 | горячий код: **46 % времени** в зоне `0o34000` |
| `0o53000–0o53777` | 234 | таблицы |
| `0o76000–0o77557` | **880** | **ядро монитора (супервизор)** |

#### 5.2. Профиль исполнения

#### 5.3. Ядро монитора

880 слов по `0o76000–0o77557`. Дизассемблированный фрагмент:

```
077000  stx,atx (5)              ; XT — сохранить РР в M[]
077001  stx,uj (7)               ; переход
077002  ita 16,its 2             ; ИТР/ИТС — работа с индексными регистрами
077004  a-x 77507,u1a 77123      ; арифметика, унитарная операция
077006  vjm 77160(16),utc        ; векторный переход
077010  aax 77473,x-a 77610      ; AAX — обращение к макросу по 0o77473
077012  *75 77273(1),utc         ; экстракод 075 — запись с проверкой
```

Характерны для кода супервизора: `vjm`/`utc`/`vtm` для переходов,
`ita`/`its` для индексных регистров, `aax` для вызова макросов,
`uza`/`u1a`/`utm` для арифметики, экстракоды `*75` для записи в память
с контрольными разрядами.

### 6. Текст на лентах

#### 6.1. `monsys.9` — диагностика ОС (GOST-10859, читается как латиница)

```
СБОЙ МАШИНЫ: ОШИБКА ВЫЧИСЛИТЕЛЯ: ОБОЗНАЧЕНИЕ ОТСУТСТВУЕТ В ДИАГНОСТИКЕ
СБОЙ МАШИНЫ: ОШИБКА ПРИ ВЫПОЛНЕНИИ ПСЕВДОКОМАНДЫ СИСТЕМЫ B ФАЙЛОВ
ВЫПОЛНЯЕТСЯ ВЫБОР ДОПУСТИМЫХ ПАРАМЕТРОВ
```

Извлекаются и служебные сообщения, например про обработку `COMMON`,
`DATA`/`EQUIV`, `END` и неверный оператор.

#### 6.2. `b.7` — компилятор B (FORTRAN)

```
B COMPILER FOR BESM-6, VERSION 04/20
COMPILED %D LINES OF CODE, FOUND %D ERRORS
UNBALANCED PARENTHESES IN EXPRESSION
*CALL OVERLAY: 66020
```

#### 6.3. `librar.12` / `librar.37` — исходники CERNlib

```
( 5X,'CONVERGENCE IS TOO SLOW, CHANGE  R'//)
(1X'GAMMA ... ARGUMENT IS NON-POSITIVE INTEGER = 'E20.5)
(1X'CDIGAM ... ARGUMENT IS NON-POSITIVE INTEGER = 'F20.2)
```

Это готовые тексты на Фортране с операторами FORMAT — подтверждение,
что ленты хранят исходники, а не только объектный код.

### 7. Выводы

1. Ленты ОС «Дубна» **не содержат отдельного формата загрузчика** в модели
   симулятора: они разложены по зонам и читаются как диски, а код бутстрапа
   задан в симуляторе отдельно.
2. Ядро монитора компактно — **880 слов** — и сосредоточено в верхних
   адресах `0o76000–0o77557`; это типичная организация супервизора:
   маленькое ядро в защищённой зоне, сервисы и обработчики — ниже.
3. Текст на лентах читается без дополнительных таблиц: GOST-10859
   в диапазоне кириллицы совпадает с ASCII-латиницей, поэтому
   русские сообщения видны как транслитерация.
4. Дамп памяти **во время исполнения** — единственный надёжный источник
   кода ядра; дамп после прогона бесполезен, так как монитор затирает память.

### 9. Ограничения

- Выполнена статическая дизассемблировка и картирование, но **не полная
  декомпиляция**: автоматического восстановления управляющих конструкций
  и имен локальных переменных здесь нет.
- Проверка достоверности снимка выполнена на 14 адресах; более широкой
  автоматической сверки не проводилось.
- Ленты `librar.12`/`librar.37` содержат в основном исходники Фортрана,
  а не машинный код; дизассемблирование к ним неприменимо.
- Соответствие между зонами ленты и адресами памяти выведено из
  реализации E70; при изменении модели симулятора вывод потребует пересмотра.

## Ядро монитора MONSYS: восстановленный код и устройство

**Дата:** 27.09.2026
**Источник:** снимок работающей ОС, снят с эмулятора (`--dump-mem-at 300000`)
**Инструмент:** `tools/besm6kernel.py`

В отличие от `docs/ose-dubna.md`, где картировались ленты, здесь
получен **исполняемый код ядра** и разобрано, как оно устроено.

---

### 1. Как получено

```bash
dotnet src/Besm6.Cli/bin/Release/net8.0/besm6.dll run examples/copy.dub \
     --limit 400000 --dump-mem /tmp/kernel.img \
     --dump-mem-at 300000 --trace-regs /tmp/trace.txt

python3 tools/besm6kernel.py structure /tmp/kernel.img /tmp/trace.txt
python3 tools/besm6kernel.py listing  /tmp/kernel.img /tmp/trace.txt \
     --start 0o76000 --count 1023 > docs/monsys-kernel.listing.txt
```

Трасса даёт **точный** следующий `K` после каждой команды. Это принципиально:
статически восстановить поток управления нельзя (раздел 2), по трассе — можно.

### 2. Две архитектурные особенности, из-за которых нужна трасса

**(а) Две команды в одном слове.** 48-битное слово = два 24-битных полуслова.
Если левая команда передаёт управление, правая **не исполняется вовсе**, но
остаётся возможной целью перехода. Листинг «две мнемоники на строку» вводит
в заблуждение: вторая может быть мёртвой.

**(б) Регистр C — одноразовый модификатор адреса.** После `utc`/`wtc` значение C
прибавляется к адресному полю **ровно следующей** команды, после чего признак
`ApplyC` сбрасывается (`InstructionExecutor.FinalizeInstruction`:
`if (frame.NextC != 0) { C = NextC; ApplyC = true; } else { ApplyC = false; }`).

Отсюда: **ядро позиционно-независимо** — все внутренние ссылки записаны как
смещения относительно базы. Статически «увидеть» цель перехода нельзя, нужно
знать C в каждой точке. В трассе C выводится явно (`C = 01614`, сброс — `Clear C`).

**Нумерация регистров.** Мнемоники печатают номер регистра **восьмеричным**
(`(16)` = M[14] = регистр обмена, `(17)` = M[15] = стек). То же в трассе:
`M17` = M[15], `M12` = M[10].

### 3. География

| Параметр | Значение |
|---|---|
| Диапазон | `0o76000–0o77756` |
| Ненулевых слов | 948 (в т.ч. 880 в `0o76000–0o77557`) |
| Исполнялось в прогоне `copy.dub` | 516 слов |
| Доля времени прогона | **46.3 %** (156 969 из 339 162 команд) |
| Подпрограмм (целей `vjm`) | 20 |

Ядро — самая горячая часть системы: половина всех исполненных команд приходится
на 948 слов.

### 4. Точки входа

Управление попадает в ядро **извне** ровно дважды за прогон, оба раза одним
путём: `K=0o00542` → `0o76002`.

```
шаг 167361 -> 0o76002  wtc 17
шаг 246353 -> 0o76002  wtc 17
```

Первая же команда ядра — `wtc 17` (загрузить базу), что подтверждает пункт 2б:
ядро начинается с установки собственного адреса.

`0o76000` — второй, холодный вход: достигается только из `0o76673` (`uj`),
2 раза за прогон. Похоже на обработчик ловушки/вектора.

### 5. Соглашение о вызовах

Обратный адрес хранится **в индексном регистре, а не в стеке** — это следует из
семантики `vjm`: `m[reg] = frame.NextK; Branch(addr)`.

| Регистр | Назначение | Наблюдения |
|---|---|---|
| M(16) = M[14] | основной регистр обратного адреса | большинство вызовов; `uj (16)` 2555 раз |
| M(6) | второй уровень вложенности | `vjm ...(6)` 3347; `uj (6)` 1982 раз |
| M(7) | третий уровень | `uj (7)` 1038 раз (только из `0o77001`) |
| M(11), M(0) | эпизодически | 180 и 67 раз |
| M(17) = M[15] | стек | 28 699 изменений за прогон |

Возврат: `uj` с пустым адресным полем и индексным регистром — `uj (16)`.

Три уровня регистров возврата — типичная схема для вложенных вызовов без
аппаратного стека. `0o77000–0o77001` (`stx, atx (16)` / `stx, uj (7)`) —
сохранить и восстановить M(7); это самая частая точка входа во «внешний» слой
ядра (2076 попаданий).

### 7. Горячее ядро

#### 7.1 Цикл ожидания `0o77661–0o77662`

```
077661   ita,      utc (4)         ; A := M(0);  C := M(4)
077662   atx (2),  vlm 77661(4)    ; Mem[M(2)+C] := A;  M(4)++;  loop
```

17120 исполнений каждого слова, 8560 переходов назад. Состояние при входе:
`M(4) = 0o77615`, `C = 0o77615`.

Цикл крутится, пока `M(4) != 0`, каждый раз **инкрементируя** его, то есть
считает `32768 − M(4)` итераций (около 115 при M(4)=0o77615). Побочно каждый
проход пишет A по адресу `C + M[2]`.

Это **задержка/ожидание**, а не вычисление: длительность задаётся M(4).

> Расхождение с учебником: `book/03-instruction-set.md` утверждает для `ЦИКЛ`
> `M--`, но реализация в `ControlInstructionExecutor` делает `m[reg] + 1`.
> Проверено на трассе: M(4) растёт. Для БЭСМ-6 верно второе.

#### 7.2 `0o77613` — самая частая подпрограмма

```
077613   ati 5,  asn 112   ; A := M(5); сдвиг по адресу 112
077614   ati 1,  uj 77273(1)
```

6694 исполнения; за вызов уходит в `0o77273` → `0o77345`/`0o77355` → `0o77002`.

#### 7.3 Внешний слой `0o77000–0o77001`

```
077000   stx,  atx (16)    ; 2076 попаданий — вход
077001   stx,  uj (7)      ; возврат через M(7)
```

## Высокоуровневый листинг ядра MONSYS и устройство ОС

**Дата:** 27.09.2026
**Инструменты:** `tools/besm6decomp.py` (декомпиляция), `tools/besm6kernel.py` (анализ)
**Артефакт:** `docs/monsys-kernel.hl.txt` — 385 строк, точка входа + 20 подпрограмм

Продолжение `docs/ose-dubna.md`: там — карта и аннотированный машинный
листинг, здесь **структурированный псевдокод** и **описание ОС как системы**.

---

### 1. Как получено

```bash
dotnet src/Besm6.Cli/bin/Release/net8.0/besm6.dll run examples/copy.dub \
     --limit 400000 --dump-mem /tmp/kernel.img \
     --dump-mem-at 300000 --trace-regs /tmp/trace.txt

python3 tools/besm6decomp.py /tmp/kernel.img /tmp/trace.txt > docs/monsys-kernel.hl.txt
python3 tools/besm6decomp.py /tmp/kernel.img /tmp/trace.txt --routine 0o77661
```

Декомпиляция трассовая: базовые блоки строятся по **наблюдаемым** переходам,
а не разбираются статически. Причина принципиальная — адресное поле команд
модифицируется базой C, статически цели переходов не восстанавливаются.

### 2. Соглашения реконструкции

| Обозначение | Смысл | Основание |
|---|---|---|
| `A`, `E`, `Y`, `R`, `C` | аккумулятор, порядок, младшие разряды, режим, база | `ProcessorState` |
| `sp` = M(17) | указатель стека (M[15]) | 28 699 изменений за прогон |
| `link` = M(16) | основной обратный адрес (M[14]) | `vjm ...(16)` + `uj (16)` |
| `link2` = M(6), `link3` = M(7) | обратные адреса 2-го и 3-го уровня | `uj (6)`, `uj (7)` |
| `ptr` = M(0) | признак/указатель байта | обнуляется `vtm`/`vjm` |
| `m1..m14` | прочие индексные регистры — локальные переменные | остаток |
| `*` | терминатор блока | — |
| `/* CALL … */` | вызов подпрограммы, адрес возврата — в `link*` | `vjm` |

**Номера регистров восьмеричные** — как их печатает дизассемблер: `(16)` = M[14].

### 3. Точка входа: инициализация супервизора

```
; ТОЧКА ВХОДА (адрес 0o76002)
0o76002 wtc 17             C = M[0o17]       ; МОД: загрузить базу ядра
0o76002 vtm -10(16)        link = 0o1665
0o76003 atx (16)           0o1604 = A
0o76003 xta 16             A = 0o16
0o76004 atx 1(16)          0o1605 = A
0o76004 xta 51             A = 0o51
0o76005 atx 67             0o67 = A
0o76005 xta (16)           A = 0o1604
0o76006 atx (17)           0o53402 = A
0o76006 rte 177            E = R
0o76007 atx 14             0o14 = A
0o76007 ita 16             A = ptr
0o76010 atx 13             0o13 = A
0o76010 vtm -14(16)        link = 0o1570
do {                                            ; цикл заполнения таблицы
    0o76011 ita 15(16)         A = link
    0o76011 atx 35(16)         0o21 = A
    do { 0o76012 vlm 76011(16) } while (0o76011);
```

Читается как `main()` супервизора:

1. **`wtc 17`** — загрузить собственный базовый адрес из памяти. Ядро
   позиционно-независимо: вся дальнейшая адресация относительна к C.
2. **Копирование трёх системных ячеек** (`0o16`, `0o51`, `0o67`) в таблицу
   монитора по адресам `0o1604`, `0o1605`, `0o53402` — перенос состояния
   в рабочую область ОС.
3. **`rte 177`** — выдача регистра режима (признак ловушки/ошибки).
4. **Цикл `0o76011–0o76012`** — заполнение области `0o1570+` значениями с
   шагом 1 (регистр `link` инкрементируется, пока не обнулится).
   Инициализация таблицы, а не вычисление.

### 4. Диспетчер: ядро обработки запросов

Самая частая подпрограмма — `0o77613` (3347 вызовов, 42 % всех вызовов):

```
; ПОДПРОГРАММА 0o77613 — "передать запрос вниз"
0o77613 ati 5              ptr = A
0o77613 asn 112            A >>= 0o112
0o77614 ati 1              ptr = A
0o77614 uj 77273(1)        goto 0o77273 + M(1)
   ...
0o77273 utm (5)            m5 += 0o2
0o77273 uj (6)             return link2
```

Это **хвост диспетчера**: записать признак, сдвинуть число и уйти на
`0o77273 + M(1)` — обработчик выбирается **значением регистра M(1)**.
Классический вектор прерывания: индекс запроса в M(1), вход в таблицу
через одно сложение.

`0o77273` — общий хвост: `m5 += 2` (счётчик) и возврат. Сюда же диспетчер
возвращается после обработчика.

Цепочка `0o77613 → 0o77273 → 0o77345/0o77355 → 0o77002` — спуск по уровням.

### 5. Цикл ожидания

```
; ПОДПРОГРАММА 0o77661 — задержка
do {   /* цикл: 0o77661 */
    0o77661 ita                A = ptr
    0o77661 utc (4)            C = 0o77615     ; УТА: база на 1 команду
    0o77662 atx (2)            0o1614 = A
    0o77662 vlm 77661(4)       управление
} while (0o77661);   /* ЦИКЛ vlm */
```

17120 исполнений — 46 % команд ядра. `vlm` инкрементирует M(4) и повторяет,
пока тот не обнулится: цикл на `32768 − M(4)` итераций, каждый проход пишет A

### 6. Самомодифицирующийся код — важная находка

Сверка содержимого трассы со снимком (`besm6kernel.py selfmod`):

| | |
|---|---|
| Команд в трассе | 339 162 |
| Не совпало со снимком | **7130 (2.10 %)** |
| Адресов с расхождением | 343 |
| Из них в ядре | `0o77345` (797), `0o77355` (476), `0o77274` (368), `0o77356` (298) |

Все четыре «горячих» адреса — **точки входа диспетчера** (`0o77274` — цель
`uj 77273(1)`). Монитор подменяет содержимое этих слов разными вариантами
trampoline-заглушек. Например, по адресу `0o77345` в трассе встречаются и
`uj 77002`, и `uj (6)` — монитор переписывает вектор перехода на конкретный
адрес.

**Практический вывод:** единственного снимка памяти недостаточно для полного
восстановления — нужны дампы в несколько моментов времени. Структура ядра при
этом устойчива (меняются единицы слов), конкретные цели ветвления — нет.

### 7. Устройство ОС MONSYS (по восстановленному коду)

```
пользовательская программа / компилятор
            │  экстракоды *50–*77 (системные вызовы)
            ▼
┌──────────────────────────────────────────────────────────┐
│ 0o76002  ИНИЦИАЛИЗАЦИЯ: загрузка базы C, копирование       │
│          системных ячеек, заполнение таблиц                │
├──────────────────────────────────────────────────────────┤
│ 0o77613  ДИСПЕТЧЕР: M(1) = номер запроса,                 │
│          переход на 0o77273 + M(1)                        │
│ 0o77273  ХВОСТ: m5 += 2, возврат                          │
├──────────────────────────────────────────────────────────┤
│ 0o76775  ВЫЗОВ ОБРАБОТЧИКА; 0o76247 / 0o76252 —          │
│          две основные ветви (1036 и 1022 вызова)          │
├──────────────────────────────────────────────────────────┤
│ 0o77000  ВНЕШНИЙ СЛОЙ: push/push, переход через link3     │
├──────────────────────────────────────────────────────────┤
│ 0o77661  ЗАДЕРЖКА: цикл на 32768 − M(4)                   │
├──────────────────────────────────────────────────────────┤
│ 0o77600  ТАБЛИЦЫ (данные, не исполняются): указатели,     │
│          флаги; заполняются из 0o76316 при старте         │
└──────────────────────────────────────────────────────────┘
```

Принципы организации, видные прямо в коде:

1. **Позиционная независимость.** Весь код адресуется через базу C; ядро можно
   перенести в другое место ОЗУ, переписав единицы слов.
2. **Регистры вместо стека для вызовов.** Три уровня `link`/`link2`/`link3`
   дают вложенность вызовов без программного стека. Стек M(17) используется
   для данных, а не для адресов возврата.
3. **Вектор прерываний в индексном регистре.** Номер обработчика берётся из
   M(1) и складывается с базой диспетчера — обработка запроса не требует
   поиска, это одно сложение.
4. **Самомодификация горячих точек.** Таблица переходов диспетчера
   переписывается под текущий поток запросов.
5. **Программные задержки.** Ожидание реализовано циклом, а не командой.
6. **Минимальная зависимость от экстракодов.** Только `*75` (запись в память,
   440 вызовов) и `*70` (диск/барабан, 15). Основная логика — в самом ядре.

### 1. Метод

Ленты смонтированы как диски, и все обращения к ним идут через экстракод E70.
При `BESM6_TRACE=1` эмулятор логирует каждое обращение с раскодированным словом
управления — это даёт **точную** карту «зона ленты → адрес ОЗУ»:

```
memAddr   = page << 10  (+ paragraph << 8 при sectIo)
```

(`--dump-mem-at` 100000 / 300000 / 600000) и выбирает тот, где больше всего
ненулевых слов: **момент принципиален** — для `fortran.dub` это 12 626 слов при
N=300000 и всего 8983 при N=600000, потому что монитор к концу задания стирает
собственный образ.

### 8. Ограничения — существенно

1. **Имена нет нигде.** В образах нет символьных имён, только адреса. Все

2. **Ленты не различаются по имени.** Барабаны монтируются динамически через

   ленты. Привязка барабана к образу потребовала бы трассировки E57 — она
   не сделана.
3. **Покрытие — только исполненный код.** Из 10 208 слов компилятора Паскаля

   не прослеживается в прочитанных зонах — есть путь загрузки помимо phys_io,

5. **Самомодификация.** Для ядра измерено 2.10 % команд, исполняющих не тот код,
   что в снимке. Для компиляторов эта доля не измерялась, но механизм тот же —
   значит и здесь снимок не полон.
6. **Два задания не дошли до конца** (`madlen.dub`, `e-2.dub` упёрлись в
   `--limit 3000000`), поэтому их покрытие занижено.

- Снимать несколько снимков за задание и объединять — закроет самомодификацию.
- Гонять задания, реально использующие Алгол, эксфор, РЕФАЛ, `librar.*`:

## Псевдо-C: восстановленный код ОС «Дубна» на уровне языка C

**Дата:** 28.09.2026
**Инструмент:** `tools/besm6decomp.py --lang c`
**Артефакт:** `docs/monsys-kernel.c.txt` — 21 функция, 681 строка

Задача: довести восстановленный код ядра до читаемого C-подобного вида.
Ниже — что получилось, что невозможно в принципе и почему.

---

### 1. Сначала — о формате числа

Прежде чем генерировать код, пришлось закрыть расхождение: учебник
`book/03-instruction-set.md:29-32` описывает формат числа БЭСМ-6 **неверно**.

Учебник утверждает: бит 47 = знак, биты 46–41 = порядок (6 бит, смещение 32),
биты 40–1 = мантисса, бит 0 не используется.

Реализация утверждает иное, и это подтверждено **четырьмя** независимыми местами:

| Источник | Что задаёт |
|---|---|
| `NormalizationAndRounding.cs:111` | `A = (Exp & 0x7F) << 41 \| (Mantissa & BITS41)` |
| `Besm6FloatDecoder.cs:26-28` | `raw = w >> 41`, `exp = raw - 64`, мантисса — знаковые 41 бит |
| `Word48.ToDouble()` | `shifted = (long)(w << 23)`, `ScaleB(shifted, w>>41 - 64 - 63)` |
| `Besm6Math.cs:106`, `MemoryInstructionExecutor.cs:204` | `(exp + 64) << 41`, `(& 0x7F) - 64` |

**Истинный формат:**

```
биты 47–41   смещённый порядок, 7 бит, смещение 64
биты 40–0    знаковая мантисса, 41 бит, масштаб 2^-40
знак         отдельного бита НЕТ — знак несёт мантисса
```

Расхождение не косметическое: при моделировании `double` по учебнику числа
получались бы неверными на порядки. Учебник здесь следует исправить отдельно.

Заодно: `ArchitectureConstants.ExponentBias = 64` объявлена, но **нигде не
используется** — мёртвая константа, совпадающая с правильным значением.

### 2. Что получилось

```c
static void f_0o76002(void)   /* ТОЧКА ВХОДА — инициализация супервизора */
{
    int link;   /* обратный адрес, M(16) */
    int sp;     /* стек данных, M(17) */
    w48 ptr;    /* признак/указатель байта, M(0) */

    C = w48[0o17];            /* МОД: база из памяти, на 1 команду */
    link = 0o1665;
    w48[0o1604] = A;
    A = w48[0o16];            /* забрать системную ячейку 0o16 */
    w48[0o1605] = A;
    A = w48[0o51];
    w48[0o67] = A;
    A = w48[0o1604];
    w48[0o53402] = A;         /* положить в рабочую область ОС */
    E = R;
    w48[0o14] = A;
    A = ptr;
    w48[0o13] = A;
    link = 0o1570;
L_76011:
    for (;;) {                /* заполнение области 0o1570+ */
        A = link;
        w48[0o21] = A;
        if (link == 0) break;
        link++;
        goto L_76011;
    }
}
```

Читается именно как `main()` супервизора: загрузить базу, скопировать три
системные ячейки в рабочие адреса, выдать регистр режима, заполнить таблицу.

Диспетчер и цикл ожидания:

```c
static void f_0o77613(void)   /* вызовов: 3347 */
{
    w48 ptr;  int m1, m5;
    ptr = A;
    A = shr(A, 0o112);        /* сдвиг по адресу */
    ptr = A;
    goto L_77345;            /* уход в обработчик */
...
static void f_0o77661(void)   /* задержка: 46 % команд ядра */
{
    w48 ptr;  int m2, m4;
    for (;;) {
        A = ptr;
        C = 0o77615;         /* УТА: база действует на СЛЕДУЮЩУЮ команду */
        w48[0o1614] = A;
        if (m4 == 0) break;
        m4++;
        goto L_77661;
    }
}
```

### 3. Модель, которую пришлось принять

| Объект C | Реальность БЭСМ-6 |
|---|---|
| `w48` | 48-битное слово: и float, и int (48 бит, доп. код), и 2 команды, и 6 байт текста |
| локальные переменные | индексные регистры M(0)…M(15) — **не память** |
| `link`, `link2`, `link3` | обратные адреса в регистрах; стека вызовов нет вообще |
| `sp` | стек **данных**, не стек вызовов |
| `C` | база, действующая ровно на одну следующую команду |
| `goto` | основной способ перехода: структурных конструкций в ISA нет |

### 4. Почему это не компилируемый C

Не из-за недоделки — из-за архитектуры:

1. **Пословная память.** Байтовой адресации нет, строки и упакованные записи
   идут через эмуляцию указателя на байт в M(0). `char*` не имеет аналога.
2. **Типов нет.** ISA не различает `int` и `double`: `aax` — AND над обоими.
   Тип каждой переменной пришлось бы **изобретать** по контексту.
3. **Нет кадров стека.** `vjm` кладёт адрес возврата в регистр; вложенность
   ограничена тремя уровнями. Соглашение вызова C неприменимо.
4. **Самомодификация 2.10 %.** Код переписывает себе же вектор перехода.
   Статический C такое не выражает в принципе.
5. **Нет имён и границ.** В образе нет ни символьной таблицы, ни имён.

Что можно сделать сверх этого — **дифференциальная реимплементация**: писать
логику на C поверх `Besm6.Runtime` и сверять с эмулятором пошагово. Это даст
исполняемый C, но это переписывание с проверкой, а не восстановление оригинала.

### 6. Ограничения вывода

- **Покрытие — только исполненный код.** Из 948 ненулевых слов ядра

- **Холодные ветви отсутствуют.** В псевдо-C попадает лишь то, что реально
  выполнялось; где разветвление не бралось, стоит только одна ветвь.
- **Невзятые переходы не восстановлены.** `if (m4 == 0) goto L_x;` описывает
  только наблюдавшуюся ветвь.
- **Вложенность циклов в выводе временами избыточна** — обратные рёбра
  помечаются как циклы даже там, где это общий хвост диспетчера.
- **Псевдо-C не компилируется** — в частности, объявления `m1..m14` внутри
  функции отражают регистры, а не переменные C.

## Структурируемость кода ядра: измерено на 14 слитых трассах

**Дата:** 28.09.2026
**Инструмент:** `tools/besm6merge.py`
**Данные:** `docs/kernel-structurability.json`

Вопрос: какая доля кода ядра автоматически переводится в `if`/`while`,
а какая требует `goto`. Ответ измерен, а не предположен — и он **опровергает
более оптимистичную гипотезу**.

### Метод

Граф управления строится по **объединению трасс 14 заданий**: ребро
`(K, half) → next_K` наблюдается, если оно встречалось хотя бы раз. Обход
подпрограммы останавливается на возврате (`uj` с пустым адресным полем) и
не заходит в чужие подпрограммы — иначе в каждую засасывается весь общий
диспетчер.

Петля считается **неразрешимой**, если её заголовок имеет входящее ребро извне
тела петли: такой цикл не представим как `while`, нужен `goto` или
дублирование кода.

### Результат

| | Одна трасса | 14 слитых трасс |
|---|---:|---:|
| Узлов в графе | 516 | **662** |
| Подпрограмм (цели `vjm` + внешние входы) | 21 | **53** |
| Разрешимых в `if`/`while` | 43 % | **42 % (22 из 53)** |

**Покрытие выросло, а структурируемость — нет.** Слияние трасс добавило 29 %
узлов и в 2.6 раза больше подпрограмм, но доля разрешимых осталась прежней.

Значит goto-тяжёлая структура ядра — **свойство кода, а не артефакт
недостаточного покрытия**. Моя более ранняя гипотеза («покрытие трассы
ограничивает структурирование») не подтвердилась.

### Что именно не структурируется

| Подпрограмма | Узлов | Неразрешимых петель |
|---|---:|---:|
| `0o77613` (диспетчер, 3347 вызовов) | 30 | 29 |
| `0o76444` | 32 | 10 |
| `0o76311` | 23 | 4 |

`0o77613` — почти целиком неразрешима: 29 петель из 30 узлов. Это и есть
характерная черта супервизора — единая точка входа с таблицей переходов,
а не набор структурированных функций.

### Сколько реально переносится в структурный C

### Вывод по исходному вопросу

Перевод в «настоящий C с именами» возможен для всех 53 подпрограмм, но:

- **для 31 потребуется `goto`** — и это не дефект генератора, а устройство
  кода;
- **структурный `if`/`while` получится у 5 подпрограмм**;
- оставшиеся 17 разрешимых — слишком мелки, чтобы из них что-то извлечь.

Иными словами: результат будет выглядеть как C **с `goto` внутри функций**, а
не как современный структурный C. Это честный потолок для автоматического
перевода.

Что можно сделать сверх автоматики — ручная реконструкция тех 5 подпрограмм
и переписывание остальных 48 в структурный вид **по смыслу**, а не по
автомату. Это работа для человека, знающего архитектуру, и автоматика здесь
даёт только каркас.

### Границы измерения

- Объединение взято по 14 заданиям; при большем числе разветвлений, не взятых
  ни в одном прогоне, цифры могут сдвинуться — но тренд (покрытие растёт,
  структурируемость нет) устойчив.
- Тела блоков берутся из образа **первой** трассы; при самомодификации (2.10 %
  команд ядра) в разных заданиях содержимое одних и тех же адресов
  расходится. На структуру это не влияет, на текст — да.
- Подпрограммы определены как цели `vjm` плюс адреса входа извне диапазона;
  часть из 53 — внутренние точки диспетчера, а не подпрограммы в смысле
  автора.
