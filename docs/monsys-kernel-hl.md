# Высокоуровневый листинг ядра MONSYS и устройство ОС

**Дата:** 27.09.2026
**Инструменты:** `tools/besm6decomp.py` (декомпиляция), `tools/besm6kernel.py` (анализ)
**Артефакт:** `docs/monsys-kernel.hl.txt` — 385 строк, точка входа + 20 подпрограмм

Продолжение `docs/monsys-kernel.md`: там — карта и аннотированный машинный
листинг, здесь **структурированный псевдокод** и **описание ОС как системы**.

---

## 1. Как получено

```bash
dotnet src/Besm6.Cli/bin/Release/net8.0/besm6.dll run examples/copy.dub \
     --limit 400000 --dump-mem /tmp/kernel.img \
     --dump-mem-at 300000 --trace-regs /tmp/trace.txt

python3 tools/besm6decomp.py /tmp/kernel.img /tmp/trace.txt > docs/monsys-kernel.hl.txt
python3 tools/besm6decomp.py /tmp/kernel.img /tmp/trace.txt --routine 0o77661
```

Декомпиляция трассовая: базовые блоки строятся по **наблюдаемым** переходам,
а не разбираются статически. Причина принципиальная — адресное поле команд
модифицируется базой C, статически цели переходов не восстанавливаются.

## 2. Соглашения реконструкции

| Обозначение | Смысл | Основание |
|---|---|---|
| `A`, `E`, `Y`, `R`, `C` | аккумулятор, порядок, младшие разряды, режим, база | `ProcessorState` |
| `sp` = M(17) | указатель стека (M[15]) | 28 699 изменений за прогон |
| `link` = M(16) | основной обратный адрес (M[14]) | `vjm ...(16)` + `uj (16)` |
| `link2` = M(6), `link3` = M(7) | обратные адреса 2-го и 3-го уровня | `uj (6)`, `uj (7)` |
| `ptr` = M(0) | признак/указатель байта | обнуляется `vtm`/`vjm` |
| `m1..m14` | прочие индексные регистры — локальные переменные | остаток |
| `*` | терминатор блока | — |
| `/* CALL … */` | вызов подпрограммы, адрес возврата — в `link*` | `vjm` |

**Номера регистров восьмеричные** — как их печатает дизассемблер: `(16)` = M[14].

## 3. Точка входа: инициализация супервизора

```
; ТОЧКА ВХОДА (адрес 0o76002)
0o76002 wtc 17             C = M[0o17]       ; МОД: загрузить базу ядра
0o76002 vtm -10(16)        link = 0o1665
0o76003 atx (16)           0o1604 = A
0o76003 xta 16             A = 0o16
0o76004 atx 1(16)          0o1605 = A
0o76004 xta 51             A = 0o51
0o76005 atx 67             0o67 = A
0o76005 xta (16)           A = 0o1604
0o76006 atx (17)           0o53402 = A
0o76006 rte 177            E = R
0o76007 atx 14             0o14 = A
0o76007 ita 16             A = ptr
0o76010 atx 13             0o13 = A
0o76010 vtm -14(16)        link = 0o1570
do {                                            ; цикл заполнения таблицы
    0o76011 ita 15(16)         A = link
    0o76011 atx 35(16)         0o21 = A
    do { 0o76012 vlm 76011(16) } while (0o76011);
```

Читается как `main()` супервизора:

1. **`wtc 17`** — загрузить собственный базовый адрес из памяти. Ядро
   позиционно-независимо: вся дальнейшая адресация относительна к C.
2. **Копирование трёх системных ячеек** (`0o16`, `0o51`, `0o67`) в таблицу
   монитора по адресам `0o1604`, `0o1605`, `0o53402` — перенос состояния
   в рабочую область ОС.
3. **`rte 177`** — выдача регистра режима (признак ловушки/ошибки).
4. **Цикл `0o76011–0o76012`** — заполнение области `0o1570+` значениями с
   шагом 1 (регистр `link` инкрементируется, пока не обнулится).
   Инициализация таблицы, а не вычисление.

## 4. Диспетчер: ядро обработки запросов

Самая частая подпрограмма — `0o77613` (3347 вызовов, 42 % всех вызовов):

```
; ПОДПРОГРАММА 0o77613 — "передать запрос вниз"
0o77613 ati 5              ptr = A
0o77613 asn 112            A >>= 0o112
0o77614 ati 1              ptr = A
0o77614 uj 77273(1)        goto 0o77273 + M(1)
   ...
0o77273 utm (5)            m5 += 0o2
0o77273 uj (6)             return link2
```

Это **хвост диспетчера**: записать признак, сдвинуть число и уйти на
`0o77273 + M(1)` — обработчик выбирается **значением регистра M(1)**.
Классический вектор прерывания: индекс запроса в M(1), вход в таблицу
через одно сложение.

`0o77273` — общий хвост: `m5 += 2` (счётчик) и возврат. Сюда же диспетчер
возвращается после обработчика.

Цепочка `0o77613 → 0o77273 → 0o77345/0o77355 → 0o77002` — спуск по уровням.

## 5. Цикл ожидания

```
; ПОДПРОГРАММА 0o77661 — задержка
do {   /* цикл: 0o77661 */
    0o77661 ita                A = ptr
    0o77661 utc (4)            C = 0o77615     ; УТА: база на 1 команду
    0o77662 atx (2)            0o1614 = A
    0o77662 vlm 77661(4)       управление
} while (0o77661);   /* ЦИКЛ vlm */
```

17120 исполнений — 46 % команд ядра. `vlm` инкрементирует M(4) и повторяет,
пока тот не обнулится: цикл на `32768 − M(4)` итераций, каждый проход пишет A

## 6. Самомодифицирующийся код — важная находка

Сверка содержимого трассы со снимком (`besm6kernel.py selfmod`):

| | |
|---|---|
| Команд в трассе | 339 162 |
| Не совпало со снимком | **7130 (2.10 %)** |
| Адресов с расхождением | 343 |
| Из них в ядре | `0o77345` (797), `0o77355` (476), `0o77274` (368), `0o77356` (298) |

Все четыре «горячих» адреса — **точки входа диспетчера** (`0o77274` — цель
`uj 77273(1)`). Монитор подменяет содержимое этих слов разными вариантами
trampoline-заглушек. Например, по адресу `0o77345` в трассе встречаются и
`uj 77002`, и `uj (6)` — монитор переписывает вектор перехода на конкретный
адрес.

**Практический вывод:** единственного снимка памяти недостаточно для полного
восстановления — нужны дампы в несколько моментов времени. Структура ядра при
этом устойчива (меняются единицы слов), конкретные цели ветвления — нет.

## 7. Устройство ОС MONSYS (по восстановленному коду)

```
пользовательская программа / компилятор
            │  экстракоды *50–*77 (системные вызовы)
            ▼
┌──────────────────────────────────────────────────────────┐
│ 0o76002  ИНИЦИАЛИЗАЦИЯ: загрузка базы C, копирование       │
│          системных ячеек, заполнение таблиц                │
├──────────────────────────────────────────────────────────┤
│ 0o77613  ДИСПЕТЧЕР: M(1) = номер запроса,                 │
│          переход на 0o77273 + M(1)                        │
│ 0o77273  ХВОСТ: m5 += 2, возврат                          │
├──────────────────────────────────────────────────────────┤
│ 0o76775  ВЫЗОВ ОБРАБОТЧИКА; 0o76247 / 0o76252 —          │
│          две основные ветви (1036 и 1022 вызова)          │
├──────────────────────────────────────────────────────────┤
│ 0o77000  ВНЕШНИЙ СЛОЙ: push/push, переход через link3     │
├──────────────────────────────────────────────────────────┤
│ 0o77661  ЗАДЕРЖКА: цикл на 32768 − M(4)                   │
├──────────────────────────────────────────────────────────┤
│ 0o77600  ТАБЛИЦЫ (данные, не исполняются): указатели,     │
│          флаги; заполняются из 0o76316 при старте         │
└──────────────────────────────────────────────────────────┘
```

Принципы организации, видные прямо в коде:

1. **Позиционная независимость.** Весь код адресуется через базу C; ядро можно
   перенести в другое место ОЗУ, переписав единицы слов.
2. **Регистры вместо стека для вызовов.** Три уровня `link`/`link2`/`link3`
   дают вложенность вызовов без программного стека. Стек M(17) используется
   для данных, а не для адресов возврата.
3. **Вектор прерываний в индексном регистре.** Номер обработчика берётся из
   M(1) и складывается с базой диспетчера — обработка запроса не требует
   поиска, это одно сложение.
4. **Самомодификация горячих точек.** Таблица переходов диспетчера
   переписывается под текущий поток запросов.
5. **Программные задержки.** Ожидание реализовано циклом, а не командой.
6. **Минимальная зависимость от экстракодов.** Только `*75` (запись в память,
   440 вызовов) и `*70` (диск/барабан, 15). Основная логика — в самом ядре.

## 8. Что восстановлено, а что нет

Восстановлено **21 тело** (1 точка входа + 20 подпрограмм), 385 строк
псевдокода.

| | |
|---|---|
| Базовые блоки | ✅ 516 — ровно столько, сколько исполняемых адресов |
| Терминаторы | ✅ 64 jmp, 45 jz, 43 jnz, 42 call, 9 loop |
| Циклы (обратные рёбра) | ✅ распознаются внутри тела подпрограммы |
| Условные переходы | ⚠️ печатаются как `if (cond) goto`; невзятая ветвь в трассе не восстанавливается |
| Имена переменных | ❌ только `m1..m14` — в образе имён нет |
| Структура данных | ❌ таблицы известны по адресам, не по типам |
| Неисполнённый код | ❌ 432 слова — холодные ветви, в листинг не попали |

## 9. Границы достоверности

- **Проверено измерением:** адреса и роли блоков, соглашение о вызовах,
  наличие циклов, частоты, факт самомодификации (2.10 %, 343 адреса).
- **Интерпретация:** названия «диспетчер», «задержка», «таблицы» выведены из
  структуры и поведения, а не из символьных имён (их в образе нет).
- **Принципиально не восстановить по одному прогону:** 432 неисполнённых слова,
  версии самомодифицированных слов, точная семантика `asn 112` (сдвиг по
  адресу) и `arx` (циклическое сложение).
- **Как закрыть пробелы:** прогнать несколько заданий (разные пути по ОС) и
  снять дампы в разные моменты; суммарное покрытие ядра вырастет с 516 из
  948 слов.

## 10. Связанные файлы

1. `tools/besm6decomp.py` — декомпиляция в псевдокод.
2. `tools/besm6kernel.py` — анализ ядра (`structure`, `listing`, `where`,
   `selfmod`, `calls`).
3. `docs/monsys-kernel.hl.txt` — полный высокоуровневый листинг.
4. `docs/monsys-kernel.listing.txt` — аннотированный машинный листинг.
5. `docs/monsys-kernel.md` — карта ядра.
6. `src/Besm6.Processor/Execution/ControlInstructionExecutor.cs` — семантика переходов.

по адресу `C + M(2)`. Это **программная задержка**: на БЭСМ-6 нет команды
«ждать», длительность задаётся числом итераций.
