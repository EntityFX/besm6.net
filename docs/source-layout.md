# Организация исходников библиотек

Физические папки отражают ответственность кода внутри DLL. Граф сборок
остался прежним: Architecture изолирована; Processor и Assembler зависят
от Architecture; Runtime связывает эти три библиотеки. `bin/` и `obj/` —
продукты сборки. Контракты после SOLID-рефакторинга описаны ниже;
историческая приёмка переноса папок приведена в конце документа.

| Библиотека | Основные папки |
|---|---|
| [Architecture](../src/Besm6.Architecture/README.md) | Isa, Numerics, State, Memory, Machine |
| [Processor](../src/Besm6.Processor/README.md) | Cpu, Execution, Arithmetic, Memory, Supervisor, Diagnostics |
| [Runtime](../src/Besm6.Runtime/README.md) | Machine, Configuration, Execution, Modeling, Timing, Loading, Extracodes, Devices, Storage, Encoding, Diagnostics, Profiling |

## Единая машина и два владельца исполнения

`Processor/Cpu` содержит общие регистры и фасад CPU. `Processor/Execution`
содержит единственную семантику команд, `Processor/Arithmetic` — общий
вычислитель АУ (арифметического устройства). Эти узлы не моделируют
ожидание хоста или аппаратную занятость ресурсов.

`Runtime/Machine` собирает CPU, память и устройства одной машины.
`Runtime/Execution` владеет функциональной симуляцией: тиками, быстрыми
блоками и планировщиком. `Runtime/Modeling` владеет аппаратным исполнением
того же CPU; `Runtime/Timing` содержит календарь, стадии АУ, память и
книжные спецификации времени. Общий координатор запрещает вложенное
исполнение. Новые аппаратные механизмы размещаются в Modeling/Timing,
а общая вычислительная семантика — в Processor.

`Processor/Supervisor` хранит привилегированное состояние УУ
(устройства управления) и общие правила входа в прерывание.
`Runtime/Devices` реализует устройства и обмен с ними.
Папки не заменяют ограничения зависимостей: Architecture не зависит от
Processor/Runtime, Processor — от Runtime; Runtime связывает компоненты.

## Контракты после SOLID-рефакторинга

`IProcessor` предоставляет запуск, шаг и наблюдение за регистрами. Редактирование
регистров, арифметика, подписки диагностики и учёт команд доступны через
`IRegisterOps`, `IAlu`, `IProcessorDebug`, `IInstructionAccountingSource`.
`State` — живое представление `IProcessorState` только для чтения;
`ProcessorSnapshot` — независимая неизменяемая копия. `M` наблюдается через
`ReadOnlySpan<uint>`; для редактирования используются `SetM`/`GetM`.
У снимка публичная коллекция `M` остаётся сериализуемой и неизменяемой.
Маска шестибитного R применяется в единственной точке записи состояния.

Функциональный и аппаратный исполнители Runtime получают внутренние роли
`IFunctionalProcessorExecution` и `IPreparedProcessorExecution`, а не конкретный
CPU. Подготовленная команда принадлежит одному процессору и поколению;
повторное использование, чужой владелец и устаревшая аренда отклоняются.
Состояние watchpoints и управляющее исключение находятся внутри Processor.
Его friend-доступ разрешён Runtime и двум тестовым сборкам; Runtime открывает
внутренности только своим тестам и интеграционным тестам. CLI использует
публичные настройки, включая `ExecutionSpeedNames.TryParse`.

| Роль памяти | Потребитель | Адреса и эффекты |
|---|---|---|
| `IHostMemory` | загрузчик, hosted-сервисы, диагностика | физические адреса хранилища; чтение включает ожидающие записи без проверки CPU-защиты/контроля и изменения порядка буферов; запись согласует буферы |
| `IOperandMemory` | CPU | нормализованные 15-битные адреса; выбранный backend выполняет приписку, защиту, контроль и операции BRZ |
| `IInstructionMemory` | выборка CPU | расширяет роль операндов; отдельная выборка половины команды с контролем и BRS |
| `ICommandMemory` | hosted CTX (`*75`) | публикация команды в адресном пространстве CPU с согласованием ожидающих алиасов и следующей выборки |

`IMemory` остаётся общим транспортом слова, без обещания одинаковой политики
адресации. `CoreMemory` реализует роли непосредственно. Buffered и Mapped
предоставляют отдельное host-представление, которое нельзя передать в CPU.
Приписка и теги не унифицируются между моделями: это часть их семантики.
`MachineCore.Memory` и `SystemBus` предоставляют host-доступ;
`MachineCore.CommandMemory` выбирается отдельно при сборке машины.
Математическая загрузка требует явного адаптера приписки.

`ExtracodeHandler` сохраняет диспетчеризацию фиксированного гостевого ABI.
Числовой парсер, часы, печать, терминал, хранение и системные услуги имеют
отдельных владельцев состояния с явными зависимостями. Сервисы не получают
`MachineCore`; терминал завершает накопленную печать через отдельный callback.
Трассировка владеет лениво открываемым writer и освобождает его через `Dispose`.

Изменения публичного API намеренные: интерфейс `IProcessor` больше не является
редактором регистров/АУ/диагностикой; `State` и снимки не изменяются напрямую;
конструктор CPU принимает `IOperandMemory`, шина — `IHostMemory`.
Клиенты должны запрашивать нужную роль явно. Стандартная конфигурация Dubna,
гостевые коды экстракодов и вычислительная семантика команд сохраняются.
