# Этап 5: отдельная шкала аппаратного времени

Срез: 10 октября 2026 года. Реализованы инфраструктура и первые стадии АУ;
аппаратный конвейер CPU и временные задержки устройств ещё не включены.

## Подтверждённые данные

Источник — Салтыков/Макаренко, «Программирование на языке Фортран»,
1976: §4, печатная стр.21 и приложение1, стр.247–249. Проверены сканы
[21](../book/fortran-1976/original/page-021.png),
[247](../book/fortran-1976/original/page-247.png),
[248](../book/fortran-1976/original/page-248.png),
[249](../book/fortran-1976/original/page-249.png).
SHA256 и границы утверждений: [аудит](../reports/hardware-time-source-audit.json).

`BookTimingSpecification` хранит 47 опубликованных строк: времена УУ
и отдельные minimum/average/maximum АУ. Книжный такт этого источника —
110 нс. Среднее2,5 такта представлено точно как275 нс; у сдвигов среднее
отсутствует. Два значения условного перехода сохраняют порядок печати,
но их соответствие исходу перехода пока не задано.

Среднее АУ не является сроком конкретной команды. Времена УУ/АУ
не складываются автоматически; отсутствие строки не заменяется числом
по умолчанию. Например, STOP, необозначенные привилегированные операции
и экстракоды возвращают `TryGet=false`. 110 нс не объявляются тактом
каждой исторической конфигурации БЭСМ-6.

## API и единицы

Имена в коде английские, историческое русское название указано коротким
комментарием у определения:

| Русский термин | Имя в коде |
|---|---|
| БАК — буфер арифметических команд | `ArithmeticCommandBuffer` |
| АУ — арифметическое устройство | `ArithmeticUnit`, существующий фасад `Alu` |
| Стадии АУ | `ArithmeticUnitStages` |
| МОЗУ — магнитное оперативное запоминающее устройство | `MramReadTiming`, физическое хранилище `PhysicalMemory` |

- `HardwareInstant` — абсолютные наносекунды отдельной шкалы.
- `HardwareDuration` — длительность в наносекундах. Сложение проверяет
  переполнение; отрицательный интервал отклоняется.
- `HardwareTimeline` — детерминированный календарь без часов хоста.
  События упорядочены по времени и регистрации. Callback может добавлять
  и отменять события, включая событие текущего момента; вложенное
  продвижение времени отклоняется.
- `HardwareEventToken` принадлежит конкретному календарю. Чужой,
  отменённый, выполненный или пустой токен не отменяет событие.
- Ошибка callback оформляется как `HardwareCallbackException` с исходной
  причиной и временем; уже доставленное событие удалено, оставшаяся
  очередь сохранена. Время остаётся на границе ошибки; продвижение
  можно продолжить отдельным вызовом.
- `HardwareResourceCalendar` резервирует явно заданные независимые
  ресурсы: начало=max(самый ранний срок, готовность ресурса),
  конец=начало+занятость. Переполнение не изменяет резервирование.
  Отмена события не снимает резервирование; эта примитива не задаёт
  аппаратной политики отмены или арбитража.

Конструктор календаря ресурсов не создаёт скрыто восемь банков, АУ,
буферы или каналы. Топологию и длительности задаёт вызывающая модель.
Готовность данных и освобождение ресурса — отдельные величины:
цикл восстановления памяти нельзя автоматически выдать за задержку
возврата операнда. Проверки с синтетическими длительностями подтверждают
сам календарь, а не историческую схемотехнику.

```csharp
using Besm6.Runtime.Timing;

var timeline = new HardwareTimeline();
var arithmeticUnit = new HardwareResource(HardwareResourceKind.ArithmeticUnit); // АУ.
var resources = new HardwareResourceCalendar(new[] { arithmeticUnit });
// Синтетический пример API, не расчёт длительности команды БЭСМ-6.
var reservation = resources.Reserve(arithmeticUnit, timeline.Now, new HardwareDuration(550));
int published = 0;
timeline.ScheduleAt(reservation.Finish, () => published = 42);
timeline.AdvanceTo(reservation.Finish);
Console.WriteLine(published); // 42
```

## Совместимость и следующие блоки

`MachineCore.HardwareTimeline` теперь владеет лениво создаваемым календарём.
Он продвигается явно: стоимость команд и общие обработчики CPU пока
не подключены к аппаратному времени. Callback запрещает повторный запуск
CPU и вложенное продвижение обеих шкал; scheduling и отмена разрешены.
`ResetCpu` сохраняет аппаратное время и очередь. После ошибки callback
защита снимается, причина сохраняется, остальные события остаются в очереди.
`SimulationClock` сохраняет один тик на завершённый шаг, включая STOP.
`Besm6Timing`, его100 нс, pacing original, DATE*, лимиты и действующие
устройства не меняются. В календаре нет различия original/max:
он движется только по явно указанным гостевым временам.

Внутренний `MachineCore.CreateArithmeticUnitStages` создаёт узел АУ на том
же календаре, фиксируя явно переданный квант. Операнды принимаются отдельно
от запуска; следующая операция использует завершённое A/Y предшественника.
Выход появляется по ИЗОП, а проверка делителя и сигнал ошибки имеют разные
сроки2,5/3 такта. Узел не создаётся обычным CPU и сохраняется при `ResetCpu`.
Физические микропоследовательности, режимы ошибок и интеграция с retirement
остаются следующей работой; [правила и границы](besm6-hardware-time.md).

| Блок этапа 5 | Статус | Необходимое подтверждение |
|---|---|---|
| Единицы времени и опубликованные диапазоны | Реализован | Сверенные сканы и независимые векторы |
| Календарь событий и ресурсов | Реализован как инфраструктура | Порядок, отмена, ошибки, переполнение, зависимости |
| Длительность АУ для конкретных операндов | Не реализован | Последовательности АУ, нормализация и округление по техническому описанию |
| Занятость и перекрытие УУ/АУ | Не реализован | Условия выдачи, блокировки зависимостей и моменты фиксации |
| Банки, БРС/БРЗ и запросы в полёте | Не реализован | Моменты получения/восстановления, сравнения адресов и арбитраж |
| Устройства и прерывания в наносекундах | Не реализован | Выбранные конфигурации и документированные задержки |
| Интеграция CPU, original/max и ОС | Не реализован | Побитовое состояние, порядок событий и контрольные временные диаграммы |

таблиц исключено.
Запрет повторного запуска машины из аппаратного callback реализован.
Правила незавершённых аппаратных запросов при ошибке и STOP ещё требуют
спецификации. Владение календарём не является готовым временным профилем CPU.

## Этап 5: границы временной спецификации УУ и АУ

Срез: 10 октября 2026 года. Продолжение первого инфраструктурного блока.
Здесь закреплены ограничения для следующей реализации; микропоследовательности

### Подтверждённые ограничения

ТО-2, §2.1–2.2: подготовка команд совмещается с АУ через буферные уровни.
§2.8–2.9: команда проходит РК/РР/ПР; передача через ПР может задерживаться
до разрешения приёма БРА/БАЗ. Поэтому единственный признак «АУ свободно»
не описывает весь путь выдачи. Прерывание блокирует дальнейший приём
команд; это не разрешение прерывать произвольный микрошаг АУ.

ТО-3, §1.1: время зависит также от поступления операндов; подготовка следующей
операции совмещается с текущей. Табличный диапазон нельзя автоматически
считать отдельной занятостью АУ и затем прибавлять полную задержку памяти:
сначала требуется установить границы измеряемого интервала.

### Следующий реализуемый блок

Для каждой операции нужны начало приёма команды, условие готовности
операнда, занятость цепей, публикация A/Y и разрешение следующей выдачи.
Нужно сверить сигналы и диаграммы ТО-2/ТО-3, а затем закрепить независимые
векторы: зависимые и независимые команды, попадания в буферы, ожидание
БРА/БАЗ, ветвление, ошибка операнда, STOP и прерывание.

До этого календарь резервирует только явно заданные синтетические интервалы.
Ни выбор среднего, ни простая сумма УУ+АУ, ни перенос задержек из SIMH
не используются как аппаратная модель. Существующий Dubna и original/max
сохраняют прежнее исполнение.

#### Контроллер логической передачи и запуска

`ArithmeticStageController` связывает существующие БАК, стадии АУ и календарь.
Переход к выбранной команде с готовым буфером начинает фазу 3 такта;
явное снятие ожидания выбранного операнда — фазу 1,5 такта по §3.7,
[PDF 20](sources/hardware-time/arithmetic-pdf-20.png), лист 37.
Для ещё не выбранной ячейки готовность только запоминается: её выбор
впоследствии начинает фазу готового буфера. Поздний РПК не повторяет уже
истёкшую передачу. Это логические точки отсчёта; электрические цепочки
усилителей не воспроизводятся.

Это цепочка чтения операнда из буфера; сроки индексных команд,
непосредственных операндов и записи данным контроллером не определяются.

ПВР освобождает ячейку БАК и однократно считывает входной операнд через
переданный считыватель. Следующая операция может подготовиться до ИЗОП,
но СПОП ставится событием только после завершения предыдущей, с её A/Y.
ИЗОП публикует выход до события запуска следующей операции того же момента.
Один экземпляр стадий АУ может иметь только один контроллер и один календарь.
Общее гашение отменяет принадлежащие контроллеру события, сохраняя сторонние.

РПК/ИЗОП подаются явно. Контроллер не декодирует физическую 17-разрядную
команду и не вычисляет полную длительность команды. В интеграционной проверке
его ИЗОП разрешает общий CPU завершить подготовленную команду. Теперь
доступна явная связь через приём операнда и поставку результата: общий
обработчик считывает операнд при ПВР, а CPU публикует готовый выход АУ,
не читая изменённое слово памяти повторно. В тесте эта связь задана явно.
Автоматическая связь запроса с контроллером и отказ операнда приняты в
последующем блоке владения запросом; полное время ИЗОП остаётся в работе.
Это не приёмка полноценного временного профиля.

`IArithmeticInstructionExecution` даёт общий opcode-обработчик с двумя
структурными получателями: немедленная арифметика и приём неизменяемого
операнда/режима. Адресация и стек не дублируются. Приём выполняет текущие
правила продвижения половины, эффективного адреса и стека; это логическая
граница API, а не утверждение о физических сроках K/M. Отмена не откатывает
уже принятые эффекты. Запись A/Y при выдаче использует прежний нормализатор;
переполнение доставляется после записи, итоговый режим — только при успехе.

Ошибка чтения сохраняет причину и описание авоста из общего обработчика
supervisor: сигнал, адрес возврата и флаги. Последующая ошибка другого
обращения не заменяет номер исходного буфера. Считыватель не может вложенно
запустить драйвер, отменить команду или продвинуть время. Функциональный
callback не может принимать или поставлять фазу аппаратной арифметики.

### Реализованная логика подготовки АУ

ТО-3, [PDF17](sources/hardware-time/arithmetic-pdf-17.png), листы30/31,
§3.2: СПОП требует завершения предыдущей операции и подготовки следующей;
ИЗОП не зависит от готовности следующей команды. РПК может появляться до
ИЗОП; ПВР требует разрешения РПК и готового операнда. `ArithmeticPipelineControl`
закрепляет эти зависимости отдельными переходами. Внешняя модель подаёт
разрешение, готовность и завершение; класс не рассчитывает импульсы РПК
и не хранит значения входных регистров АУ. Это логическая проверка порядка,
а не электрическая модель сигналов.

ТО-3, [PDF18](sources/hardware-time/arithmetic-pdf-18.png), листы32/33,
§§3.3–3.6: БАК имеет четыре 17-разрядные линейки, кольцевые счётчики приёма
и выдачи. ПВР передвигает счётчик выдачи и разрешает повторное использование
освобождённой линейки. `ArithmeticCommandBuffer` сохраняет её до ПВР:
просмотр кода и завершение предыдущей операции не освобождают ячейку.
Нулевой код является допустимым содержимым, а не признаком пустой ячейки.

ТО-3, [PDF20](sources/hardware-time/arithmetic-pdf-20.png), листы36/37,
§3.7: при готовом операнде БРУС запрос/приём занимает три такта; после
снятия задержки готовностью БРЧ приём следует через полтора такта.
`ArithmeticBufferTransferTiming` предоставляет две разные точки отсчёта.
Он не выбирает фазу самостоятельно, не задаёт задержку МОЗУ и не
приравнивает момент получения данных к освобождению банка. Квант передаётся
явно; полуцелые такты представляются без округления.

### Критическая граница публикации результата

ТО-3, [PDF32](sources/hardware-time/arithmetic-pdf-32.png), листы60/61,
§§3.22–3.23: при подготовленной следующей операции СПОП может совпадать с
ИЗОП. Описание отдельно рассматривает наложение округления при выдаче
результата. Поэтому нельзя просто выполнить нынешний обработчик и затем
считать все биты наблюдаемыми в произвольно выбранный момент ИЗОП.
Требуется сверка конца операции, выдачи и начала следующей для конкретного
типа команды. Новые управляющие компоненты не публикуют A/Y и не меняют
текущую арифметику.

В общем нормализаторе выделено чистое вычисление `Evaluate`: оно возвращает
`NormalizedArithmeticResult` без записи A/Y и без доставки переполнения.
В результате отдельно представлены мантисса до выходного округления,
накладываемый младший бит, Y и признак отложенного исключения. Нынешний
`NormalizeAndRound` публикует этот же результат сразу и затем бросает
исключение, сохраняя контракт Dubna. Второго алгоритма нормализации нет.

Это логическое разделение, не полное содержимое физических регистров АУ.
Лист61 различает округлённое значение на выходной шине и запись младшего
бита в сумматор. Описанная передача единицы из младших разрядов при
нормализации снимает необходимость выходного округления. Источник не
позволяет назначить универсальный срок фиксации «через такт после ИЗОП»
или «только при следующем СПОП»: для этого нужны соответствующие сигналы.
Логический приём/выдача теперь доступны общему CPU через явную связь;
автоматические физические временные точки ещё не определены для всех команд.

Общие вычисления сложения/вычитания, умножения, деления, изменения порядка
и знака теперь могут возвращать подготовленный результат, не изменяя CPU.
Для каждой операции один generic-алгоритм завершает работу
через структурный получатель результата: обычный путь вызывает немедленную
нормализацию/запись, подготовленный путь сохраняет значение. Обычная
нормализация сохраняет отдельную границу вызова JIT, чтобы не развернуть
её в каждом обработчике и не вытеснить встраивание самого `Evaluate`.
Короткие обёртки операций также сохраняют прежние границы вызовов:
их встраивание не должно раздувать общий диспетчер арифметическими телами.
Это организация общего кода, а не аппаратная стадия или задержка.

### Почему время деления нельзя получить из цикла нынешнего АУ

ТО-3 §4.16, [PDF50](sources/hardware-time/arithmetic-pdf-50.png),
листы96/97, описывает сумму и переносы как двухрядный остаток; три старших
разряда в схеме управления становятся доступны на полтакта раньше,
чем на основном сумматоре. Это определяет выдачу следующего действия.
Полное сложение целых чисел на хосте не сохраняет эти промежуточные сигналы.

[PDF52](sources/hardware-time/arithmetic-pdf-52.png), листы100/101,
задаёт начальный код счётчика `101000` (40) и уменьшение на единицу в
каждом такте деления. Нулевой счётчик завершает собственно деление,
после чего начинается образование частного. Отдельно описаны 41 разряд
частного и разряд для округления. Эти этапы нельзя объединить в
«40 итераций до готового A» или заменить средним временем таблицы.

Нынешний `NrDiv` имеет быстрый случай делителя с мантиссой `BIT40` и
выход при нулевом остатке. Они допустимы для вычисления гостевых битов,
но количество выполненных итераций этого C#-цикла не является аппаратным
временем деления. Временной драйвер должен воспроизводить подтверждённые
стадии отдельно от стоимости расчёта результата на хосте. Сами быстрые
случаи и правила округления Dubna в этом блоке не изменены.

Проверено 17 новых случаев: кольца БАК, противодавление, освобождение по
ПВР, подготовка до ИЗОП, независимый ИЗОП, невозможность перезаписи
подготовленного операнда, разные фазы БРУС и точность полутактов.
Интеграция с CPU, банковские задержки и время устройств ещё не завершены.

### Первые интервалы банков MRAM

ТО-4, редакция1-66, [PDF3](sources/hardware-time/mram-pdf-03.png), лист3,
§§1.1–1.2: восемь автономных банков по4096 слов выбираются младшими
разрядами адреса. Минимальный полный цикл между началами выборок одного
банка —2 мкс; возврат данных указан как приблизительно0,9 мкс.

`MramReadTiming` разделяет `DataReady` и `BankAvailable`. Занятый банк
отклоняет запрос без скрытого помещения в очередь; порядок повторных
запросов должна определить будущая модель УУ. Разные банки могут быть
зарезервированы независимо. Геометрия `Simh512K` отклоняется: её аппаратная
временная спецификация отсутствует в этом источнике.

Задержка чтения передаётся явно, опубликованные900 нс названы приблизительными.
Это не точная калибровка и не момент видимости записи: источник отдельно
считает магнитный цикл от начала считывания, а не от начала всего запроса.
Примитива пока только резервирует интервалы; память и CPU к ней не подключены.
Семь новых проверок покрывают независимость банков, сохранение занятости
после возврата данных, отказ без очереди, границы адресов, переполнение
и отдельный этап передачи БРЧ→АУ.

### Данные на стадиях АУ и задержка проверки делителя

Внутренний `ArithmeticUnitStages` связывает БАК и управляющие переходы с
неизменяемым `PreparedArithmeticOperation`. Операнд и режим принимаются при
ПВР. Расчёт общим алгоритмом начинается при СПОП с выходным A/Y предыдущей
завершённой операции. Поэтому приём следующего операнда до ИЗОП не использует
устаревший аккумулятор. При ИЗОП результат становится доступен через
`TryReadOutput`; отдельно сохраняются мантисса до выходного округления и
накладываемый младший бит. Совпадение ИЗОП/СПОП проверяется в заданном порядке
событий календаря.

ТО-3, [PDF34](sources/hardware-time/arithmetic-pdf-34.png), листы64/65,
§3.28: проверка делителя происходит через2,5 такта после начала деления;
сигнал УДО появляется через3 такта. Это разные переходы. До проверки ИЗОП
деления отклоняется, а для неправильного делителя отклоняется и до УДО.
Знание ошибки при вычислении на хосте не публикует её раньше аппаратной
точки. Ошибка удерживается как гостевая причина, без исключения из callback;
новые ПВР/СПОП после неё блокируются. Отдельная ошибка callback сохраняет
свою причину и оставшиеся аппаратные события.

Квант передаётся явно; тесты100/110 нс проверяют масштабирование и полуцелую
границу, а не объявляют оба значения одной исторической конфигурацией.
Узел принадлежит машине и сохраняет работу при `ResetCpu`. Обычный CPU
его не создаёт и по-прежнему использует немедленный путь Dubna.

Границы: декодирование физического17-разрядного кода БАК, длительности
микропоследовательностей, физические43-разрядные регистры и retirement
CPU ещё не реализованы. ИЗОП и РПК подаёт вызывающая модель,
средние времена таблицы для этого не используются.

### Управление ошибками АУ

ТО-3 §3.28, [PDF34](sources/hardware-time/arithmetic-pdf-34.png),
[PDF35](sources/hardware-time/arithmetic-pdf-35.png),
[PDF36](sources/hardware-time/arithmetic-pdf-36.png), листы64–68,
закрепляют четыре режима. `ArithmeticErrorControl` реализует их логические
сигналы: останов, продолжение с регистрацией, продолжение при арифметических
ошибках с возможным остановом по контролю и прерывание только по контролю.
В последнем режиме подавлены УПр и передача АВП/УДО для арифметических
причин; местные АВП/УДО и причина входного контроля различаются. Выбор
удержания по контролю задаётся отдельно, он не выводится из БлПр.

Проверка стабильного входного50-разрядного слова завершается через1,5 такта
после поступления. Используется существующая проверка полного контроля
`MemoryWord50.HasValidOperandControl`: чётное число единиц означает ошибку.
Разрешение РУПр появляется через2 такта после СПОП. Ошибка, известная до
разрешения, не устанавливает УПр раньше; поздний результат свёртки не
публикуется до своей границы. После установки причина и код источника
сохраняются независимо от последующего корректного слова.

Переполнение распознаётся по ИЗОП, а входная ошибка запрещает его индикацию
через РУПр. При продолжении УДО снимается по ИЗОП, УПр и АВП — через такт.
При останове сигналы удерживаются; ПСб/УОЗ разрешает следующий запуск.
`LastInterruptSample` фиксирует причину по ИЗОП и не стирается местным
сбросом. В отдельном контроллере это снимок; модель машины теперь связывает
его с общим регистром причины и явной границей принятия УУ (см. ниже). Событие снятия старой причины не стирает новую индикацию.

Аппаратный режим задаётся внутренним параметром узла АУ. В нём общий
алгоритм выполняется один раз с включённым выявлением переполнения;
контроллер самостоятельно определяет блокировку и передачу причины.
Режим Dubna и обычное конструирование стадий сохраняют `OvfDisable`.
Гостевые A/Y и округление от разделения причины и доставки не меняются;
новых проверок в обычном обработчике CPU нет.

`ApplyGeneralClearSignal` принимает конкретный управляющий сигнал очистки,
обнуляет логические A/Y и кольца БАК, снимает блокировки и отменяет только
свои незавершённые события. `ResetCpu` этого не делает. Этот API не задаёт
восьмитактовую микропоследовательность общего гашения: её внутренние точки
и цепь начального РПК ещё требуется воспроизвести отдельно.

Ограничения: не моделируются изменения электрического кода в ходе свёртки,
полные совместные условия сигналов по схемам, физическое размещение причин
в регистре БРУС и вход в прерывание УУ. После неправильного делителя общий
алгоритм не даёт результата; узел не начинает следующую арифметику с
вымышленным нулём или старым A. Продолжение с физическим результатом такого
деления требует микропоследовательности и независимых векторов. Управляющие
режимы реализованы, но этим полный цикл восстановления машины не закрыт.

### Выбор действия и опережающий контроль деления

ТО-3 §4.16, таблица4.4 на [PDF48](sources/hardware-time/arithmetic-pdf-48.png),
задаёт выбор сложения с делителем, вычитания либо одного сдвига по пяти
разрядам: двум старшим разрядам ряда переносов и трём ряда суммы.
`DivisionControl.Decode` воспроизводит таблицу, включая сохранение предыдущего
действия для нулевого старшего разряда суммы. Четыре неопределённые комбинации
дают только сдвиг. Знак полностью приведённого остатка не заменяет эти входы.
Независимая транскрипция таблицы проверяет все128 сочетаний разрядов,
предыдущего действия и знака делителя.

На [PDF52](sources/hardware-time/arithmetic-pdf-52.png), лист100, усилитель
ЗУ+ЧВР хранит именно предыдущее сложение. Вычитание и один сдвиг снимают
этот признак. Перед первым действием он установлен только для отрицательного
делимого и положительного делителя; знак берётся из мантиссы, а не порядка.

[PDF50](sources/hardware-time/arithmetic-pdf-50.png), лист97, отделяет
появление управляющих разрядов РСУД/РПУД от появления соответствующего
двухрядного остатка в основных регистрах на0,5 такта. `DivisionControl.Sample`
фиксирует действие немедленно и регистрирует эту следующую границу в календаре.
Следующая выборка разрешена через полный такт; значения разрядов предоставляет
будущая модель сумматоров. `AvailableMainRemainder` содержит управляющий снимок,
чья граница достигнута, а не вычисленные полные ряды остатка.

Стадии АУ создают отдельный управляющий узел при СПОП деления. ИЗОП не может
опередить уже запрошенную границу основного остатка. Завершение закрывает узел,
общий сигнал гашения отменяет его собственное событие; старое событие не
попадает в следующую операцию. Общий результат деления по-прежнему вычисляется
существующим алгоритмом, без нового пути гостевой арифметики.

Остаются физические43/42-разрядные ряды, образование частного из двух
составляющих, связь счётчика с начальным значением40 с42 цифрами частного, специальные
сигналы округления и завершающие переносы/нормализация. Управляющая таблица
и полутактовая граница не задают полную длительность или автоматический ИЗОП.

### Две составляющие частного и коррекция младшего разряда

`DivisionQuotientParts` принимает42 явных импульса сдвига составляющих.
По ТО-3 §4.16, [PDF48](sources/hardware-time/arithmetic-pdf-48.png), лист93,
вычитание делителя заносит единицу в положительную составляющую, сложение —
в отрицательную. При одном сдвиге единица не заносится ни в одну; сдвигаются
обе составляющие. Их разность образует частное. Логическое представление
хранит41 разряд образования и дополнительный разряд каждой составляющей,
не подменяя отдельное физическое размещение положительного разряда в ДРОМ.

[PDF49](sources/hardware-time/arithmetic-pdf-49.png), лист95, задаёт восемь
сочетаний хвостов для точного деления на положительный/отрицательный делитель.
Они сохранены в независимых тестовых векторах как фрагменты регистров,
а не вымышленные полные операнды. Правило на
[PDF50](sources/hardware-time/arithmetic-pdf-50.png), лист96: если первый
основной разряд обеих составляющих равен нулю, коррекции нет. Иначе единица
дополнительного разряда положительной составляющей требует+1, ноль —−1.
Проверены все девять достижимых сочетаний двух младших пар разрядов.

При образовании частного дополнительный разряд отделяется, отрицательная
составляющая выдаётся обратным кодом. [PDF53](sources/hardware-time/arithmetic-pdf-53.png),
лист102, реализует коррекцию−1 запретом единицы перехода в дополнительный
код через ДПР, коррекцию+1 — отдельной единицей в первом разряде регистра
суммы. `DivisionQuotientFormation` разделяет эти два сигнала и входные коды.
Знаковые значения до/после коррекции используются как логический эталон;
это ещё не физические ряды сумматора и не запись A/Y процессора.

`DivisionControl.ShiftQuotientParts` принимает отдельный импульс для последнего
действия таблицы4.4; повторный импульс для одной выборки отклоняется.
Появление основных рядов не вызывает сдвиг автоматически: фазу должен
задавать будущий драйвер. Завершение/гашение закрывает старый узел, новое
деление получает нулевые составляющие. Общий результат Dubna не заменяется.

Остаются связь этих42 импульсов со счётчиком40 и начальными фазами,
физические ряды остатка и сумматора образования частного, разрешения
округления из управляющих схем, завершающие переносы/нормализация,
длительность и аппаратная публикация результата в CPU.

### Автоматическое владение запросом общего CPU

`HardwareProcessorModel.BindArithmeticInstruction` связывает одноразовую
команду CPU с единственным `ArithmeticStageController`. Контроллер принимает
операнд через общий обработчик при ПВР, запускает общий расчёт при СПОП
и передаёт результат CPU при ИЗОП. Диагностический `Transitioned` вызывается
после обязательной передачи разрешения: замена или ошибка наблюдателя
не отключает исполнение. Обработчик CPU завершается вне callback календаря.

При отказе чтения CPU хранит причину и детали авоста, БАК освобождается,
арифметика не запускается. Это логическая граница отказа общего исполнителя,
не утверждение о полной физической последовательности аппаратного контроля.
Код17-разрядной команды, РПК и срок ИЗОП по-прежнему задаются явно.
`ScheduleBoundArithmeticCompletionAt` владеет таким явным сигналом: отмена
или смена поколения CPU исключают его доставку прежнему запросу.

Связанный запрос исключает сторонние команды в этом контроллере.
Отмена удаляет его передачу, запуск и внутренние события деления, сохраняя
память, A/Y уже завершённой операции, календари, устройства и чужие события.
Это отмена программного запроса, не сигнал общего гашения. Принятые эффекты
адресации/стека CPU не откатываются. ResetCpu аннулирует дескриптор;
следующее действие драйвера освобождает его связь. Старый callback при прямом
продвижении календаря также не читает операнд и не запускает расчёт.

Перед новым связыванием простаивающая АУ согласует логический выход с текущими
A/Y общего CPU, включая функциональные команды между модельными запросами.
Автоматическая связь пока применяет прежнюю Dubna-совместимую арифметику.
Четыре физических режима ошибок остаются отдельным проверенным компонентом;
их выдача в БРУС/УУ и полная последовательность гашения требуют дальнейшей
интеграции, и такая конфигурация связывания пока явно отклоняется.

### Источник операнда в 17-разрядной команде АУ

ТО-3 §3.8, [PDF21](sources/hardware-time/arithmetic-pdf-21.png), листы38/39,
и [PDF22](sources/hardware-time/arithmetic-pdf-22.png), лист40, задаёт формат
слова БАК. `ArithmeticCommandWord` декодирует именно этот интерфейс:

| Источник | Признак | Поля |
|---|---|---|
| Внешнее устройство | Разряд17=1 | Разряд16 запрещает остальные управляющие сигналы,12 задаёт чтение,11–1 — адрес |
| Индекс-регистр | Разряд17=0,16=1 | 15–1 — полный операнд; остальные признаки класса не интерпретируются |
| Непосредственный операнд | 17=16=0,9=1 | 15–10 — код операции,7–1 — операнд;8 не используется |
| Запись | 17=16=9=0,8=1 | 7=1 — установка контрольных признаков из3–1,7=0 — запись в буфер |
| Буферное чтение | 17=16=9=8=0 | 15–10 — код операции,6–4 — признаки группы,3–1 — номер |

Признаки6–4 сохраняются раздельно: при сочетании нескольких единиц
приоритет групп не выдумывается. Это не декодер гостевой команды24 бит.
Физическое соответствие шестибитного поля гостевым Opcode ещё не закреплено;
поля операнда/адреса доступны будущей УУ, но общий CPU остаётся источником
данных и семантики связанной команды. Текущая типизированная связь использует
класс источника, а не объявляет реализацию всех физических полей слова.

Контроллер различает буферную передачу и прямой приём. Для прямого пути
`TryAcceptDirectOperand` требует выбранную команду и РПК; момент сигнала
ПВРА/ПВРМ задаётся управляющей последовательностью явно. Он не получает
3/1,5 такта цепочки БРЧ. Разрешение само по себе не назначает срок приёма.
Приём запускает прежний общий обработчик ровно один раз; СПОП остаётся
календарным событием, выдача — общей границей завершения.

В модели типизированная связь допускает буферный источник для арифметики
памяти и непосредственный для e+n/e-n. Запись, индексный операнд, внешние
устройства и несовпадающий источник пока отклоняются до изменения CPU.
Нет автоматического кодирования слова БАК из команды УУ или полного ИЗОП;
в проверках сроки прямого приёма и завершения заданы синтетически.

### Формирование слова АУ из подготовленной команды общего CPU

Таблица1.1 ТО-3, [PDF4](sources/hardware-time/arithmetic-pdf-04.png),
листы4/5, содержит отдельные столбцы программного и аппаратного кода.
Для поддержанных арифметических команд они дают следующие восьмеричные
значения: сложение004, вычитание005, обратное вычитание006, модули007,
изменение знака014, деление016, умножение017, порядки024/025,
коррекция порядков адресом034/035. `ArithmeticCommandEncoding` закрепляет
этот подтверждённый набор, не выдавая поддержку остальных строк таблицы.

Модель может формировать слово автоматически. Код занимает15–10 разряды;
коррекция адресом устанавливает9 разряд и семь младших битов операнда.
Для арифметики памяти вызывающий узел предоставляет выделенную ячейку БРУС:
разряд4 задаёт БРЧ,5 — специальные регистры,6 — пультовые внешние устройства;
при отсутствии этих признаков выбирается БРЗ,3–1 содержат номер0–7.
Выделение ячейки и доставка её данных принадлежат следующей интеграции
MRAM/буферов. Представление слота не заменяет содержимое буферной памяти.

Непосредственный операнд формируется общим кодом адресации CPU: C,
нормализация15-разрядного адреса и индексный регистр. Preview не изменяет
K, половину, эффективный адрес или регистры и не читает память; при приёме
используется тот же обработчик. Слово сохраняется как выданная команда.
Типизированная связь проверяет код операции и непосредственный операнд
против подготовленной команды; смешанные буферные признаки отклоняются
без предположений о приоритете. Изменение C/M между выдачей и прямым приёмом,
влияющее на операнд, сообщает конфликт модели до изменения CPU; запрос
остаётся доступным для отмены. Это не гостевой авост и не замена данных слова.

Низкоуровневая перегрузка с raw uint сохранена для синтетических проверок
буферных фаз. Новый путь выдачи использует кодирование и типизированную
проверку. Прежние непосредственные тестовые слова с нулевым полем операции
заменены независимыми034/035; числа и ожидания результата не ослаблены.

Один источник семантики сохранён: слово АУ выбирает согласованный обработчик
того же CPU, общая арифметика вычисляет и публикует результат. Векторы полных
слов проверяются отдельно от сравнений с обычным Step. Автоматическое
формирование слова не задаёт РПК, прямой ПВР или срок ИЗОП; эти управляющие
цепочки, перекрытие запросов и аппаратная ошибка/УУ остаются в работе.

### Общий вход логических операций: подготовка временных последовательностей

ТО-3 §4.18–4.20 описывает сравнение (XOR), логическое умножение (AND)
и логическое сложение (OR): [лист103](sources/hardware-time/arithmetic-pdf-53.png),
[листы104/105](sources/hardware-time/arithmetic-pdf-54.png). Таблица1.1
сопоставляет им программные и физические коды012/12,011/11 и015/15.
Общий staged-путь расширен этими командами: тот же обработчик адреса и
стека читает операнд при ПВР, общий вычислитель вычисляет результат при
СПОП, а CPU публикует A/Y и логический режим при разрешении завершения.
Обычный исполнитель использует тот же вычислитель. Сохраняется принятая
семантика Dubna: Y=0 для AND/OR, прежний A для XOR; аппаратные отличия
регистров/режима не вводятся этим инфраструктурным изменением.

Независимые векторы AA AND CC=88, AA XOR CC=66, AA OR CC=EE проверяют
приём один раз и отсутствие публикации до завершения. Изменение памяти
после ПВР не заменяет принятый операнд. Дополнительные векторы полных слов
сравнивают обе половины, пять режимов, регистры и диагностику с обычным Step.

Сроки завершения этих проверок синтетические. Таблица даёт для AND/OR
постоянную длительность4 такта, но сама по себе не доказывает точку отсчёта
для планирования сигнала ИЗОП в нашем календаре. РазделIV прямо отсылает
к отдельным временным диаграммам ИЫ3.050.000 Д2. В просмотренном PDF ТО-3
после текста находятся логические схемы Д3, а не эти временные диаграммы.
Автоматический ИЗОП и зависимые последовательности остаются в разработке;
табличное среднее XOR не подключается как таймер завершения.


### Фиксированный логический интервал СПОП→ИЗОП

Для первого автоматического завершения используется совокупность двух
источников ТО-3: §3.2 (листы30/31) определяет СПОП/ИЗОП как начало/конец
операции; таблица1.1 (листы4/5) даёт равные min/max: AND/OR4 такта,
сборка/разборка53. Это логическая модель интервала, не воспроизведение
электрической диаграммы Д2. РПК остаётся явным входом; раннее разрешение
на полутакт не выводится из таблицы. Для XOR и других переменных операций
средние табличные длительности не превращаются в сроки.

`ArithmeticFixedCompletionTiming` допускает только четыре проверенных opcode.
`ArithmeticStageController` регистрирует срок при фактическом СПОП,
владеет его отменой и проверяет актуальность CPU-запроса перед ИЗОП.
Общий staged-обработчик сборки/разборки принимает память при ПВР,
вычисляет тем же битовым алгоритмом и публикует A/Y только при retirement.
Начальная выдача РПК, назначение БРУС, переменные сроки, аппаратный режим
ошибок и полная последовательность УУ остаются отдельной работой.

### Передача причины при ИЗОП и принятие УУ

ТО-3 §3.28, листы66–68: АУ передаёт УПр/АВП/УДО/код источника в регистр
БРУС при ИЗОП. Снятие местных сигналов через такт не является очисткой
принятого регистра. ТО-8 §6.12, листы116/117, задаёт разряды23–21:
111 — неправильный делитель,011 — переполнение,001 — контроль числа;
1–4 обозначают источник входного контроля. В режиме «только контроль»
местные арифметические сигналы не становятся переданной причиной.

`ArithmeticInterruptionPort` принимает свежий sample завершения и фиксирует
его в общем `SupervisorControl.InternalInterrupts`. Накопление причин
сохраняет прежнюю OR-семантику супервизора; приоритет одновременных источников
на физической шине не объявляется воспроизведённым.
`HardwareProcessorModel.AcceptArithmeticInterruption` принимает источник
отдельно, вне callback и без текущего CPU lease. Возвратную позицию и признаки
предоставляет УУ: §6.20 запрещает считать текущий K точным адресом отказа АУ.
Используется общий ОпПр1 (§6.16), вектор00500 и правила ПоП/ПоК/БРО.

Общее гашение АУ и программный ResetCpu не подтверждают ожидающий источник.
При принятии очищается ожидающая доставка, гостевой регистр остаётся под
управлением программы. Останов допускает повторное принятие. Следующая
выборка аппаратного владельца ожидает эту границу. Физическая политика
ошибок ещё не связана с guest staged-арифметикой; переменные сроки,
перекрытие УУ/АУ, память и устройства остаются незавершёнными.

#### Физическая политика в связанной команде CPU

Типизированное связывание явно принимает политику ошибок для supervisor CPU.
Выдача проверенного A/Y использует общую арифметику; сигнал переполнения
обрабатывается стадиями АУ и не повторяется как синхронный авост Dubna.
Неверный делитель с доставленной причиной завершает логический запрос без
публикации численного результата; УУ отдельно принимает причину с явной
позицией возврата. При подавленных сигналах численное продолжение пока явно
неподдержано. Отмена логического запроса не равна общему сбросу или PSb:
принадлежащие запросу события удаляются, поднятые сигналы сохраняются.
Синхронизация регистров разрешена лишь при простое, известном выходе и без
удержанного прерывания. Переменные IZOP/RPK,50-битный вход памяти и перекрытие
не добавлены этим блоком.
