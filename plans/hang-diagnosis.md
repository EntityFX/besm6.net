# Диагностика: почему симулятор C# «виснет» на dub-файлах

**Дата:** 21.08.2026
**Задача:** выяснить корневую причину зависания симулятора C# при запуске `.dub`.
**Вердикт:** это **НЕ баг ядра симулятора** (CPU/АЛУ/память/экстракоды работают).
Это **бесконечный цикл поллинга в ядре MONSYS**, в который попадает MONSYS при
запуске «тяжёлых» высокоуровневых трансляторов. Ядро C# корректно исполняет
MONSYS и «лёгкие» примеры; зависает именно на сервисе ОС, который в C#-порту
не реализован или реализован неверно.

---

## 1. Доказательства (сводка)

### 1.1 Ядро РАБОТАЕТ (проверено прогоном и тестами)
- `*bemsh` → **OK** (384K–392K инструкций, `examples_report.json`)
- `*madlen` → **OK**
- `*fortran` (FORTRAN-Dubna, «Hello World») → **завершается** (530K инструкций)
- `name.dub` → **OK** (209K)
- ALU-тесты зелёные (см. `plans/fix-alu.md`), `dotnet test` — зелёный

→ CPU, память, Е50 (мат. функции), Е57 (монтаж лент), Е64 (вывод), Е70 (disk/drum
I/O) — всё это реально работает: иначе `*bemsh`/`*fortran` не завершились бы.

### 1.2 Виснет ТОЛЬКО на «тяжёлых» компиляторах
| Пример | Компилятор | Статус |
|--------|-----------|--------|
| `forex.dub` | EXFOR (`*forex`) | **виснет** (PC=0002AA, 100M+ инструкций) |
| `pi.dub` | EXFOR (`*forex`) | **виснет** (PC≈07EAB) |
| `algol.dub` | ALGA (`*algol`) | **виснет** |
| `pascal.dub` | Pascal (`*pascal`) | **виснет** |
| `b/*.dub` | B-компилятор | **ERROR** (rc=1, crash) |
| `grafor/*` | grafor | **ERROR** (rc=1) |
| `fortran.dub` | FORTRAN-Dubna | **OK** (530K) |
| `bemsh.dub` | БЭМШ | **OK** |
| `madlen.dub` | МАДЛЕН | **OK** |

### 1.3 «Виснет» = ИСТИННЫЙ бесконечный цикл, а не «мало инструкций»
```
forex.dub --limit 100000000:
  PC=0002AA  asn 20073,atx 53(1)   ← одна и та же строка, PC не меняется
  ... (100 млн раз)
```

**Конкретная петля (trace forex.dub --limit 100000):**
```
┌─────────────────────────────────────────────────────────────────────────┐
│ 0002ED  wtc 1522,xta                                                   │
│ 0002EE  atx 155(7),vtm 37773(1)                                        │
│ 0002EF  xta 155(7),asn 20070         ← читает/пишет статус-слова      │
│ 0002F0  atx 155(7),yta 10000         ← обновляет очередь задач         │

│ 0002F3  xta 153(7),aax 10144(7)    ← вычитает/сравнивает счётчик      │
│ 0002F4  u1a 1423,xta 154(7)                                              │

│ 0002FC  xta 153(7),asn 20102                                               │
│ 0002FD  atx 0(7),yta 10000                                              │
│ 0002FE  asn 20153,wtc 0(7)                                               │
│ 0002FF  xts 30104(7),wtc 0(7)  ← читает статус устройства (30104)     │
│ 000300  asn 20120,aax 10152(7)                                           │
│ 000301  atx 153(7),aex 20147(7)                                         │
│ 000302  uza 1413,xta 153(7)                                              │

│ 000319  a+x 154(7),atx 154(7)                                            │
│ 00031A  x-a 20144(7),u1a 1413                                           │
│ 00031B  xta 153(7),utc                                                  │
│ 00031C  v1m 1437(4),vtm 37720(4) ← PIO: инициирует I/O!               │
│ 00031F  utm 10(4),asn 20100(4)                                          │
│ 000320  aox 10000(7),atx 0(7)   ← сбрасывает флаг готовности           │
│ 000321  uj 0(6),utc                                                    │
│ 00030A  vlm 1357(1),vlm 1355  ← ЦИКЛ: проверка → ветвление            │
└──────────────────────┬──────────────────────────────────────────────────┘
                       │
                       └───── (если условие не выполнено) ← цикл начинается заново
```

Это **диспетчер задач MONSYS** (job scheduler). Он крутит фиксированную
последовательность ~30 инструкций (0002ED→000321→00030A→0002ED...),
в которой:
- Читает **статус устройства** из памяти (PC=0002FF: `xts 30104(7)`)
- Вычитает счётчик (PC=00031A: `x-a 20144(7)`)
- Инициирует **PIO** (PC=00031C: `v1m 1437(4)`)
- Сбрасывает **флаг готовности** (PC=000320: `aox 10000(7)`)
- Проверяет условие (PC=0002F5/00030A) → если НЕ выполнено → **повтор**

**Корень:** флаг готовности (статус-слово в памяти) никогда не становится
"готово", т.к. механизм прерываний/DMA-статуса в C#-порту отсутствует.
MONSYS корректно ждёт — но сигнал, который должен придти, **не приходит**.

## 2. Корневая причина (по убыванию вероятности)

### 2.1 (Самая вероятная) Не поднят признак завершения I/O / не реализован сервис ОС
MONSYS — реальный образ ОС (288 страницы). Запуск HL-компилятора =
загрузка с диска + трансляция + job-планирование. В MONSYS I/O идёт через
**интерrupt-модель**: «выдать канальную команду → поллить статус-регистр →
прерывание о завершении». В C#-порту (см. `ExtracodeHandler.E70`, line 422-494)
передача делается **синхронно**, но **статус-регистр «готовность устройства»
нигде не выставляется** — нет механизма прерываний/флагов готовности.

Следствие: любой путь MONSYS вида «I/O → ожидание готовности → continue»
зацикливается, т.к. флаг-условие никогда не становится true.
Подтверждение: разработчики сами заложили детектор этого случая —
`ExtracodeHandler.cs` line 85-93:
> «MONSYS is polling for I/O/interrupt that never arrives.»

EXFOR/ALGA/B/Pascal используют этот путь активнее, чем FORTRAN-Dubna/БЭМШ —
поэтому именно они виснут, а FORTRAN-Dubna/BEMSH «на грани» доходят (530K).

### 2.2 Не-/частично реализованные сервисы ядра MONSYS (C# vs C++)
Из `ExtracodeHandler.cs`:
| Экстракод | Назначение | C# | Влияние |
|-----------|-----------|----|---------|
| **E72** (line 215-218) | страницы памяти ОС Дубна | **пустой no-op** | планировщик задач/присвоение страниц зависает |
| **E76** (line 239-246) | вызов рутин ядра | **частично** (throw на addr≥10) | вызовы рутин ядра не завершаются |
| **E21** (line 122) | семафоры lock/release | **no-op** | ожидание семафора = вечный цикл |
| **E65** (line 164-202) | выключатели пульта | **частично** (throw на неизвестных) | режимы ОС задаются неверно |
| **E63** (line 129-159) | ОС Дубна | **частично** | сервисы job-контроля неполны |
| **E71** (line 498-521) | терминальный ввод | `Console.ReadLine()` | в неблокируемом режиме возвращает `""` → MONSYS может «ретырить» |

Именно E72/E76/E21 — это то, на чём держится job-планирование MONSYS, а значит
и запуск HL-трансляторов. E72 = no-op — **главный кандидат**.

### 2.3 (Второстепенно) Искривлённый вывод, НЕ причина виса
`fortran.dub` печатает мусор-числа («15002…») вместо «Hello, World!» — это
отдельный дефект E64 (real/text output, `plans/bring-up-plan.md`), но он НЕ
блокирует завершение — длятся лишь значения. Не корневая причина виса.

## 3. Почему это «корневая причина», а не симптом
- Симптом: PC застревает на одной инструкции и исполняет её 100M+ раз.
- Причина: ядро MONSYS крутит цикл ожидания (I/O-готовность / E72/E76/E21),
  а соответствующий сервис в C#-порту не «поднимает» ожидаемый флаг/условие.
- Доказательство, что ядро невиновно: идентичный «Hello World» на
  `*fortran` и `*bemsh`/`*madlen` завершается; виснут только пути EXFOR/ALGA/B,
  требующие полного набора сервисов ядра.

---

## 4. Как подтвердить/исправить (следующие шаги)
1. **Логируй E72/E76/E21/E65/E71 в `Handle()`** (как E75, line 85-81):
   печатать `opcode + addr(M16) + PC` при каждом вызове. Прогнать `forex.dub`
   со `--limit 200000` и увидеть, какой экстракод гоняется в цикле до PC=0002AA.
2. **Сверить E72/E76 с C++** (`ref/extracode.cpp`, `ref/e57.cpp`):
   - E72: присвоение/снятие страниц памяти, status-коды в ACC.
   - E76: полный dispatch рутин ядра.
   - E21: корректные семафоры (lock/ready/timeout).
3. **Флаг I/O-готовности**: после E70 (read/write страницы) выставлять
   соответствующий статус-бит (как в C++ disk.cpp/drums.cpp), который MONSYS
   опрашивает в поллинг-цикле. Найти в C++ `machine.cpp`/`disk.cpp` имя этого
   регистра и повторить в C#.
4. **E71 input**: в неблокируемом/авто-режиме не возвращать «пустую ретыр» —
   либо дать EOL сразу, либо сделать input-флаг готовым, чтобы MONSYS не крутил.

### Критерий «почему выяснено»
- Прогон `forex.dub` с логгированием экстракодов покажет ОДИН повторяющийся
  вызов (E72/E76/E21/I/O-статус) → подтверждает §2.
- Реализация этого сервиса → `forex.dub` проходит 0002AA и завершается.
